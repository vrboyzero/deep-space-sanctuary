# 心智记忆与用户画像功能分析

更新时间：2026-06-11

## 1. 范围与结论

本文基于当前仓库代码、WebChat/RPC 暴露能力、定向测试结果，以及外部官方资料，对 `star-sanctuary` 中“心智记忆”和“用户画像”相关实现做一次工程视角的状态分析。

结论先行：

- 当前仓库的“长期记忆基础设施”成熟度较高，已经明显超出普通 RAG。
- 当前仓库的“运行时心智注入”处于中上水平，已经具备轻量摘要、预算控制、会话边界控制。
- 当前仓库的“用户画像”仍偏弱，主要是文件驱动和自由文本锚点，不是强结构化 profile store。
- 当前仓库的“心智记忆”更像“静态 persona + 长期记忆 + 运行时摘要聚合”，还不是独立的认知状态机或可演化心智模型。

综合判断：

- 工程记忆成熟度：`8.1 / 10`
- 心智/画像成熟度：`6.6 / 10`

## 2. 当前实现映射

### 2.1 静态画像层

当前仓库存在一条稳定的静态 persona 注入链路，主要由以下文件组成：

- `SOUL.md`
- `USER.md`
- `IDENTITY.md`
- `MEMORY.md`

相关代码：

- `packages/belldandy-agent/src/system-prompt.ts`
- `packages/belldandy-agent/src/workspace.ts`

当前行为：

- `system-prompt.ts` 会把上述文件按优先级注入到 `static-persona` 段中。
- `workspace.ts` 中的 `extractIdentityInfo()` 会从 `IDENTITY.md` / `USER.md` 里解析 `名字 / 头像 / Emoji` 等基础身份字段。

这一层的优点是稳定、简单、可控、易编辑；缺点是：

- 画像主要是“文档本体”，不是“结构化状态”。
- `USER.md` 的硬解析只覆盖基础身份字段，无法表达高质量偏好、沟通风格、长期约束、关系网络、置信度与冲突状态。

### 2.2 长期记忆层

长期记忆核心在：

- `packages/belldandy-memory/src/manager.ts`
- `packages/belldandy-memory/src/store.ts`

当前实现不是单表记忆，而是完整的记忆底座，至少包含：

- `chunks`
- `embedding_cache`
- `tasks`
- `task_memory_links`
- `task_activities`
- `experience_candidates`
- `experience_usages`
- `memory_sources`
- `memory_scores`
- `memory_tree_nodes`
- `memory_tree_edges`
- `memory_clean_reports`
- `chunks_fts`
- `chunks_vec`

当前具备的主要能力：

- FTS 全文检索
- 向量检索
- 规则重排
- 时间衰减重排
- 同源惩罚与 MMR 去重
- adaptive retrieval skip
- node-assisted retrieval
- memory tree 治理
- source inventory / score rebuild
- dedup / vacuum / ingest / report ledger

这说明仓库中的“记忆”已经不是简单的“历史消息检索”，而是具备可治理、可维护、可扩展的数据面。

### 2.3 运行时心智摘要层

运行时心智摘要链路在：

- `packages/belldandy-core/src/mind-profile-snapshot.ts`
- `packages/belldandy-core/src/mind-profile-runtime-digest.ts`
- `packages/belldandy-core/src/mind-profile-runtime-prelude.ts`

当前行为：

- `buildMindProfileSnapshot()` 会聚合：
  - `USER.md`
  - `MEMORY.md`
  - 最近 durable memory
  - resident digest
  - experience usage
  - profile/global memory tree node
- `buildMindProfileRuntimeDigest()` 会把这些信号压成少量行数、字符预算受限的 digest。
- `buildMindProfileRuntimePrelude()` 会把 digest 注入为 `<mind-profile-runtime>` prelude。

当前优点：

- 有预算控制：`maxLines / maxLineLength / maxChars`
- 有弱信号 gating：`minSignalCount`
- 有 session boundary：只注入 `main` 会话，不注入 `goal / goal_node`

当前缺点：

- 注入内容仍以“摘要行”为主，不是结构化 profile state。
- 心智层读的是“聚合结果”，不是“画像字段的显式真值层”。

### 2.4 任务记忆、经验沉淀、共享治理与 Dream

这部分已经形成多条成熟链路：

- `packages/belldandy-core/src/context-injection.ts`
- `packages/belldandy-memory/src/task-processor.ts`
- `packages/belldandy-memory/src/task-recap.ts`
- `packages/belldandy-core/src/server-methods/memory-experience.ts`
- `packages/belldandy-memory/src/dream-input.ts`
- `packages/belldandy-core/src/server.ts`

当前能力包括：

- `recent-memory`
- `work-overview`
- `resume-details`
- `workRecap`
- `resumeContext`
- `experience candidate`
- `experience synthesis`
- `experience publish`
- `experience usage`
- `skill freshness`
- `shared review / claim / revoke / batch source review`
- `external ingest`
- `dedup preview/apply`
- `vacuum preview/apply`
- `Dream` 反思、commons/export、Obsidian

这意味着系统已经具备“做过什么、为什么停、下步做什么、哪些经验可复用、哪些共享记忆需要治理”的产品级链路。

## 3. 评分口径

- `9-10`：能力强、链路闭环、可产品化、可维护
- `7-8`：主链路成熟，但在结构化、治理或边界能力上仍有缺口
- `5-6`：可用，但偏弱或偏局部实现
- `0-4`：概念存在但实现不完整，或只停留在草案层

## 8. 当前主要缺口与风险

### 8.1 结构化用户画像缺口

这是当前最大的短板。

目前的画像形态更接近：

- `USER.md` 文本
- `IDENTITY.md` 文本
- 运行时摘要行

而不是：

- 有 schema 的 profile document
- 有置信度的字段值
- 有来源链的事实记录
- 有冲突处理与 supersede 机制的画像状态

直接影响：

- 用户偏好很难字段级更新
- 新旧偏好冲突无法清晰裁决
- 画像历史无法稳定审计
- runtime digest 难以区分“稳定画像”和“近期噪声”

### 8.2 心智记忆仍偏摘要聚合

当前的 `mind-profile-runtime` 是有价值的，但它本质是“把多种来源压成几行背景提示”，而不是“独立的可推演心智状态”。

直接影响：

- 无法表达多层时间尺度
- 无法表达当前置信度
- 无法表达是否已过期、是否被反证
- 无法表达画像字段的最后确认时间

### 8.3 记忆分类已存在，但运行策略还不够显式

仓库已支持：

- `preference`
- `experience`
- `fact`
- `decision`
- `entity`

但这些更多还是“分类标签”，还不是“写入策略、检索策略、遗忘策略、治理策略”的一级驱动。

### 8.4 新鲜度与冲突治理不统一

当前仓库已经有：

- `updated_at`
- `recency_score`
- `interaction_score`
- `usageCount`
- `skill_freshness`

但仍缺少统一的：

- `last_confirmed_at`
- `stale`
- `contradicted_by`
- `superseded_by`
- `confidence`
- `review_status`

## 9. 外部方案借鉴与可优化需求点

### 9.1 Mem0 可借鉴点

官方资料显示，Mem0 已把记忆从一开始就做成明确的层次和操作面：

- `Conversation memory`
- `Session memory`
- `User memory`
- `Organizational memory`

可借鉴点：

1. 显式区分“当前任务上下文”和“用户长期画像”
2. 提供 `add / search / update / delete / history`
3. 提供记忆更新操作，不要求先删后加
4. 提供 memory decay，把最近访问过的记忆在搜索时上浮，而不是简单硬删除
5. 提供 memory evaluation，把记忆质量变成可测对象

对本仓库的启发：

- 应把当前 `USER.md + MEMORY.md + runtime digest` 升级为显式 `profile state + history`
- 应把 `recent use` 和 `last confirmed` 引入画像与 durable memory 的统一新鲜度策略
- 应补充画像/记忆评估面板，而不是只看检索是否“感觉可用”

### 9.2 LangMem / LangGraph 可借鉴点

官方资料显示，LangMem 的记忆设计非常适合作为“结构化画像 + 分层记忆”的参考：

- user profile 采用“单一、简洁、结构化 profile 文档”模式
- semantic memory 用于事实、偏好、关系等集合型长期知识
- episodic memory 用于沉淀成功经验与完整情境
- hot path 支持实时记录
- background manager 支持延迟、去抖、异步整理

可借鉴点：

1. 把用户画像从“自由文本锚点”升级为“单一 canonical document”
2. 明确区分：
   - `profile semantic`
   - `episodic task`
   - `procedural experience`
3. 支持后台记忆整理，而不是把所有写入都放在主会话热路径
4. 明确指导什么时候写记忆、什么时候修正旧记忆

对本仓库的启发：

- 现有 Dream runtime 很适合承接 background memory manager 角色
- 现有 task / experience 已接近 episodic / procedural 的雏形
- 现有 profile/global tree 很适合作为上层压缩层，但下层需要 canonical profile state

### 9.3 Letta 可借鉴点

官方资料显示，Letta 的记忆设计重点在：

- memory blocks：始终可见、固定挂在上下文里的核心记忆
- archival memory：检索式长期记忆库
- shared memory blocks：多 agent 共享块
- sleep-time agents：异步反思并更新 memory blocks

可借鉴点：

1. 明确区分“始终在 prompt 里可见的核心画像”和“按需检索的外部长记忆”
2. 共享记忆块与多 agent 协作关系天然清晰
3. sleeptime / dreaming 不只是生成摘要，而是要回写核心记忆

对本仓库的启发：

- 当前 `SOUL.md / USER.md / IDENTITY.md / MEMORY.md` 很像 memory blocks
- 当前 `chunks / memory search / tree` 很像 archival memory
- 当前 Dream runtime 与 Letta 的 sleep-time agents 非常接近
- 当前最大缺口是：Dream 还没有稳定回写“核心画像真值层”

### 9.4 可优化需求点清单

按优先级排序，建议补齐以下需求：

1. 结构化 profile state
2. 画像字段级冲突处理
3. 画像字段级来源链与历史
4. profile / semantic / episodic / procedural 分层
5. background memory consolidation
6. 统一 freshness / stale / supersede 策略
7. 记忆质量评估与观测面板
8. 多用户命名空间与共享画像

## 10. 记忆系统升级路线图

### 10.1 Goal

把当前系统从“多源摘要聚合型记忆”升级为“结构化用户画像 + 分层长期记忆 + 后台反思整理”的记忆系统，同时保持现有任务续做、经验沉淀、共享治理与 WebChat 产品面不回退。

### 10.2 Risk Level

整体风险：`中高`

主要失败模式：

- 画像字段被错误覆盖，导致稳定偏好丢失
- 新旧偏好冲突未被显式治理，造成 prompt 漂移
- runtime 注入内容变多，带来 token 膨胀
- 新 schema 与旧 `USER.md / MEMORY.md` 兼容不好，迁移成本过高
- 将所有记忆都结构化后，写入与治理成本显著上升

### 10.3 Feasibility

整体可行性：`高`

原因：

- 已有 durable extraction，可作为写入入口
- 已有 memory tree，可作为上层压缩视图
- 已有 Dream runtime，可作为后台 consolidation 入口
- 已有 WebChat / RPC / report ledger，可作为产品与治理面承载

### 10.4 Rough Workload

粗略工作量按单人全职估算：

- `P0`：中到偏大
- `P1`：中
- `P2`：中到偏大

更适合按 `3` 个里程碑推进，而不是一次性重做。

### 10.5 Closure Boundary

本路线图包含：

- 结构化用户画像
- 分层记忆策略
- 后台反思回写
- 新鲜度/冲突治理
- 可观测性与评估面

本路线图不包含：

- 模型微调
- 强化学习
- 跨仓库统一画像平台
- 完整权限体系重构

当前 `P0` 实施期明确不包含：

- `P2-3 多用户 / 多实体命名空间`
- `P2-4 人工审核与高风险画像写入守门`

“完成”定义：

- 画像不再仅依赖 `USER.md` 自由文本
- 画像写入具备来源、冲突与历史
- 主会话读取的是 canonical profile state + relevant durable memory
- Dream/后台流程可以安全整理而不是只生成旁路摘要

### 10.6 行为验收描述

1. Given 用户在多轮会话中明确表达稳定偏好，When durable extraction 与 profile update 运行，Then 系统应把对应字段写入 canonical profile state，并记录来源链。
2. Given 用户表达了与旧画像冲突的新偏好，When profile merge 运行，Then 系统不应静默覆盖旧值，而应记录 supersede / conflict 状态并保留审计历史。
3. Given `main` 会话启动且存在足够稳定画像信号，When runtime prelude 生成，Then 系统应优先从 canonical profile state 生成简洁画像摘要，而不是只依赖自由文本文件摘取。

### 10.8 P1：把记忆分类升级为分层策略

目标：

- 让当前已有分类从“标签”升级为“运行策略”

#### P1 范围收敛结论

风险级别：

- `中`

主要失败模式：

- 把 `P1` 做成“一次性重写整套 memory system”，导致改动面失控
- 在 `project semantic` 上过早引入新的自动写入链，和 `P0` 刚建立的真值层节奏混在一起
- freshness 语言一次性覆盖过深，结果停留在概念层，无法接到现有代码与观测面
- Dream、审核守门、多实体命名空间提前回流，导致 `P1/P2` 边界再次模糊

可行性与前置条件：

- `P0` 已完成，`profile state` 可作为 `P1` 的第一层稳定锚点
- 现有代码里已经存在可直接纳入 `P1` 的成熟模块：
  - `profile state / mind-profile-runtime`
  - `task / workRecap / resumeContext / derived-task-retrieval`
  - `experience candidate / usage / skill freshness`
  - `shared review / dedup / inventory / tree report`
- 因此 `P1` 不需要从零新建系统，优先做“统一分层语言 + 显式映射 + 读取侧收敛”

P1 本轮明确包含：

- 定义统一 `memory class` / layer contract，覆盖：
  - `profile semantic`
  - `project semantic`
  - `episodic task`
  - `procedural experience`
  - `governance`
- 将现有实现显式映射进分层模型：
  - `profile state` -> `profile semantic`
  - `global/profile tree + curated durable memory + MEMORY.md 稳定行` -> `project semantic`
  - `task / workRecap / resumeContext / task activities / derived-task-retrieval` -> `episodic task`
  - `experience candidate / published method / published skill / usage / skill freshness` -> `procedural experience`
  - `shared review / claim / revoke + dedup / vacuum / inventory / tree report` -> `governance`
- 统一 freshness / stale / supersede 语言，并优先和现有：
  - `skill freshness`
  - `recency_score`
  - `interaction_score`
  - `derived task recency`
  做语义对齐
- 让 runtime / learning review / doctor / observability 逐步消费“分层后的显式结果”，而不是继续直接读杂合聚合源

P1 本轮明确不包含：

- `Dream` 升级为后台 consolidation writer
- 高风险画像字段自动写入
- 人工审核与高风险画像守门
- 多用户 / 多实体命名空间
- 全量替换现有 `memory.sqlite`、索引、检索链
- WebChat 大型编辑面或评估面板重做
- 新一轮“大而全”的 project semantic 自动提取写入链

关闭边界：

- 做完 `P1` 并不意味着所有记忆都变成新的独立表或独立写入器
- `P1` 的完成定义是：现有核心记忆资产已经能被稳定归入统一层级语言，并能在 runtime / review / observability 中按层读取与解释
- `P2` 才继续处理 Dream 后台整理、评估面板、多实体与高风险审核

建议拆成三批推进：

1. `P1-A`：memory class contract + 现有模块显式映射
2. `P1-B`：freshness / stale / supersede 统一语言与读取优先级
3. `P1-C`：learning review / doctor / runtime observability 接入分层视图

推荐理由：

- 先统一语言，再统一读取，再补治理与观测
- 先让现有成熟模块“归位”，再决定哪些层值得新增真值写入
- 这样可以避免 `P1` 过早滑向 `P2`

#### P1-1 显式定义四层记忆模型

4. `P1-C1` 让 learning review / doctor / runtime inspect 能看到 classed signals

#### P1-A1 实施方案：五层 contract 与现有模块映射

##### Goal

把 `profile semantic / project semantic / episodic task / procedural experience / governance` 从“文档里的概念层”收敛成“代码里可落地的统一 contract”，并明确每一层：

- canonical source 在哪里
- primary write path 是什么
- 哪些模块只是 derived read model / runtime projection
- runtime / learning review / doctor / inspect 应该消费哪一层结果

这一批的目标不是新建整套 writer，而是先把现有成熟模块稳定归位，避免后续 `P1-B / P1-C` 继续建立在混合聚合语义之上。

##### Candidate Options

###### 方案 A：只在文档中统一命名，不落代码 contract

优点：

- 改动最小
- 没有任何运行时风险

缺点：

- 无法约束后续代码接线
- `learning review / doctor / runtime inspect` 仍会继续各自消费不同口径的字段
- 不能解决“树节点/派生视图被误当成真值层”的问题

结论：

- 不建议作为 `P1-A1` 主方案

###### 方案 B：新增共享 contract + binding registry，但不重做底层存储

做法：

- 新增独立类型文件定义五层 `memory class`
- 为每层补 `canonical source / truth mode / primary write path / read adapters / runtime consumers / review consumers`
- 通过 binding registry 把现有模块显式挂到五层之下
- 底层 `task / experience / tree / inventory / dedup / profile state` 先不重构存储

优点：

- 改动可控
- 能直接支撑 `P1-B` freshness 统一与 `P1-C` 观测接线
- 符合当前仓库“先最小接线、再逐层收敛”的节奏

缺点：

- `project semantic` 仍会保留“聚合真值契约”而不是独立状态表
- 需要对 `derived` 与 `canonical` 的边界写得足够严格

结论：

- 推荐

###### 方案 C：直接为五层都补独立 state / writer / table

优点：

- 结构最整齐
- 理论上长期最统一

缺点：

- 明显越过 `P1-A1` 边界
- 会把 `project semantic`、Dream、审核守门、多实体等议题提前卷进来
- 对当前 `manager.ts` 等大文件的技术债不友好

结论：

- 本期不取

##### 推荐方案

推荐采用：`方案 B：共享 contract + binding registry，底层存储暂不重做`

推荐理由：

- `P0` 已经把 `profile semantic` 的第一层 canonical truth 建稳，适合作为 `P1` 的锚点
- `episodic task / procedural experience / governance` 在当前仓库里已经有成熟写入与读取模块，缺的是统一 class contract，不是重写底座
- `project semantic` 当前最需要先澄清“什么算 canonical、什么只是聚合读模型”，而不是马上上新表
- `packages/belldandy-memory/src/manager.ts` 已明显超大，`P1-A1` 更适合把新增逻辑拆到独立 contract / binding 文件，`manager` 只保留 wiring

##### 风险级别与主要失败模式

风险级别：

- `中`

主要失败模式：

- 把 `memory tree` 或 `derived retrieval` 误标成某层 canonical truth，导致真值边界继续模糊
- 把 `governance` 既当记忆内容层又当审查工单层，造成 review/apply 语义混乱
- 为 `project semantic` 过早补自动写入链，反而让 `P1-A1` 失去收口
- 统一 contract 时继续把新逻辑堆进 `manager.ts`，扩大技术债

##### 可行性与前置条件

整体可行性：`高`

前置条件：

- `P0` 的 `profile state` 已完成并可直接作为 `profile semantic` canonical source
- `task / experience / governance` 相关模块当前都已存在稳定读写入口
- `P1-A1` 只做 contract 与模块映射，不要求本批同步统一底层分值算法与新写入器

##### Rough Workload

`P1-A1` 工作量估计：`S-M`

拆分建议：

1. 文档与类型契约：`S`
2. binding registry 与模块映射：`S`
3. 首批 consumer 接线点预留：`S-M`

适合拆成 `2-3` 个小 PR，而不是继续堆到单个大改动里。

##### Closure Boundary

`P1-A1` 明确包含：

- 定义五层 `memory class` 统一命名
- 明确每层的 `canonical source / primary write path / read model / runtime usage / observability usage`
- 输出“现有模块 -> 五层 contract”的显式映射
- 明确哪些模块是 `canonical`，哪些只是 `derived` / `runtime projection` / `review artifact`

`P1-A1` 明确不包含：

- 新建 `project semantic state` 独立表
- 新增 Dream writer
- 新增高风险画像字段自动写入
- 多实体命名空间

完成标准：

- 五层都有统一 contract 描述
- 每层至少有一个明确 canonical source
- 现有主要模块都能被映射到五层之一，且标清 truth mode
- 后续 `P1-B / P1-C` 可以基于该 contract 继续编码，而不再重新争论边界

##### Contract 形状

`P1-A1` 不建议先做“大而全总 schema”，而是先统一一套最小 contract 字段语义。建议 contract 至少显式覆盖：

- `memoryClass`
  - 取值：`profile_semantic | project_semantic | episodic_task | procedural_experience | governance`
- `truthMode`
  - 取值：`canonical | derived | runtime_projection | review_artifact`
- `canonicalSource`
  - 当前层真正的事实锚点或审计锚点
- `primaryWritePath`
  - 当前仓库里实际写入该层的主入口
- `primaryReadModels`
  - 当前仓库里主要的派生读取面
- `runtimeConsumers`
  - prompt、resume、task continuation 等运行时消费方
- `observabilityConsumers`
  - doctor、inspect、learning review、report preview 等观测面
- `freshnessSignals`
  - 当前层后续需要统一的新鲜度字段来源
- `lineageSignals`
  - 当前层的 source refs、review decision、history/event 等来源链信号

实现建议：

- 新增独立类型文件，例如 `packages/belldandy-memory/src/memory-class-contract.ts`
- 新增独立 binding 文件，例如 `packages/belldandy-memory/src/memory-class-bindings.ts`
- 不把这套 contract 继续塞进 `packages/belldandy-memory/src/manager.ts`

### 10.11 边界澄清与目标分层图

这一节用于明确一件事：

- `profile state` 缺口，主要是在说“用户画像”
- `mind layer` 读聚合结果的问题，是在说“整个心智记忆层”

也就是说，P0 不是要一次性把整个心智记忆系统全部重写，而是要先把“用户画像真值层”补出来；P1 才是把更广义的心智记忆做分层真值化。

#### 10.11.1 边界定义

用户画像回答的是：

- 这个用户是谁
- 有哪些稳定偏好
- 习惯怎样协作
- 对输出风格、节奏、约束有什么长期要求

整个心智记忆回答的是：

- 用户画像是什么
- 当前项目有哪些长期事实与稳定约束
- 最近任务做到哪里、为什么停下
- 哪些经验已经被证明可复用
- 哪些 shared / resident 记忆还在治理中

关系上可以理解为：

- 用户画像是心智记忆的一个子集
- 心智记忆包含用户画像，但不等于用户画像

#### 10.11.5 对 P0 / P1 范围的直接影响

P0 只解决：

- 用户画像没有显式真值层
- runtime 对画像的读取还主要依赖自由文本与聚合摘要
- durable extraction 还不能稳定更新画像字段

P1 才解决：

- 整个心智记忆的分层真值化
- 项目语义、情节任务、程序性经验、共享治理之间的统一数据语言
- runtime mind layer 不再直接读杂合聚合源，而是读分层后的 canonical state

换句话说：

- `P0 = 先把“人”这层做实`
- `P1 = 再把“整套心智记忆”分层做实`

### 10.12 P0 范围收敛说明

`P0` 实施期只设计并推进 `P0`，即“建立结构化画像真值层”。

`P0` 包含：

- canonical profile state
- profile patch 写入协议
- conflict / history 最小闭环
- runtime 读路径从自由文本优先切到 profile state 优先
- `USER.md` 兼容与镜像策略

`P0` 明确不包含：

- `P1` 的整套心智记忆分层真值化
- `P2-1 Dream` 后台整理升级
- `P2-2` 记忆评估面板
- `P2-3` 多用户 / 多实体命名空间
- `P2-4` 人工审核与高风险画像写入守门

这样收口的原因：

- 当前最明确、收益最高、耦合最小的缺口在用户画像真值层
- 如果不先建立 profile state，后续 `P1/P2` 都缺少稳定锚点
- 一次性把整套心智记忆全部重做，风险过高，回滚成本也高

### 10.13 P0 实施方案计划

#### 10.13.1 Goal

在不破坏现有任务记忆、经验沉淀、shared 治理与 Dream 主链路的前提下，为用户画像建立一个：

- 结构化
- 可追踪来源
- 可处理冲突
- 可被 runtime 直接读取
- 可与现有 `USER.md` 共存

的 canonical profile state。

#### 10.13.2 Candidate Options

本期 P0 有三个主要实现候选。

##### 方案 A：`USER.md` 增强型文件方案

做法：

- 继续以 `USER.md` 为真值源
- 在文档中增加约定结构、frontmatter 或锚点块
- durable extraction 直接回写 `USER.md`

优点：

- 人工可读性最好
- 改造面最小
- 不需要新表

缺点：

- 字段级冲突难处理
- 审计历史、来源链、置信度表达困难
- 读写并发与回写合并复杂
- 未来扩到多实体命名空间会非常吃力

适配判断：

- 适合作为临时过渡
- 不适合作为 P0 主方案

##### 方案 B：SQLite 单文档 JSON 方案

做法：

- 在 SQLite 新增一个 profile state 记录
- 将整个画像作为一个 JSON blob 持久化
- 变更时整体读取、整体 merge、整体写回

优点：

- 与现有 `MemoryStore` 风格兼容
- schema 最简单
- 首版开发速度快

缺点：

- 字段级 diff、冲突与历史查询不够自然
- 单字段修改也要整体 merge
- 后续做字段级治理、统计、观测会变笨重

适配判断：

- 可行
- 但中期会很快遇到治理瓶颈

##### 方案 C：SQLite 行级真值层 + 事件日志 + `USER.md` 镜像

做法：

- 在 SQLite 中保存 canonical profile state
- 以“字段路径”为粒度保存当前值
- 额外保留 profile event / history
- `USER.md` 降级为人工可读镜像或手工编辑入口

优点：

- 字段级冲突处理自然
- 历史、来源链、置信度、新鲜度都容易表达
- runtime 可直接读取结构化状态
- 后续接 `P1/P2`、多实体命名空间、审核守门都顺

缺点：

- 比方案 A/B 初期工作量稍大
- 需要设计 row model 与镜像规则

适配判断：

- 最适合本仓库现有能力与后续演进方向

#### 10.13.3 推荐方案

推荐采用：`方案 C：SQLite 行级真值层 + 事件日志 + USER.md 镜像`

推荐理由：

- 当前仓库已经有成熟的 SQLite schema 扩展方式，见 `packages/belldandy-memory/src/store.ts`
- 当前仓库已经有 durable extraction 与 runtime snapshot 两个天然接线点，适合直接接入结构化状态
- 当前仓库未来明确会走 `P1 / P2` 分层与治理路线，行级真值层比单文档 blob 更容易承接
- `USER.md` 仍可保留为人工可读入口，避免完全牺牲可维护性

#### 10.13.6 `USER.md` 的角色调整

P0 之后，`USER.md` 不再是唯一真值源，而是以下两种角色之一：

1. 可读镜像

- 系统根据 `profile_state_entries` 生成或刷新摘要化 `USER.md`

2. 手工编辑入口

- 用户仍可修改 `USER.md`
- 但写入链路不直接把 `USER.md` 当真值
- 而是走“解析 -> profile patch -> merge -> event log”流程

推荐 P0 先做：

- `profile state -> USER.md` 单向镜像

P0 暂不做：

- 复杂的双向自动同步

原因：

- 双向同步很容易带来冲突与误覆盖
- 单向镜像已经足够支持 runtime 与人工查看

#### 10.13.7 写入链路设计

P0 推荐拆成三种写入源。

1. durable extraction 写入

入口：

- `packages/belldandy-memory/src/manager.ts`

行为：

- durable extraction 产出普通 durable memory
- 同时尝试产出 profile patch
- 仅高置信度、稳定信息可落入 profile state

2. 手工编辑导入

入口：

- `USER.md`

行为：

- 只解析有限结构字段
- 生成 profile patch
- 走统一 merge 流程

3. 后台整理写入

P0 暂不实现真正后台 consolidation

行为：

- 仅预留事件模型与 merge 接口
- 后续由 Dream / sleeptime-like runtime 接入

#### 10.13.8 读取链路设计

P0 推荐调整读取优先级如下：

1. 先读 `profile_state_entries`
2. 再读 `USER.md` 作兼容补充
3. 再读 recent durable memory / memory tree / resident digest 作为非画像信号

直接影响文件：

- `packages/belldandy-core/src/mind-profile-snapshot.ts`
- `packages/belldandy-core/src/mind-profile-runtime-digest.ts`

目标效果：

- runtime 第一层画像锚点来自 canonical profile state
- 聚合摘要仍保留，但降级为补充层

#### 10.13.9 Merge 与冲突策略

P0 只做最小冲突策略，不追求一步到位。

建议规则：

1. 同路径、同类型、同值：

- 只更新 `lastConfirmedAt`
- 追加 source refs

2. 同路径、同类型、不同值：

- 如果新值置信度显著更高，标记旧值 `superseded`
- 否则写入 event，保留 `conflict_pending`

3. 明显短期值：

- 不进 profile state
- 仅保留为普通 durable memory

4. 缺少足够证据：

- 记录为 event candidate 或跳过
- 不直接写真值层

P0 暂不做：

- 自动多值并存策略
- 复杂的人审流程
- 多 reviewer 审批

#### 10.13.11 分阶段执行步骤

##### Step 1：定义类型与表结构

目标：

- 建立 profile state 最小数据模型

包含：

- `profile-state-types.ts`
- `profile_state_entries`
- `profile_state_events`
- `MemoryStore` 基础读写接口

主要风险：

- path/value model 设计不稳，后续难扩展

回滚方式：

- 新表独立存在，不改老表
- 出问题可停用读取，不影响旧链路

工作量：

- `S-M`

预期效果：

- 为后续写入和 runtime 读取提供稳定底座

##### Step 2：实现 merge 引擎与 event log

目标：

- 让 profile patch 可以安全合并

包含：

- patch normalize
- same-value confirm
- conflict / supersede
- source refs merge
- event log append

主要风险：

- merge 规则过于激进，误覆盖旧值

回滚方式：

- 保留旧值与 event log
- 可关闭自动写入，仅保留事件记录

工作量：

- `M`

预期效果：

- 真值层第一次具备“可更新但可审计”的基本能力

##### Step 3：接入 durable extraction -> profile patch

目标：

- 让真实对话可更新画像

包含：

- 扩 extraction 输出结构
- 增加 profile patch 过滤
- 只允许高置信稳定信息落表

主要风险：

- 短期信息误入长期画像

回滚方式：

- 开关关闭 profile patch apply
- durable memory 主链路仍保留

工作量：

- `M`

预期效果：

- 系统首次拥有“自动画像更新”能力

##### Step 4：切 runtime 读取优先级

目标：

- 让 runtime 从真值层拿画像

包含：

- `mind-profile-snapshot.ts` 调整读取链路
- `mind-profile-runtime-digest.ts` 调整信号来源
- 保留 `USER.md` / `MEMORY.md` 兼容兜底

主要风险：

- 画像为空时 prompt 质量回退

回滚方式：

- 保留旧读取路径作为 fallback

工作量：

- `S-M`

预期效果：

- `mind-profile-runtime` 从聚合摘要向“真值层优先”切换

##### Step 5：补最小可观测与兼容出口

目标：

- 让开发者能看见 P0 写入结果

包含：

- 最小只读 RPC
- `USER.md` 镜像或 profile inspect 输出
- 定向测试

主要风险：

- 没有可观测出口，后续调试困难

回滚方式：

- 只读接口不影响主链路

工作量：

- `S`

预期效果：

- P0 结果可查、可测、可解释

#### 10.13.12 Validation

P0 完成后至少需要以下验证层级。

1. Unit

- profile patch normalize
- merge / conflict / supersede
- event log append
- `USER.md` 轻解析到 patch

2. Integration

- durable extraction -> profile patch -> store
- profile state -> mind-profile snapshot -> runtime prelude

3. Regression Focus

- `goal / goal_node` 仍不注入 `mind-profile-runtime`
- 现有 task / experience / shared review 不受影响
- 未生成 profile state 时，旧 `USER.md` 路径仍可工作

4. Manual

- 在 WebChat 中检查 runtime 注入是否更稳定
- 检查 `USER.md` 镜像是否可读
- 检查 profile history 是否可追溯

#### 10.13.13 风险等级与阻塞点

风险等级：`中`

主要失败模式：

- profile merge 误判冲突，导致稳定偏好被覆盖
- extraction 误把短期上下文写入长期画像
- runtime 切读后，旧工作区没有 profile state，导致画像信号变弱
- `USER.md` 镜像策略不清晰，用户误以为它仍是唯一真值

当前最可能的阻塞点：

- profile path 设计是否足够稳
- merge 规则粒度是否过粗
- `USER.md` 兼容边界如何定义最小闭环

#### 10.13.14 Feasibility

整体可行性：`高`

原因：

- 数据层已有成熟 schema 扩展模式
- runtime 读取点集中
- durable extraction 已经输出结构化候选
- P0 可独立落地，不必等待 P1/P2

#### 10.13.15 Rough Workload

P0 整体工作量估计：`M`

拆分估计：

- Step 1：`S-M`
- Step 2：`M`
- Step 3：`M`
- Step 4：`S-M`
- Step 5：`S`

适合拆成 `4-6` 个独立 PR 或 issue，而不是一把梭。

#### 10.13.16 Closure Boundary

P0 完成即视为完成，不要求本期继续扩展到：

- 多用户命名空间
- 人工审核守门
- Dream 后台 consolidation
- 全量项目语义层结构化

P0 的完成标准是：

- 用户画像有 canonical profile state
- durable extraction 可以有限更新画像
- runtime 画像读取优先走 profile state
- 冲突与历史有最小闭环
- 旧 `USER.md` 路径仍可兼容

#### 10.13.17 推荐下一步

P0 建议先从以下顺序开工：

1. 先出 `profile-state-types.ts` 与 path 约定
2. 再出 `MemoryStore` 新表与最小 CRUD
3. 再落 merge 引擎
4. 然后接 durable extraction
5. 最后切 runtime 读路径并补观测接口

原因：

- 这是最小可回滚路径
- 每一步都能独立验证
- 出现问题时，可以停在任意一步而不把旧系统拖垮

## 11. 后续计划

下一步建议优先做 `P0 Step 1：profile-state-types + 表结构设计稿`，原因如下：

- 当前最大缺口不是检索底座，而是画像真值层缺失
- 只要 profile state 仍不存在，后续 Dream、评估、共享画像都会缺少稳定落点
- 先把 path/value/event model 设计稳，后续 `MemoryStore / merge / extraction / runtime` 才不会反复返工

当前还缺的关键闭环：

- 结构化 profile state schema
- profile patch 写入协议
- conflict/history 的最小数据模型
- `USER.md` 与新 schema 的兼容策略
