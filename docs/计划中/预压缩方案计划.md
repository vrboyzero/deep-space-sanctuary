# 预压缩方案计划

评估日期：2026-07-07

## 核心判断

这个想法方向是对的，尤其适合“长文档、OCR、图片理解摘要、网页、日志、代码片段”这类高 token 输入。但不建议做成“所有输入统一按百分比压缩后再给主 Agent”。更稳的做法是：**预压缩作为可选的输入预算层，只压缩高成本附件/长文本，并保留原文可回取引用**。

## 预期收益

1. 能降低主模型 prompt token，特别是附件理解结果、长文档、历史上下文。
2. 可以让昂贵模型专注推理，而不是消耗大量 token 读原始材料。
3. 对 Star Sanctuary 现有架构契合，因为项目里已经有附件理解、上下文压缩、memory / tool result 压缩等机制，可以扩展成“发送前预压缩”。

## 主要风险

1. **信息丢失**：用户问细节、数字、代码、表格、图片局部内容时，便宜模型可能删掉关键点。
2. **响应变慢**：每次多一次模型调用，会增加首 token 延迟。
3. **百分比不等于成本**：压缩百分比对用户直观，但 token 不等于字符，中文、英文、代码、JSON、Markdown 表格差异很大。
4. **图片理解质量下降**：如果图片原本会直接发给主模型做视觉理解，先用便宜模型转文字可能降低视觉细节能力；如果图片已经被系统转成图片摘要，那压缩摘要才比较合理。

## 推荐方案

PLAN

Goal  
在不明显损害回答质量的前提下，降低长输入和附件理解结果进入主 Agent 前的 token 成本。

Constraints  
预压缩不能覆盖原始信息；必须可关闭；失败时不能阻断对话；需要避免短消息也额外增加延迟；需要能解释“哪些内容被压缩了”。

Steps
1. 增加预压缩设置：开关、触发阈值、目标压缩比例、压缩模型配置。
2. 在附件理解完成之后、主 Agent run 之前执行预压缩。
3. 只对超过阈值的长文本块执行，不压缩短用户问题。
4. 压缩输出必须带结构：摘要、关键事实、数字/表格/代码保留、遗漏风险、原文引用 id。
5. 原始内容存入 conversation attachment / generated artifact / memory reference，可由主 Agent 需要时回取。
6. UI 展示“已预压缩：原字符数 -> 压缩字符数，模型，耗时”。

Validation  
对长文档问答、图片摘要问答、代码片段问答做回归：比较开启/关闭预压缩后的答案正确率、token 成本、首响应延迟。

## 候选方案对比

| 方案 | 描述 | 优点 | 缺点 | 推荐度 |
| --- | --- | --- | --- | --- |
| A. 全量统一预压缩 | 每次用户输入 + 附件摘要整体压缩到百分比 | 实现简单，成本下降明显 | 最容易丢关键意图；短消息也变慢；主 Agent 看到的是二手信息 | 不推荐 |
| B. 分块预压缩 + 原文回取 | 只压缩长附件/长文本块，保留原文引用 | 成本、质量、可追溯性平衡最好 | 实现稍复杂，需要引用和回取机制 | 推荐 |
| C. 只在 token 预算紧张时压缩 | 正常不压缩，超过模型上下文或预算阈值才压缩 | 最保守，质量损失低 | 日常成本节省不如 B | 可作为初版 |

推荐采用 **B. 分块预压缩 + 原文回取**，并把 **C. 只在 token 预算紧张时压缩** 作为默认策略的保护条件：开启预压缩后，只有超过阈值才压缩；如果已经接近上下文预算，则强制压缩。

## 设置项建议

### 1. 预压缩开关

合理，但建议不要只有简单开关，而是分成：

- `关闭`
- `仅附件/长文本`
- `所有长输入`

不建议默认压缩用户短问题，因为用户问题本身常常包含精确意图。

### 2. 压缩百分比

可以保留，但最好命名为“目标保留比例”或“目标压缩后长度比例”。

例如 50% 表示“压缩到原字符数约 50%”。但内部最好仍然估算 token，避免中文、英文、代码差异导致成本不可控。

### 3. 触发字数

合理，但要修正“汉字字符数”的概念。

在 JavaScript 字符串长度里，一个常见汉字通常是 1 个 UTF-16 code unit，不是 2 个字符。所谓“1 个汉字是 2 个字符”更接近字节层面的 UTF-16/某些编码概念，不适合直接作为前端/Node 的字符统计规则。

建议 UI 直接说“字符数”，例如：

- 默认触发阈值：`4000` 字符
- 轻量用户可调：`1000 / 4000 / 10000`
- 高级设置再允许自定义

## 执行时机

最佳时机：

```text
用户发送消息
-> 附件解析 / 图片理解 / OCR
-> 生成本轮输入包
-> 判断是否超过阈值
-> 预压缩
-> 主 Agent run
```

不要在附件解析前压缩，因为图片、PDF、文档还没变成可压缩文本。也不要在主 Agent 内部第一轮再压缩，因为那时昂贵模型已经吃到上下文了。

## 压缩提示词要求

预压缩模型不能只“总结”。它应该按保真压缩来做。

必须保留：

1. 用户明确问题和任务目标。
2. 数字、日期、文件名、路径、错误信息。
3. 表格列名、代码标识符、关键字段名。
4. 图片摘要中的对象、位置关系、文字 OCR、异常细节。
5. 不确定或被省略的信息。
6. `sourceRefs`，让主 Agent 知道可回取原文。

建议压缩输出结构：

```json
{
  "summary": "压缩后的主要内容",
  "keyFacts": ["必须保留的事实、数字、结论"],
  "preservedDetails": ["路径、代码符号、表格字段、OCR 文本等"],
  "omissionRisks": ["可能被压缩掉但后续可能需要回看的内容"],
  "sourceRefs": ["attachment:xxx", "message:xxx"]
}
```

## 与 Star Sanctuary 现有架构的接入点

代码调研后确认可接在以下链路附近：

1. `packages/belldandy-core/src/attachment-understanding-runner.ts`
   - 附件落盘、图片/视频自动识别摘要注入、音频转写缓存复用。
   - 适合在附件理解完成后输出待压缩文本块。
   - 当前已经存在附件文本压缩：`preparePromptWithAttachments()` 会对超过 `1200` 字符的 `attachment_text` 调用 `createCompressionPipeline()`，并同步回写 `promptText` 与 `promptDeltas`。

2. `packages/belldandy-core/src/query-runtime-message-send.ts`
   - `message.send` 主执行链。
   - 适合在构造主 Agent 输入前触发预压缩。
   - 当前链路是：读取历史 -> 持久化原始用户消息 -> 附件理解/附件 prompt 生成 -> 注册 run -> `runAgentInBackground()`。
   - `buildMessageSendAgentRunInput()` 会把 `preparedPrompt.promptText` 作为 `runInput.text`，把原始 `userText` 保留在 `runInput.userInput`，并在存在图片/视频等 `contentParts` 时构造结构化 `runInput.content`。

3. `packages/belldandy-agent/src/tool-agent.ts`
   - 已有上下文压缩、token budget、prompt snapshot、工具结果压缩等能力。
   - 不建议第一版把“用户输入预压缩”塞进这里启动，因为进入这里时主模型 messages 已经开始组装；但可以复用统一压缩管线、token 估算与压缩观测思路。
   - 当前工具结果压缩已经在 ReAct 循环内执行：`compressToolMessagesInPlace()` 先压缩旧 tool message，再走 `microcompactMessages()` 和 in-loop compaction。

4. `apps/web/public/app/features/settings.js` / `settings-runtime.js`
   - 适合增加开关、比例、阈值、压缩模型配置。
   - 当前 WebChat 已经绑定 compaction 与 `BELLDANDY_COMPRESSION_REFERENCE_STORE` 设置，新增预压缩设置可以沿用 `config.read` / `config.update`。

5. `apps/web/public/app/features/chat-ui.js` 或 observability 面板
   - 适合展示“本轮已预压缩”的可见状态。

## 代码级调研结论（2026-07-07）

### 1. `message.send` 时机链路

当前 `message.send` 的关键链路位于 `packages/belldandy-core/src/query-runtime-message-send.ts`：

```text
validate request / resolve agent + model
-> tool password approval sanitizes userText
-> getConversationHistoryCompacted(conversationId)
-> conversationStore.addMessage(conversationId, "user", userText)
-> preparePromptWithAttachments(...)
-> detectChatCommanderTrigger(userText)
-> runAgentInBackground(...)
-> buildMessageSendAgentRunInput(...)
-> runAgentWithLifecycle(...)
```

关键影响：

1. **原始用户消息先持久化，附件 prompt 后生成**。预压缩如果只改变 `preparedPrompt.promptText`，不会改写 conversation history。
2. **Agent 同时收到两份语义入口**：`runInput.text = input.promptText`，`runInput.userInput = input.userText`。因此设计时要明确主模型看的文本是压缩版，但审计/原始用户意图仍可从 `userInput` 和 conversation history 回看。
3. **Chat Commander 和工具密码确认应继续使用原始/脱敏后的 `userText`**，不能基于压缩文本判断，否则触发词、密码确认语义可能被压缩模型改写。
4. **最佳插入点不是发送前最前面，而是在 `preparePromptWithAttachments()` 之后、`runAgentInBackground()` 之前**。这样附件文本、OCR、音频转写、图片/视频理解摘要都已经完成，且还没进入主 Agent 模型调用。

### 2. 附件与多模态链路

`preparePromptWithAttachments()` 会把附件分成几类处理：

1. 图片：可能注入 raw `image_url` / data URL `contentPart`，也可能生成图片理解摘要、OCR、标签、关键区域等文本 prompt delta。
2. 视频：可能注入 raw video `contentPart`，也可能生成视频理解摘要。
3. 音频：走 STT 转写，转写文本加入 prompt。
4. 文本附件：按 `AttachmentPromptLimits` 截断后加入 prompt。
5. 其他文件：只注入 workspace path 提示。

关键影响：

1. **文本预压缩不能减少 raw 图片/视频输入成本**。只要 `contentParts` 仍包含图片/视频，主模型仍可能为多模态输入付费。
2. 第一版不应默认移除 raw multimodal `contentParts`。这会改变视觉理解质量，属于更高风险的“成本优先模式”。
3. 当前已有附件文本压缩，但它是硬编码阈值 `1200`、本地规则压缩、无 UI 设置、默认不启用附件引用回取。新方案应优先“治理和泛化现有机制”，不是从零新建一条孤立链路。

### 3. 现有压缩机制

当前至少有四类压缩/预算保护机制：

| 机制 | 位置 | 触发时机 | 类型 | 作用 |
| --- | --- | --- | --- | --- |
| 附件文本压缩 | `attachment-understanding-runner.ts` | 附件 prompt 组装后 | 本地规则压缩 | 压缩长附件文本进入本轮 prompt |
| 工具结果压缩 | `tool-agent.ts` | ReAct 循环内、microcompact 前 | 本地规则压缩 + 可选 reference store | 压缩旧 tool result |
| microcompact | `tool-agent.ts` / `microcompact.ts` | ReAct 循环内 | 消息级压缩/清理 | 收缩陈旧工具消息 |
| compaction / session memory | `conversation.ts` / `compaction.ts` | 读取历史、循环内、digest 刷新 | LLM 摘要 + fallback | 压缩会话历史和长期继续上下文 |
| budget protect | `tool-agent.ts` / `budget-protect.ts` | 主模型请求前 token 预检 | 历史压缩/删除 | 保护 memory/capability，避免超上下文 |

统一压缩管线位于 `packages/belldandy-agent/src/context-compression/`：

1. `createCompressionPipeline()` 默认包含 JSON、log、search result、code snippet、plain text 压缩器。
2. 当前压缩器是结构保留/抽取式规则压缩，不调用便宜模型。
3. `CompressionPolicy` 支持 `enabled`、`allowLossy`、`allowReferenceStore`、`minSavingsRatioToApply` 和 `sourceOverrides`。
4. `CompressionReferenceStore` 已存在，但默认是内存 store；`gateway-main.ts` 默认让 tool_result 可使用 reference store，`attachment_text` 明确 `allowReferenceStore: false`。
5. 当前没有“按目标百分比压到指定字符数”的能力。压缩是否应用由压缩器收益和 `minSavingsRatioToApply` 决定。

### 4. 记忆影响评估

记忆链路非常关键，调研结论是：**不要把预压缩结果写回持久化用户消息**。

证据：

1. `ConversationStore.addMessage()` 只保存 `role/content/timestamp/clientContext` 等原始消息字段。
2. `refreshConversationDigestAndBroadcast()` 调用 `ConversationStore.refreshSessionDigest()`，后者基于 `buildSessionDigestHistoryView()` 读取持久化 conversation messages。
3. durable extraction 在 `DurableExtractionRuntime` 中通过 `conversationStore.getCanonicalExtractionView(conversationId)` 获取 canonical messages，再在 `MemoryManager.extractMemoriesFromConversation()` 中拼成文本，截断最近 `8000` 字符后调用记忆提取模型。
4. 因此只要预压缩只作用于本轮 `runInput.text/content`，session digest 和 durable memory 仍以原始 conversation 为准。

风险点：

1. 附件理解摘要目前主要作为本轮 prompt delta / promptText 进入 Agent，不等同于普通 conversation user message。也就是说，附件全文/摘要是否进入长期记忆，不能只靠预压缩设计保证。
2. 如果未来把附件摘要也写入 conversation history，需要区分“用户原始消息”和“系统生成附件理解结果”，否则 durable extraction 可能把临时 OCR/视频摘要当成长期事实。
3. reference store 目前默认内存级，不能作为长期记忆依据。若需要跨 run 回取原文，应落盘到 attachment artifact 或 prompt snapshot sidecar，而不是只依赖内存 reference。

推荐原则：

1. 原始 `userText` 永远先保存。
2. 预压缩只修改 runtime prompt，不改写 conversation message。
3. 压缩元数据写入 `promptDeltas` / `attachmentStats` / prompt snapshot，方便审计。
4. durable memory 不直接消费压缩摘要，除非后续专门设计“附件理解结果进入记忆”的受控通道。

### 5. 工具调用影响评估

如果预压缩只作用于本轮初始输入，对工具调用的直接影响较小，但有三个间接影响：

1. 主 Agent 可能因为摘要缺细节而更频繁调用文件/附件回取工具，工具调用次数可能上升。
2. 工具结果已经有压缩、microcompact、budget protect，不应再对 tool result 做同一套“发送前预压缩”，否则会重复压缩并降低可诊断性。
3. 如果压缩摘要删除了路径、文件名、错误码、表格列名等工具定位线索，会降低 Agent 正确调用工具的能力。

因此预压缩提示词必须偏“保真压缩”，不是普通摘要；对代码、日志、JSON、搜索结果优先复用现有结构化压缩器。

### 6. prompt snapshot 与可观测性影响

Agent 的 `onPromptSnapshot` 会保存实际发给模型的 messages 和 `promptDeltas`。`mergePromptSnapshotInputMeta()` 会删除 `promptDeltas` 本体，但 deltas 会作为 snapshot 顶层字段保存。

方案要求：

1. 被预压缩的文本必须在 `promptDeltas` 中标记：
   - `compressed: true`
   - `compressionStrategy`
   - `originalChars`
   - `compressedChars`
   - `sourceRef` / `referenceId`
   - `compressionMode: "preflight"`
2. `runInput.meta` 应补充 `preflightCompression` 汇总：
   - appliedCount
   - failedCount
   - totalOriginalChars
   - totalCompressedChars
   - durationMs
   - model / strategy
3. WebChat token observability 已经能展示 usage compression payload，预压缩也应复用类似结构，而不是只写日志。

### 7. 响应速度评估

当前本地规则压缩几乎不增加明显网络延迟；便宜模型预压缩会增加一次额外模型请求。

结论：

1. 对短消息和普通问答，预压缩应默认不触发。
2. 对长附件/长文档，额外延迟可接受，但必须 fail-open，并设置独立 timeout。
3. 如果预压缩模型与主模型共用同一 provider/API key，网络拥塞或限流会同时影响两者，应允许配置独立 route/baseUrl/apiKey。
4. 如果主模型支持 prompt cache，过度改写前缀可能降低 cache 命中。预压缩应该尽量只改用户消息尾部/附件块，不改 stable system prefix。

## 优化后的方案调整

基于代码调研，方案从“新增一次便宜模型全文预压缩”调整为四层：

### Phase 0：治理现有附件压缩

先把现有 `attachment_text` 压缩从硬编码能力变成可配置能力：

1. 增加后端配置：
   - `BELLDANDY_PREFLIGHT_COMPRESSION_ENABLED`
   - `BELLDANDY_PREFLIGHT_COMPRESSION_MODE=off|attachments|long_input|all_long_blocks`
   - `BELLDANDY_PREFLIGHT_COMPRESSION_THRESHOLD_CHARS`
   - `BELLDANDY_PREFLIGHT_COMPRESSION_TARGET_RATIO`
   - `BELLDANDY_PREFLIGHT_COMPRESSION_TIMEOUT_MS`
2. 现有附件压缩阈值 `1200` 改为读取策略，默认仍可保持保守值。
3. 给附件压缩启用可选 reference store 或 artifact sidecar。
4. 把压缩结果汇总透传到 prompt snapshot / usage observability。

### Phase 1：运行时 prompt 分块预压缩

在 `preparePromptWithAttachments()` 之后、`runAgentInBackground()` 之前增加 `preparePreflightCompressedPrompt()`：

```text
input: userText + preparedPrompt + settings + conversationId/runId
output: promptText/contentParts/promptDeltas/meta compression summary
```

处理规则：

1. 用户短问题不压缩。
2. 用户长文本可以作为单独 block 压缩，但必须保留原始 `userText` 到 `runInput.userInput` 和 conversation history。
3. 附件文本、OCR、音频转写、图片/视频理解摘要按 block 压缩。
4. raw `contentParts` 默认不压缩、不删除。
5. 压缩失败直接回退原文。

### Phase 2：原文回取闭环

现有 `CompressionReferenceStore` 是好起点，但第一版要注意生命周期：

1. 本轮内回取：可用内存 reference store。
2. 跨 run 回取：应使用 attachment artifact / prompt snapshot sidecar / conversation artifact，而不是只用内存 store。
3. 回取工具应受权限和路径约束，避免让模型任意读取不相关原文。

### Phase 3：可选便宜模型压缩

便宜模型压缩不应作为第一版唯一实现，而应作为压缩器策略之一：

1. 默认优先规则压缩：快、稳定、低风险。
2. 当内容是自然语言长文档、OCR、图片理解摘要时，可选 LLM abstractive compression。
3. 对代码、JSON、日志、表格，优先结构化/抽取式压缩，不优先使用便宜模型自由摘要。
4. LLM 压缩必须输出结构化 JSON，并进行 schema 校验；失败则回退规则压缩或原文。

## 五项优化综合实施计划

本节把“附件压缩配置化、附件原文 sidecar 回取、附件任务感知压缩、工具结果 adaptive keep、工具结果持久 reference”纳入同一条预压缩演进路线。核心原则是：**先让现有压缩可控、可解释、可回取，再逐步提升压缩智能度**。

### 1. 附件压缩配置化

目标：把当前 `attachment-understanding-runner.ts` 中硬编码的 `ATTACHMENT_COMPRESS_THRESHOLD = 1200` 改成可配置策略，并统一到 Preflight Compression 概念下。

建议配置项：

| 配置项 | 默认值 | 作用 |
| --- | --- | --- |
| `BELLDANDY_PREFLIGHT_COMPRESSION_ENABLED` | `false` 或 `true` 需产品取舍 | 总开关 |
| `BELLDANDY_PREFLIGHT_COMPRESSION_MODE` | `attachments` | `off / attachments / long_input / all_long_blocks` |
| `BELLDANDY_PREFLIGHT_ATTACHMENT_THRESHOLD_CHARS` | `1200` 或 `4000` | 附件文本触发阈值 |
| `BELLDANDY_PREFLIGHT_TARGET_RATIO` | `0.5` | 目标保留比例，仅作为策略提示，不强制保证 |
| `BELLDANDY_PREFLIGHT_MIN_SAVINGS_RATIO` | `0.15` | 压缩收益低于该值则回退原文 |
| `BELLDANDY_PREFLIGHT_TIMEOUT_MS` | `3000` | 预压缩最大耗时，超时 fail-open |
| `BELLDANDY_PREFLIGHT_ATTACHMENT_REFERENCE` | `sidecar` | `none / memory / sidecar` |

实现建议：

1. 新增 `packages/belldandy-core/src/preflight-compression-config.ts`，负责读取 env、归一化数值和模式。
2. `preparePromptWithAttachments()` 接收 `preflightCompressionPolicy`，不再直接使用硬编码阈值。
3. `gateway-main.ts` 组装 policy，传入 `message.send` 运行时依赖。
4. `config-channel.ts` 将新增配置加入安全更新白名单；是否热更新由实现复杂度决定，第一版可以保存后提示重启。
5. WebChat settings 可放在“模型/高级上下文”区域，初版后端配置先行，UI 可作为第二步。

风险等级：低到中。主要风险是配置项过多导致误配；需要用保守默认值和清晰文案降低风险。

可行性：高。现有附件压缩入口已经集中，只需要把阈值、开关和 policy 从硬编码变为参数。

工作量：小到中，约 1-2 个后端文件 + 配置测试；如果同步 WebChat UI，增加 2-4 个前端文件/测试。

闭合边界：

1. 配置能控制附件文本压缩是否启用、阈值和收益门槛。
2. 关闭后附件 prompt 保持原样。
3. 开启后仍保持 fail-open。
4. prompt snapshot 和 usage meta 能看到是否压缩。

预期效果：先解决“不可控”和“不可解释”的问题，为后续任务感知和 sidecar 回取打基础。

### 2. 附件原文 sidecar 回取

目标：压缩附件文本时，不只在内存里保存原文，而是给每个被压缩 block 写入可回取 sidecar，避免主 Agent 只能依赖二手摘要。

建议数据结构：

```ts
type PreflightCompressionSidecar = {
  version: 1;
  conversationId: string;
  runId?: string;
  sourceRef: string;
  sourceKind: "attachment_text" | "attachment_understanding" | "audio_transcript" | "ocr_text";
  sourceName?: string;
  fingerprint?: string;
  originalTextPath: string;
  compressedText: string;
  originalChars: number;
  compressedChars: number;
  strategy: string;
  createdAt: number;
};
```

建议落盘位置：

```text
<stateDir>/storage/preflight-compression/<conversationId>/<runId>/<sourceRef>.json
<stateDir>/storage/preflight-compression/<conversationId>/<runId>/<sourceRef>.txt
```

实现建议：

1. 新增 `preflight-compression-sidecar.ts`，提供 `writePreflightSidecar()`、`readPreflightSidecar()`、`listPreflightSidecars()`。
2. `preparePromptWithAttachments()` 在压缩应用前先写原文 sidecar，成功后把 `sourceRef` 写入 `promptDelta.metadata`。
3. 新增只读回取 RPC 或工具能力，例如 `preflight.compression.retrieve` / `attachment_source.retrieve`，输入 `conversationId + runId + sourceRef`。
4. 回取路径必须限制在 `stateDir/storage/preflight-compression` 下，不能接受任意路径。
5. sidecar 元数据可进入 prompt snapshot，但原文正文不应重复写入 prompt snapshot，避免再次膨胀。

风险等级：中。主要风险是 sidecar 生命周期、权限边界和磁盘增长。

可行性：中高。附件已经落盘，新增 sidecar 与现有 storage 模式契合；需要补清理策略。

工作量：中，约 2-4 个后端文件 + RPC/工具测试 + 安全路径测试。

闭合边界：

1. 被压缩附件 block 有稳定 `sourceRef`。
2. 主 Agent 或用户能通过受控接口回取原文。
3. sidecar 不泄漏到普通 prompt，也不绕过 workspace 权限。
4. 压缩失败时不产生误导性 sidecar 元数据。

预期效果：把附件压缩的信息丢失风险从“不可恢复”降为“可按需回取”。

### 3. 附件任务感知压缩

目标：根据用户当前任务调整压缩强度，而不是只按字符数和固定规则压缩。

任务意图分类建议：

| 意图 | 信号 | 压缩策略 |
| --- | --- | --- |
| 摘要/概括 | 总结、提炼、概述、overview | 可以积极压缩 |
| 精确核对 | 逐字、完整、精确、核对、原文、表格、数字 | 降低压缩强度或跳过 |
| 代码/错误排查 | 报错、堆栈、代码、函数、路径、行号 | 结构保留优先，保留错误上下文 |
| 图片/OCR 细节 | 图片文字、位置、截图、票据、界面 | 保留 OCR、坐标/区域、对象关系 |
| 未明确 | 无明显信号 | 保守压缩，只处理超长 block |

实现建议：

1. 新增轻量 `classifyPreflightCompressionIntent(userText, attachments)`，第一版使用规则分类，不调用模型。
2. `CompressionRequest.metadata` 增加 `taskIntent`、`precisionRequired`、`sourceRef`。
3. 对 `precisionRequired=true` 的附件 block：
   - 提高触发阈值；
   - 提高目标保留比例；
   - 对表格/代码/日志改用结构保留；
   - 必须写 sidecar 后才允许压缩。
4. 对 summary intent 可以允许更强抽取式压缩，后续再接 LLM 压缩器。

风险等级：中。规则分类可能误判；必须保证误判时偏保守。

可行性：高。第一版规则分类即可落地，不依赖模型。

工作量：中，约 1 个分类模块 + 附件压缩策略改造 + 单元测试。

闭合边界：

1. 用户要求精确/完整时，附件压缩不会激进删细节。
2. 用户要求总结时，长附件能更积极压缩。
3. 分类结果进入压缩元数据，便于 prompt snapshot 审计。

预期效果：减少“用户明明要细节，系统却先摘要掉”的核心质量风险。

### 4. 工具结果 adaptive keep

目标：把当前固定“保留最近 4 条 tool message 不压缩”改为按工具类型、token 预算和当前任务引用关系自适应保留。

建议策略：

1. 保留最近关键工具结果：
   - 最近一轮失败的 `run_command` / test output；
   - 最近打开/读取的文件内容；
   - 最近被 assistant 明确引用的路径、行号、错误码。
2. 对低价值旧结果更积极压缩：
   - 大量搜索结果；
   - 重复日志；
   - 大 JSON 响应；
   - 已被后续摘要覆盖的工具结果。
3. 从固定 `keepRecentToolMessages` 改为：
   - `minRecentToolMessages`
   - `maxRecentToolMessages`
   - `recentToolTokenBudget`
   - `criticalToolNames`

实现建议：

1. 新增 `selectToolMessagesForCompression(messages, context)`，输出每条 tool message 的 `keep/compress/skip` 决策和 reason。
2. 在 `compressToolMessagesInPlace()` 中替换固定 `compactUntil` 逻辑。
3. 复用已有 `toolCallNameById`，增加 tool result token 估算。
4. 将 adaptive keep 诊断写入 usage meta：
   - keptRecentCount
   - keptCriticalCount
   - compressedCount
   - decisionReasons

风险等级：中。错误压缩关键工具结果会影响当前推理链。

可行性：中。工具结果链路已经集中，但“当前任务引用关系”只能做启发式判断。

工作量：中，约 1-2 个 agent 文件 + 多组 tool-agent 测试。

闭合边界：

1. 默认行为与当前“最近 4 条保留”兼容。
2. 开启 adaptive 后，关键工具结果完整保留，旧低价值结果压缩。
3. usage meta 能解释每条工具结果为什么被保留或压缩。

预期效果：在不破坏当前工具推理链的前提下，比固定 N 条保留更省 token。

### 5. 工具结果持久 reference

目标：工具结果被压缩后，不只依赖内存 `CompressionReferenceStore`，而是可在跨 run / prompt snapshot 检查时回取原始工具输出。

建议数据结构：

```ts
type ToolCompressionReferenceSidecar = {
  version: 1;
  conversationId?: string;
  runId?: string;
  refId: string;
  toolName: string;
  toolCallId?: string;
  originalTextPath: string;
  compressedText: string;
  originalChars: number;
  compressedChars: number;
  strategy: string;
  createdAt: number;
  retention: "conversation" | "prompt_snapshot";
};
```

实现建议：

1. 扩展 `ContextCompressionPipeline` 的 reference store 支持：新增可选 `PersistentCompressionReferenceStore`。
2. 第一版不要替换现有内存 store，可增加包装 store：写内存 + 写 sidecar。
3. `wrapWithMarker()` marker 中保留 `refId`、`retrievable`、`source`、`strategy`。
4. `pruneBeforeSummarize()` 需要识别持久 ref 是否仍可回取，避免把可回取 marker 误标为失效。
5. 新增受控读取接口，按 `conversationId/runId/refId` 回取，不暴露任意文件路径。

风险等级：中到高。工具输出可能包含敏感信息，持久化必须有保留期、脱敏边界和权限控制。

可行性：中。现有 reference store 接口清晰，但从内存扩展到持久化需要安全设计。

工作量：中到大，约 3-5 个后端文件 + 安全/保留期/回取测试。

闭合边界：

1. 被压缩工具结果能跨 run 回取。
2. prompt snapshot 中 marker 与 reference 状态一致。
3. 持久 reference 有保留期和清理策略。
4. 不把敏感工具输出长期无限保存。

预期效果：降低工具结果压缩的不可逆风险，让压缩更适合长任务和跨轮排查。

## 综合阶段安排

推荐分成四个实现阶段，不把五项优化一次性合并上线：

### 阶段 A：附件压缩配置化 + 观测补强

包含：

1. 附件压缩配置化。
2. `preflightCompression` meta 汇总。
3. prompt delta 元数据补齐。
4. 后端配置白名单与测试。

暂不包含：

1. sidecar 回取。
2. LLM 压缩。
3. 工具压缩改造。

风险等级：低。  
工作量：小到中。  
完成标准：关闭配置时行为不变；开启配置时长附件按策略压缩；压缩结果在 run meta / prompt snapshot 可见。

### 阶段 B：附件 sidecar 回取 + 任务感知压缩

包含：

1. 附件原文 sidecar 写入和受控读取。
2. 规则型任务意图分类。
3. 精确任务保守压缩，摘要任务积极压缩。
4. 回取验收测试。

暂不包含：

1. 持久工具 reference。
2. provider-native context editing。
3. 删除 raw multimodal `contentParts`。

风险等级：中。  
工作量：中。  
完成标准：被压缩附件可通过 `sourceRef` 回取；精确/完整类任务不会激进压缩；sidecar 路径受限。

### 阶段 C：工具结果 adaptive keep

包含：

1. 工具结果压缩候选选择器。
2. 按工具类型/token/关键引用保留。
3. usage meta 透出 keep/compress 决策。
4. 保持当前默认策略兼容。

暂不包含：

1. 工具结果持久 reference。
2. 大规模重写 microcompact。

风险等级：中。  
工作量：中。  
完成标准：最近关键工具结果完整保留；旧低价值结果可压缩；现有 tool-agent 压缩测试仍通过。

### 阶段 D：工具结果持久 reference

包含：

1. 持久 reference sidecar store。
2. marker 与持久 reference 状态同步。
3. 受控回取接口。
4. 保留期/清理策略。

暂不包含：

1. 将所有工具输出默认长期保存。
2. 自动把工具原文写入 durable memory。

风险等级：中到高。  
工作量：中到大。  
完成标准：压缩工具结果可跨 run 回取；敏感输出不无限期保留；reference 失效时 marker 可解释。

## 五项优化优先级与取舍

| 优化项 | 推荐优先级 | 主要收益 | 主要风险 | 推荐处理 |
| --- | --- | --- | --- | --- |
| 附件压缩配置化 | P0 | 让现有能力可控、可关闭、可观察 | 配置复杂度 | 先做 |
| 附件原文 sidecar 回取 | P0 | 降低附件压缩信息丢失风险 | 路径权限、磁盘增长 | 紧随配置化 |
| 附件任务感知压缩 | P1 | 避免精确任务被摘要误伤 | 意图误判 | 与 sidecar 同阶段做 |
| 工具结果 adaptive keep | P1 | 比固定最近 4 条更省 token | 压缩关键工具结果 | 单独阶段做 |
| 工具结果持久 reference | P2 | 长任务跨轮可回取工具原文 | 敏感数据持久化 | 最后做，先设计安全边界 |

综合推荐：先把附件压缩做成“可控 + 可回取 + 任务感知”，再优化工具结果保留策略，最后补工具结果持久 reference。这样收益路径最短，且不会先碰敏感数据持久化这个高风险点。

## 推荐第一版实现边界（代码调研后修订）

第一版建议包含：

1. 后端配置和策略解析，不先做复杂 UI 也可以，但 `config-channel` 要允许更新。
2. 将现有附件压缩阈值、开关、收益门槛、reference 模式纳入配置。
3. 增加 `preflightCompression` 汇总元数据，进入 `runInput.meta` 和 prompt snapshot。
4. 附件文本压缩优先支持 sidecar 回取：压缩前保存原文，压缩 prompt 中写入 `sourceRef`。
5. 增加规则型任务感知压缩：精确/完整/代码/表格类任务保守压缩，摘要类任务允许更积极压缩。
6. 对长用户文本和附件文本做分块压缩；短消息不触发。
7. 保留原始 conversation message，不写回压缩版本。
8. 压缩失败 fail-open。
9. 补充单元测试：
   - 短消息不触发；
   - 长附件触发且回写 promptText/promptDeltas；
   - 压缩失败回退；
   - conversation history 仍保存原文；
   - `contentParts` 不被删除。
   - 精确任务下附件压缩降级或跳过；
   - 被压缩附件可通过 `sourceRef` 回取原文。

第一版暂不建议包含：

1. 默认启用便宜模型摘要。
2. 删除 raw 图片/视频输入。
3. 工具结果持久 reference 默认开启。
4. 把附件理解摘要自动写入 durable memory。
5. 对工具结果再加一层预压缩。
6. Provider-native context editing。

工具结果优化的第一批边界：

1. 先做 `adaptive keep`，默认保持当前最近 4 条保留策略兼容。
2. 只增强“哪些旧工具结果可以压缩”的选择逻辑，不重写 microcompact。
3. 持久 reference 作为单独后续阶段，需要先完成敏感数据持久化与清理策略设计。

## 行为验收描述

### 场景 1：短消息不触发预压缩

前置条件：预压缩开启，触发阈值为 4000 字符。  
操作：用户发送 200 字符以内的普通问题，且无附件。  
预期结果：系统直接调用主 Agent，不发生预压缩模型调用。

### 场景 2：长附件摘要触发预压缩

前置条件：预压缩开启，触发阈值为 4000 字符，目标保留比例为 50%。  
操作：用户上传文档，附件理解结果与用户输入合计 10000 字符。  
预期结果：系统先调用预压缩模型，将长文本压缩到约 5000 字符，并把压缩结果传给主 Agent。

### 场景 3：压缩失败不阻断对话

前置条件：预压缩开启，但压缩模型调用失败。  
操作：用户发送超过阈值的长输入。  
预期结果：系统记录预压缩失败，并回退为原始输入调用主 Agent，不中断本轮对话。

### 场景 4：主 Agent 可回取原文

前置条件：长附件内容已被预压缩，原文引用已保存。  
操作：主 Agent 需要核对被压缩掉的细节。  
预期结果：主 Agent 能通过引用读取原始附件理解结果或原文片段，而不是只能依赖二手摘要。

### 场景 5：精确任务触发保守压缩

前置条件：预压缩开启，用户上传长表格或代码文件。  
操作：用户要求“逐字核对”“保留完整表格字段”或“定位具体错误行”。  
预期结果：系统识别为精确任务，提高压缩保留比例或跳过压缩；若仍压缩，必须写入 sidecar 并保留字段名、数字、路径、错误行等关键细节。

### 场景 6：附件 sidecar 受控回取

前置条件：附件文本已被压缩，`promptDelta.metadata.sourceRef` 已生成。  
操作：通过受控回取接口读取该 `sourceRef`。  
预期结果：只能读取对应 conversation/run 下的 sidecar 原文，不能读取任意文件路径；找不到或已过期时返回可诊断错误。

### 场景 7：工具结果 adaptive keep 保留关键结果

前置条件：Agent 已产生多条工具结果，包含最近失败测试输出、搜索结果和旧日志。  
操作：进入下一轮工具调用前触发工具结果压缩。  
预期结果：最近失败测试输出和当前引用路径保持完整，旧搜索结果/旧日志被压缩，usage meta 中说明 keep/compress 决策原因。

### 场景 8：工具结果持久 reference 可回取

前置条件：工具结果压缩启用持久 reference，旧工具输出被压缩成 marker。  
操作：后续 run 通过 `refId` 回取原始工具输出。  
预期结果：系统返回原始输出或明确说明 reference 已过期/失效；marker 中的 retrievable 状态与实际回取能力一致。

## 原始实现边界草案

以下是初评阶段的边界草案；代码调研后的修订版以上文“推荐第一版实现边界（代码调研后修订）”为准。

第一版原始建议包含：

1. 设置项：开关、触发阈值、目标保留比例、压缩模型。
2. 文本块级预压缩：用户长文本、附件理解文本、OCR 文本。
3. 原文引用保存：至少能在本轮 conversation 内回取。
4. 失败回退：预压缩失败后使用原始输入。
5. 基础观测：记录原字符数、压缩字符数、耗时、模型、是否失败。

第一版不建议包含：

1. 直接压缩 raw 图片视觉输入。
2. 对所有短消息强制预压缩。
3. 用预压缩替代已有长期 memory / context compression。
4. 复杂的多级摘要树。
5. 自动删除原始附件理解结果。

## 最终建议

这个功能值得做，但不要做成“简单全文百分比摘要”。建议定义成 **Preflight Input Compression**：

1. 默认关闭或“仅长附件开启”。
2. 超阈值才触发。
3. 分块压缩，不压缩用户短问题。
4. 原文必须可回取。
5. 压缩失败时回退原文。
6. UI 显示压缩状态和节省估算。
7. 第一版先支持文本/附件理解摘要，图片 raw multimodal 不强行替换。

这样能拿到大部分 token 成本收益，同时把信息丢失和响应变慢控制在可接受范围内。

## 当前剩余边界与遗漏计划检查（阶段 A-D 后）

阶段 A-D 已完成后，原代码调研阶段的“未运行自动化测试、未设计 sidecar / reference 格式、未明确持久 reference 权限边界、adaptive keep 未回归验证”等风险已经闭环。当前仍需要明确保留的计划内容如下：

1. **便宜模型预压缩仍未进入实现范围**：还没有接入独立低价模型做 LLM 压缩，也没有做真实 provider 价格、延迟、质量的 A/B 测算。该项应继续作为后续实验，不应默认上线。
2. **用户长文本预压缩仍未实现**：当前主要闭环是附件文本和工具结果；用户直接输入的超长正文、画布快照、手写粘贴内容等还没有统一进入 `PreflightCompressionPolicy`。
3. **WebChat 设置与诊断入口仍缺少完整 UI**：配置通道已支持后端配置读写，但 WebChat 还没有为新增预压缩配置、持久 reference TTL / max entries、sidecar / reference 回取状态提供完整设置与诊断视图。
4. **sidecar / persistent reference 清理策略仍可增强**：工具 reference 已有 TTL 和最大条目控制，附件 sidecar 仍缺少统一清理任务；后续应避免长期运行后磁盘增长不可控。
5. **prompt snapshot / observability 仍需前端展示补强**：压缩 metadata 和 `usage.compression.selection` 已进入链路，但还没有在 doctor、prompt snapshot 查看器或 token usage 面板中完整解释每条保留/压缩/回取状态。
6. **`listPreflightSidecars()` 仅停留在早期设计**：实际阶段 B 只实现了受控写入与单条读取；如后续要做 UI 列表、诊断或清理，需要补受限列表接口。
7. **provider-native context editing 暂不纳入**：当前方案仍基于本地压缩、sidecar 和 reference store；供应商原生上下文编辑能力需要单独评估兼容性和锁定风险。
8. **超 3000 行大文件约束仍需持续遵守**：`apps/web/public/app.js`、`gateway-main.ts`、`tool-agent.ts` 都已超过 3000 行；后续 WebChat、Gateway、Agent 接入应优先新建局部模块，只在大文件中做最小接线。

## 后续增强建议（阶段 A-D 后）

下一步建议先补“可观测与清理”闭环，再考虑便宜模型压缩实验：

1. 先做 WebChat / doctor 诊断入口，展示附件压缩、sidecar、工具 adaptive keep、persistent reference 的实际状态。
2. 补附件 sidecar 与工具 reference 的清理任务，把 TTL、最大条目数、磁盘占用纳入 doctor 输出。
3. 把用户长文本预压缩作为独立阶段接入，先只处理明显超阈值的文本块，并复用任务感知与原文回取规则。
4. 设计便宜模型压缩实验开关，只在可测量的 provider 组合上启用，先记录成本、延迟、压缩率、回取率和人工质量样本。
5. 若需要前端列表或诊断，补 `listPreflightSidecars()` 等受限枚举接口，但必须限制 conversation / run / sourceRef 范围，避免任意文件枚举。
6. 后续实现继续按大文件约束拆分：WebChat 逻辑放入 `apps/web/public/app/features/`，Gateway / Agent 逻辑放入新模块，大文件只保留注册、透传和调用。

为什么先做它：阶段 A-D 已经把核心安全边界和可回取能力打通，当前最大缺口不再是“能不能压缩”，而是“能不能让用户看清楚压缩发生了什么、原文在哪里、何时会清理、是否真的省钱”。

当前还缺的关键闭环是：前端可观测、清理治理、用户长文本入口、便宜模型成本质量评估，以及受限列表/诊断接口。
