# 上下文与记忆管理变量分析

更新时间：2026-06-19

## 先说结论

当前这套环境变量整体是可用的，核心链路已经真实生效，不是“写了但没接线”的状态。

但从“面向 1M 上下文模型”的角度看，当前配置存在两个明显特点：

- 长上下文预算已经放开得比较大：`BELLDANDY_MAX_INPUT_TOKENS=850000`
- 记忆 / 注入 / transcript / compaction 仍然偏“保守 + 防膨胀”设计，并没有因为 1M 窗口而完全放任扩张

这本身不是坏事。当前主要风险不是“上下文不够大”，而是：

- 工具结果 transcript 写回偏大，容易让会话逐轮膨胀
- compaction 触发得偏早，长上下文优势未完全吃满
- `session digest` 当前没有启用限流，默认是无限制刷新预算
- 有少量变量存在“配置写着，但由于上层开关关闭，实际不生效”的情况

本次结论可以概括为：

1. 现有上下文 / 记忆相关变量大部分都有效，且当前运行日志已经证明多项功能已启用。
2. 当前没有“硬冲突导致功能互相打架”的严重问题。
3. 存在几组“语义重叠但并非冲突”的配置，需要明确理解它们的优先级与覆盖关系。
4. 如果目标是稳定跑 1M 级别模型，建议把当前配置从“中等保守”调整为“长上下文友好但仍受控”的版本，而不是盲目把所有注入项都调大。

## 当前实现的几个关键事实

### 1. WebChat 主会话的真实主键是 `conversationId`

系统当然能区分“新对话”和“旧对话”，但 WebChat 主链路里最核心的会话标识是 `conversationId`，不是口头描述里常说的 `sessionKey`。

关键依据：

- `packages/belldandy-core/src/query-runtime-message-send.ts`
- `apps/web/public/app.js`

更准确地说：

- 当前轮主对话是按 `conversationId` 持续追加
- 某些内部 hook / task memory / goal session 会复用 `sessionKey` 这个术语
- 不能把二者完全等同成“对用户看到的主会话标识”

### 2. 旧会话并不是“完全不可见”

默认自动注入到 prompt 的上下文，不会包含所有旧会话全文；这一点是对的。

但系统是能读取旧会话内容的，前端甚至已经内置了让 Agent 主动读取会话历史的动作提示：

- `conversation_list`
- `conversation_read`
- `conversation.meta`
- `conversation.timeline.get`

关键依据：

- `apps/web/public/app.js`
- `packages/belldandy-core/src/server-methods/workspace-conversation.ts`

因此更准确的说法应是：

- “旧会话默认不会整段进入当前 prompt”
- 但“旧会话可以被列出、读取、摘要、恢复、导出”

### 3. 记忆类功能受 `BELLDANDY_MEMORY_ENABLED` 总开关控制

当前实现里，以下开关都要先经过 `BELLDANDY_MEMORY_ENABLED`：

- `BELLDANDY_CONTEXT_INJECTION`
- `BELLDANDY_AUTO_RECALL_ENABLED`
- `BELLDANDY_EMBEDDING_ENABLED`
- `BELLDANDY_MEMORY_SUMMARY_ENABLED`
- `BELLDANDY_MEMORY_EVOLUTION_ENABLED`

关键依据：

- `packages/belldandy-core/src/memory-runtime-switches.ts`

所以这类变量虽然分别有自己的值，但它们不是彼此完全独立的孤岛。

### 4. `.env.local` 当前覆盖了 `.env` 中的部分同名值

当前已确认以下值以 `.env.local` 为准：

- `BELLDANDY_MAX_INPUT_TOKENS=850000`
- `BELLDANDY_EMBEDDING_BATCH_SIZE=3`
- `BELLDANDY_TOOL_RESULT_TRANSCRIPT_CHAR_LIMIT=20000`
- `BELLDANDY_COMPACTION_THRESHOLD=85000`
- `BELLDANDY_COMPACTION_MODEL=qwen3.6-flash`

这意味着你不能只看 `.env` 里的注释样例来判断“当前实际运行值”。

## 当前环境中的实际值与生效情况

### A. 记忆总开关与检索相关

当前值：

- `BELLDANDY_MEMORY_ENABLED="true"`
- `BELLDANDY_EMBEDDING_ENABLED="true"`
- `BELLDANDY_EMBEDDING_BATCH_SIZE="3"`

功能：

- `BELLDANDY_MEMORY_ENABLED`：记忆运行时总开关

- `EMBEDDING_BATCH_SIZE` 与 1M 上下文窗口没有直接绑定关系，不需要因为模型上下文大就同步调大

当前评价：

- `3` 是合理值

## 当前有没有真实冲突？

结论：当前没有严重冲突，但有 4 组需要正确理解优先级。

### 1. `.env` 与 `.env.local` 的覆盖

这是覆盖，不是冲突。

表现：

- `.env` 里写了 `EMBEDDING_BATCH_SIZE=2`
- `.env.local` 里写了 `EMBEDDING_BATCH_SIZE=3`

最终生效：

- `3`

同理：

- `TOOL_RESULT_TRANSCRIPT_CHAR_LIMIT` 最终是 `20000`，不是 `.env` 里的 `12000`

### 2. `TASK_DEDUP_GUARD_ENABLED=false` 与 `MODE/POLICY`

这是“上层关闭、下层保留”，不是硬冲突。

表现：

- 你保留了 dedup 的策略值
- 但总开关已关，因此运行时不会注册去重钩子

建议理解为：

- 当前 dedup 实际关闭
- `MODE/POLICY` 只是保留一套将来可恢复的策略模板

### 3. `MAX_INPUT_TOKENS` 很大，但 compaction 仍然较早触发

这也不是冲突，是一种策略选择。

表现：

- 上限 85 万
- compaction 阈值 8.5 万
- 循环中触发比例 0.55

实际效果：

- 你在用长上下文模型
- 但系统并不打算“真正把 prompt 长到非常长再处理”

### 4. `session digest` 存在，但限流空着

这不是冲突，是“功能开启但保护没配置”。

## 面向 1M 模型的完整建议

下面这套建议目标不是“最大化注入”，而是：

- 让 1M 窗口真正有收益
- 仍然防止 prompt 膨胀失控
- 保留良好的恢复、观测和回滚能力

```env
BELLDANDY_PROMPT_SNAPSHOT_HEARTBEAT_MAX_RUNS=5
BELLDANDY_PROMPT_SNAPSHOT_RETENTION_DAYS=7

BELLDANDY_MEMORY_SESSION_DIGEST_MAX_RUNS=12
BELLDANDY_MEMORY_SESSION_DIGEST_WINDOW_MS=3600000
```

## 为什么推荐这样调

### 1. 记忆注入只适度放宽，不建议暴涨

建议：

- `CONTEXT_INJECTION_LIMIT: 5 -> 6`
- `TASK_LIMIT: 3 -> 4`
- `AUTO_RECALL_LIMIT: 3 -> 4`
- `AUTO_RECALL_MIN_SCORE: 0.35 -> 0.38`

原因：

- 1M 模型不怕多几百 token 的记忆摘要
- 但召回质量差的内容一多，问题会从“放不下”变成“噪声高”

### 2. `INCLUDE_SESSION=false` 建议继续保持

原因：

- 这是防重复执行、防“刚做完的步骤再被塞回 prompt”的关键项
- 长上下文模型不是靠重复塞 session 做记忆，而是靠更大 headroom 接住更完整的自然对话

### 3. transcript 上限建议收回到 `12000`

这是我最明确的一条建议。

原因：

- 工具结果 transcript 是最容易造成会话持续膨胀的来源
- 1M 窗口并不意味着应该保留更多原始工具输出垃圾
- 真正重要的工具结果应由 artifact path、recent tool result、timeline、transcript export、prompt snapshot 来承担可回溯性

### 4. `MAX_HISTORY` 建议从 `10` 提到 `16`

原因：

- 1M 模型更适合保留更多“最近原始消息”
- 只保留 10 条会偏依赖 compaction summary，损失局部上下文原貌
- `16` 是一个比较稳的中间值，不会像 `30+` 那样明显拉高每轮 prompt

### 5. compaction 应该后移，而不是关闭

建议：

- `COMPACTION_THRESHOLD: 85000 -> 140000`
- `COMPACTION_KEEP_RECENT: 16 -> 20`
- `COMPACTION_TRIGGER_FRACTION: 0.55 -> 0.72`

原因：

- 你已经有大输入预算，没必要在 5.5 成上限附近就频繁触发循环内压缩
- 但也不建议关掉 compaction，否则最终会退化成更硬的裁剪或更重的长 prompt

### 6. `session digest` 建议加温和限流

建议：

- `BELLDANDY_MEMORY_SESSION_DIGEST_MAX_RUNS=12`
- `BELLDANDY_MEMORY_SESSION_DIGEST_WINDOW_MS=3600000`

原因：

- 这不会影响功能存在
- 只是在高频刷新观测面板 / 高频读会话摘要时防止无意义地重复刷新 digest

### 7. prompt snapshot 建议小幅提高保留量

建议：

- `MAX_RUNS: 48 -> 64`
- `MAX_PERSISTED_RUNS: 20 -> 24`

原因：

- 1M 模型调优时，更需要回看“到底送了什么 prompt”
- prompt snapshot 是调上下文系统时最有价值的取证面之一

## 如果你保持当前配置，不改也会怎样？

当前配置不会坏，系统也不是错配。

但实际表现大概率会是：

- 长上下文模型有更大余量
- 可系统仍然会较早进入 compaction / summary 驱动
- 会话中真正长期保留的原始上下文比例不算高
- transcript 写回偏大，长期来看会增加 compaction 与恢复负担

换句话说，当前更像：

- “用 1M 模型获得稳定性冗余”

而不是：

- “积极利用 1M 模型保留更多原始上下文”

## 本次最终判断

### 当前这些变量的功能现在有没有冲突？

结论：

- 没有严重冲突
- 有少量覆盖关系与上层开关覆盖下层策略的情况
- 当前更大的问题不是冲突，而是“长上下文预算放大了，但 compaction / transcript / history 仍按偏保守策略在运行”

### 当前最值得优先调整的 5 项

按优先级排序，我建议优先看这 5 项：

1. `BELLDANDY_TOOL_RESULT_TRANSCRIPT_CHAR_LIMIT`
2. `BELLDANDY_COMPACTION_THRESHOLD`
3. `BELLDANDY_COMPACTION_TRIGGER_FRACTION`
4. `BELLDANDY_MAX_HISTORY`
5. `BELLDANDY_MEMORY_SESSION_DIGEST_MAX_RUNS` / `BELLDANDY_MEMORY_SESSION_DIGEST_WINDOW_MS`

## 后续计划

如果下一步继续做更深一层的收敛，优先建议做两件事：

1. 先用 prompt snapshot + session digest + conversation timeline 做一次真实长会话取证。
2. 再根据真实会话里“tool result、memory prelude、system prompt、recent messages”分别占多少 token，决定是否继续放大 `MAX_HISTORY` 或进一步后移 compaction。

为什么先做这两步：

- 因为你当前已经不是“功能没开”的阶段
- 当前缺的关键闭环，是“这套 1M 配置在真实会话里到底是谁在吃 token”

在没有这层证据前，继续盲调更多变量，收益会快速下降。
