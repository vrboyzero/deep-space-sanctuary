# 上下文与记忆管理变量分析

更新时间：2026-06-19

## 先说结论

当前这套环境变量整体是可用的，核心链路已经真实生效，不是“写了但没接线”的状态。

但从“面向 1M 上下文模型”的角度看，当前配置存在两个明显特点：

- 长上下文预算已经放开得比较大：`BELLDANDY_MAX_INPUT_TOKENS=850000`
- 记忆 / 注入 / transcript / compaction 仍然偏“保守 + 防膨胀”设计，并没有因为 1M 窗口而完全放任扩张

这本身不是坏事。当前主要风险不是“上下文不够大”，而是：

- 工具结果 transcript 写回偏大，容易让会话逐轮膨胀
- compaction 触发得偏早，长上下文优势未完全吃满
- `session digest` 当前没有启用限流，默认是无限制刷新预算
- 有少量变量存在“配置写着，但由于上层开关关闭，实际不生效”的情况

本次结论可以概括为：

1. 现有上下文 / 记忆相关变量大部分都有效，且当前运行日志已经证明多项功能已启用。
2. 当前没有“硬冲突导致功能互相打架”的严重问题。
3. 存在几组“语义重叠但并非冲突”的配置，需要明确理解它们的优先级与覆盖关系。
4. 如果目标是稳定跑 1M 级别模型，建议把当前配置从“中等保守”调整为“长上下文友好但仍受控”的版本，而不是盲目把所有注入项都调大。

## 当前实现的几个关键事实

### 1. WebChat 主会话的真实主键是 `conversationId`

系统当然能区分“新对话”和“旧对话”，但 WebChat 主链路里最核心的会话标识是 `conversationId`，不是口头描述里常说的 `sessionKey`。

关键依据：

- `packages/belldandy-core/src/query-runtime-message-send.ts`
- `apps/web/public/app.js`

更准确地说：

- 当前轮主对话是按 `conversationId` 持续追加
- 某些内部 hook / task memory / goal session 会复用 `sessionKey` 这个术语
- 不能把二者完全等同成“对用户看到的主会话标识”

### 2. 旧会话并不是“完全不可见”

默认自动注入到 prompt 的上下文，不会包含所有旧会话全文；这一点是对的。

但系统是能读取旧会话内容的，前端甚至已经内置了让 Agent 主动读取会话历史的动作提示：

- `conversation_list`
- `conversation_read`
- `conversation.meta`
- `conversation.timeline.get`

关键依据：

- `apps/web/public/app.js`
- `packages/belldandy-core/src/server-methods/workspace-conversation.ts`

因此更准确的说法应是：

- “旧会话默认不会整段进入当前 prompt”
- 但“旧会话可以被列出、读取、摘要、恢复、导出”

### 3. 记忆类功能受 `BELLDANDY_MEMORY_ENABLED` 总开关控制

当前实现里，以下开关都要先经过 `BELLDANDY_MEMORY_ENABLED`：

- `BELLDANDY_CONTEXT_INJECTION`
- `BELLDANDY_AUTO_RECALL_ENABLED`
- `BELLDANDY_EMBEDDING_ENABLED`
- `BELLDANDY_MEMORY_SUMMARY_ENABLED`
- `BELLDANDY_MEMORY_EVOLUTION_ENABLED`

关键依据：

- `packages/belldandy-core/src/memory-runtime-switches.ts`

所以这类变量虽然分别有自己的值，但它们不是彼此完全独立的孤岛。

### 4. `.env.local` 当前覆盖了 `.env` 中的部分同名值

当前已确认以下值以 `.env.local` 为准：

- `BELLDANDY_MAX_INPUT_TOKENS=850000`
- `BELLDANDY_EMBEDDING_BATCH_SIZE=3`
- `BELLDANDY_TOOL_RESULT_TRANSCRIPT_CHAR_LIMIT=20000`
- `BELLDANDY_COMPACTION_THRESHOLD=85000`
- `BELLDANDY_COMPACTION_MODEL=qwen3.6-flash`

这意味着你不能只看 `.env` 里的注释样例来判断“当前实际运行值”。

## 当前环境中的实际值与生效情况

### A. 记忆总开关与检索相关

当前值：

- `BELLDANDY_MEMORY_ENABLED="true"`
- `BELLDANDY_EMBEDDING_ENABLED="true"`
- `BELLDANDY_EMBEDDING_BATCH_SIZE="3"`

功能：

- `BELLDANDY_MEMORY_ENABLED`：记忆运行时总开关

- `EMBEDDING_BATCH_SIZE` 与 1M 上下文窗口没有直接绑定关系，不需要因为模型上下文大就同步调大

当前评价：

- `3` 是合理值

## 当前有没有真实冲突？

结论：当前没有严重冲突，但有 4 组需要正确理解优先级。

### 1. `.env` 与 `.env.local` 的覆盖

这是覆盖，不是冲突。

表现：

- `.env` 里写了 `EMBEDDING_BATCH_SIZE=2`
- `.env.local` 里写了 `EMBEDDING_BATCH_SIZE=3`

最终生效：

- `3`

同理：

- `TOOL_RESULT_TRANSCRIPT_CHAR_LIMIT` 最终是 `20000`，不是 `.env` 里的 `12000`

### 2. `TASK_DEDUP_GUARD_ENABLED=false` 与 `MODE/POLICY`

这是“上层关闭、下层保留”，不是硬冲突。

表现：

- 你保留了 dedup 的策略值
- 但总开关已关，因此运行时不会注册去重钩子

建议理解为：

- 当前 dedup 实际关闭
- `MODE/POLICY` 只是保留一套将来可恢复的策略模板

### 3. `MAX_INPUT_TOKENS` 很大，但 compaction 仍然较早触发

这也不是冲突，是一种策略选择。

表现：

- 上限 85 万
- compaction 阈值 8.5 万
- 循环中触发比例 0.55

实际效果：

- 你在用长上下文模型
- 但系统并不打算“真正把 prompt 长到非常长再处理”

### 4. `session digest` 存在，但限流空着

这不是冲突，是“功能开启但保护没配置”。

## 面向 1M 模型的完整建议

下面这套建议目标不是“最大化注入”，而是：

- 让 1M 窗口真正有收益
- 仍然防止 prompt 膨胀失控
- 保留良好的恢复、观测和回滚能力

## 为什么推荐这样调

### 1. 记忆注入只适度放宽，不建议暴涨

建议：

- `CONTEXT_INJECTION_LIMIT: 5 -> 6`
- `TASK_LIMIT: 3 -> 4`
- `AUTO_RECALL_LIMIT: 3 -> 4`
- `AUTO_RECALL_MIN_SCORE: 0.35 -> 0.38`

原因：

- 1M 模型不怕多几百 token 的记忆摘要
- 但召回质量差的内容一多，问题会从“放不下”变成“噪声高”

### 2. `INCLUDE_SESSION=false` 建议继续保持

原因：

- 这是防重复执行、防“刚做完的步骤再被塞回 prompt”的关键项
- 长上下文模型不是靠重复塞 session 做记忆，而是靠更大 headroom 接住更完整的自然对话

### 3. transcript 上限建议收回到 `12000`

这是我最明确的一条建议。

原因：

- 工具结果 transcript 是最容易造成会话持续膨胀的来源
- 1M 窗口并不意味着应该保留更多原始工具输出垃圾
- 真正重要的工具结果应由 artifact path、recent tool result、timeline、transcript export、prompt snapshot 来承担可回溯性

### 4. `MAX_HISTORY` 建议从 `10` 提到 `16`

原因：

- 1M 模型更适合保留更多“最近原始消息”
- 只保留 10 条会偏依赖 compaction summary，损失局部上下文原貌
- `16` 是一个比较稳的中间值，不会像 `30+` 那样明显拉高每轮 prompt

### 5. compaction 应该后移，而不是关闭

建议：

- `COMPACTION_THRESHOLD: 85000 -> 140000`
- `COMPACTION_KEEP_RECENT: 16 -> 20`
- `COMPACTION_TRIGGER_FRACTION: 0.55 -> 0.72`

原因：

- 你已经有大输入预算，没必要在 5.5 成上限附近就频繁触发循环内压缩
- 但也不建议关掉 compaction，否则最终会退化成更硬的裁剪或更重的长 prompt

### 6. `session digest` 建议加温和限流

建议：

- `BELLDANDY_MEMORY_SESSION_DIGEST_MAX_RUNS=12`
- `BELLDANDY_MEMORY_SESSION_DIGEST_WINDOW_MS=3600000`

原因：

- 这不会影响功能存在
- 只是在高频刷新观测面板 / 高频读会话摘要时防止无意义地重复刷新 digest

### 7. prompt snapshot 建议小幅提高保留量

建议：

- `MAX_RUNS: 48 -> 64`
- `MAX_PERSISTED_RUNS: 20 -> 24`

原因：

- 1M 模型调优时，更需要回看“到底送了什么 prompt”
- prompt snapshot 是调上下文系统时最有价值的取证面之一

## 如果你保持当前配置，不改也会怎样？

当前配置不会坏，系统也不是错配。

但实际表现大概率会是：

- 长上下文模型有更大余量
- 可系统仍然会较早进入 compaction / summary 驱动

- transcript 写回偏大，长期来看会增加 compaction 与恢复负担

换句话说，当前更像：

- “用 1M 模型获得稳定性冗余”

而不是：

- “积极利用 1M 模型保留更多原始上下文”

### 当前这套 compaction 相关变量的实际生效顺序图（按 2026-06-25 配置）

以下顺序图是按你当前实际配置推导的：

- `BELLDANDY_MAX_INPUT_TOKENS="850000"`
- `BELLDANDY_MAX_HISTORY="20"`
- `BELLDANDY_COMPACTION_KEEP_RECENT="20"`
- `BELLDANDY_COMPACTION_TRIGGER_FRACTION="0.72"`
- `BELLDANDY_MODEL_CONTEXT_WINDOW="1000000"`
- `BELLDANDY_COMPACTION_CONTEXT_WINDOW_FRACTION="0.8"`
- `BELLDANDY_COMPACTION_THRESHOLD="800000"`
- `BELLDANDY_COMPACTION_WARNING_THRESHOLD="700000"`
- `BELLDANDY_COMPACTION_BLOCKING_THRESHOLD` 未显式设置（当前为注释）
- `BELLDANDY_TOOL_LOOP_ITERATION_BUDGET=0`

由此可得：

- 循环内 compaction 检查线：`850000 * 0.72 = 612000`
- 主 compaction 阈值：`1000000 * 0.8 = 800000`
- warning 阈值：固定 `700000`
- blocking 阈值：`max(700001, 800000 * 0.9) = 720000`

实际顺序如下：

```text
消息进入会话
  ↓
ConversationStore 先受 MAX_HISTORY=20 限制
  - 加载时裁剪到最后 20 条
  - 内存中也只保留最后 20 条
  ↓
进入 ToolAgent 主循环
  ↓
统一压缩层先处理旧 tool_result
  - content-aware compression（Phase 1 / Phase 2）
  - 这一步不看 800000
  ↓
microcompact 再处理旧 tool 消息
  - 默认只保留最近若干条 tool 输出原文
  - 这一步也不看 800000
  ↓
循环内 compaction 预检查
  - 若当前总 token > 612000，才尝试进入 in-loop compaction
  - 这里只是“尝试检查”，不是一定压缩
  ↓
semantic compaction 正式判断
  - 若 user/assistant 历史消息 token <= 800000，则不做主压缩
  - 若 user/assistant 历史消息条数 <= KEEP_RECENT=20，也不做主压缩
  - force=true 时跳过“是否超过 800000”这一步
  ↓
进入 rolling / archival summary 构建
  - prompt >= 700000：标记 warning
  - prompt >= 720000：不再调用摘要模型，直接走本地 fallback summary
  ↓
产出压缩后的 Conversation context + recent messages
```

#### 这张图里最关键的实际含义

1. `612000` 不是主压缩阈值，只是“开始尝试检查 compaction”的门槛。
2. `800000` 才是 primary 路由下的主 compaction 阈值。
3. `720000` 不是“抢先阻止主压缩”的阈值，而是“进入 compaction 后，阻止继续调用摘要模型”的预算保护阈值。
4. 你当前 `MAX_HISTORY=20` 且 `COMPACTION_KEEP_RECENT=20`，这会强烈抑制主 compaction 的触发空间。

#### 为什么说 `MAX_HISTORY=20` + `KEEP_RECENT=20` 会强烈抑制主 compaction

因为当前实现里：

- 会话加载时会先被 `MAX_HISTORY` 裁到最后 20 条
- 内存里的历史也只保留最后 20 条
- 而 in-loop compaction 又会先判断：
  - `historyMessages.length <= keepRecent` 就直接返回，不压缩

在你当前配置下：

- `MAX_HISTORY=20`
- `KEEP_RECENT=20`

这意味着：

- 对 user/assistant 主历史来说，经常还没轮到“超过 800000 再压缩”
- 就已经被“只保留最近 20 条消息”这一层给截断了

所以如果你体感是“上下文一直涨不上去”，比起 `force=true`，当前更像真正主因的是：

1. `MAX_HISTORY=20`
2. `KEEP_RECENT=20`
3. 旧 `tool_result` 在进入主 compaction 前就已经先被统一压缩层 + microcompact 处理掉了

### 关于 `force=true`：它会不会导致你看到“上下文一直涨不上去”

先说当前结论：

- 以你现在的实际配置来看，**在线主链路里 `force=true` 当前并没有生效**

原因很简单：

- `force=true` 在 tool loop 里只会在 `nextModelCallIndex > BELLDANDY_TOOL_LOOP_ITERATION_BUDGET` 时触发
- 而你当前是 `BELLDANDY_TOOL_LOOP_ITERATION_BUDGET=0`

当前实现里，`iterationBudget <= 0` 会直接视为“不启用这套预算限制”，因此不会进入这条 `force=true` 路径。

换句话说：

- 你现在看到的“上下文涨不上去”
- 不是因为 tool-loop budget 触发了 `force=true`

#### `force=true` 在当前代码里真正做了什么

它的作用不是“无条件清空上下文”，而是：

- 跳过 `originalTokens <= tokenThreshold` 这道判断
- 只要历史消息条数还大于 `keepRecent`
- 就强制把更早的 user/assistant 历史折叠进 summary

也就是说，`force=true` 的真实语义更接近：

- “即使还没到 800000，也先把旧历史收口后再停”

而不是：

- “遇到就直接把上下文压到很低”

#### 那为什么你以前会感觉“涨不上去”

如果不是 `force=true`，当前更可疑的是这几层联合作用：

1. `MAX_HISTORY=20`
   - 会话读写时就先把消息窗口裁短了。

2. `KEEP_RECENT=20`
   - 主 compaction 看到 user/assistant 历史条数不超过 20 时，直接不压，也意味着“更早历史已经没有机会继续自然堆高”。

3. `tool_result` 提前被压
   - 统一压缩层和 microcompact 都发生在主 compaction 前，很多最吃 token 的往往正是旧工具输出。

4. `triggerFraction=0.72`
   - 只要总 prompt 逼近 `612000`，系统就会开始尝试 compaction 检查。
   - 虽然这一步不保证真的压缩，但会让“预算保护机制”更早介入。

#### `blocking=720000` 会不会在没到 800000 之前就先把 compaction 弄坏

不会。

更准确地说：

- 它不会阻止 compaction “开始”
- 它只会阻止 compaction “继续调用摘要模型”

当前流程是：

1. 先判断是否进入 compaction
2. 进入后，构建 rolling / archival summary 的 prompt
3. 如果这个摘要 prompt 自己已经大到 `>= 720000`
4. 那就不再请求摘要模型，而是直接切到本地 fallback summary

所以它不会出现：

- “还没到 `800000`，主 compaction 就先被 blocking 熔断”

真正会出现的是：

- 主 compaction 已经开始
- 但摘要模型调用被预算保护截住
- 改走本地 fallback summary

这属于：

- “压缩质量降级”

而不是：

- “主压缩完全失效”

| `blocking` 阈值 | `76500` | 自动推导为 `720000` | 旧配置在 very early compaction prompt 就可能触发“放弃调用摘要模型，直接走本地 fallback summary”；新配置仍保留预算保护，但已经不再是早期频繁触发的级别。 |
| `MAX_HISTORY` | `10` | `20` | 新配置把原始消息窗口从 10 条扩到 20 条，能保留更多“最近真实上下文”；旧配置更依赖 summary 与 transcript 恢复。 |
| `KEEP_RECENT` | `16` | `20` | 旧配置更容易把超过 16 条的 user/assistant 历史折叠进 summary；新配置保留最近原文更多，但也更容易出现“主 compaction 触发空间被 keepRecent 吃掉”的情况。 |
| `MODEL_CONTEXT_WINDOW` / `CONTEXT_WINDOW_FRACTION` | 都未显式设置 | 都已显式设置 | 旧配置完全不知道主模型窗口，只能机械按固定阈值工作；新配置终于具备“随着 1M 主模型能力联动”这一层语义。 |
| 主体感 | “上下文很容易提前被压缩，长不起来” | “主压缩明显后移，但最近原文窗口仍受 `MAX_HISTORY=20` / `KEEP_RECENT=20` 共同约束” | 旧配置的主要问题是阈值保守；新配置的主要限制已从“阈值太低”转向“最近消息窗口本身偏紧”。 |

#### 最值得抓住的变化

1. 旧配置的核心问题是：`850000` 的输入预算，配了一个 `85000` 的 compaction 阈值，本质上只让系统使用了大约 `10%` 的 headroom 就开始主动摘要化。
2. 新配置已经把这个问题基本纠正：主阈值被推到了 `800000`，不再是“模型给了 1M，但策略只敢用 85K”。
3. 旧配置更像“优先求稳、优先省 prompt”；新配置更像“允许真实长上下文先长起来，再在靠近预算边缘时收口”。
4. 新配置剩下的主要瓶颈，已经不是 `COMPACTION_THRESHOLD` 太低，而是：
   - `MAX_HISTORY=20`
   - `KEEP_RECENT=20`
   - 旧 `tool_result` 会在主 compaction 前被更早压掉
