# 计划模式功能优化方案

## 1. Goal

为 Star Sanctuary 的“计划相关能力”做一次收口盘点，并给出后续优化边界。本文重点回答两个问题：

1. 项目里现在到底有没有 Agent 在执行任务过程中的“计划”能力。
2. 如果有，这些能力分别以什么形式暴露给用户、主 Agent、后端运行态和前端 UI。

本文结论不是“从零设计 planner”，而是先确认现状：仓库已经具备多条计划相关能力线，但尚未形成普通主会话层统一、持续、可观测的计划模式。

截至 `2026-06-27`，本文提出的主会话统一 `planState / plan panel` MVP 与进入策略收尾已经完成；本文现阶段同时承担两种作用：

1. 保留最初方案设计与边界判断，说明为什么采用当前路线。
2. 作为实现收口记录，明确哪些能力已经落地，哪些内容被明确留在未来增强而不再纳入本轮范围。

在这次补充盘点里，还需要把一个看似独立、实际与后续统一收口强相关的入口问题一起归位：

- **Dynamic Workflow 工具入口可见性**：`run_workflow` 相关能力虽已实现，且现在已经在 WebChat 的“调用设置 → 内置工具”里补齐了基础可见性与缺失原因提示；但这一项不等于“统一 Plan Mode”，只能视为后续统一收口前的前置修补。

## 2. 现状结论

### 2.1 总结

项目当前已经实现三条明确的计划相关能力线：

1. **Goal / 长期任务 planning**：提供 task graph、capability plan、checkpoint、handoff、governance 等正式治理能力。
2. **Dynamic Workflow / 动态工作流编排**：提供 `WorkflowContext`、`run_workflow`、journal、预算熔断、恢复与状态查询能力。
3. **Subtask / delegation 执行中拆解**：提供子任务拆分、resume、takeover、update、archive、team lane、fan-in 等运行能力。

当前最接近“planner”核心实现的不是普通聊天会话内建 plan，而是：

- `packages/belldandy-core/src/goals/capability-planner.ts`

它服务的是 Goal 节点 capability plan，而不是通用主会话级的统一计划状态协议。

### 2.2 关键判断

立项时，仓库**不缺计划原语**，缺的是：

- 普通主会话层统一的 plan state
- 主 Agent 可持续更新的当前计划对象
- 前端可稳定展示的统一“计划面板”
- 与普通聊天会话强绑定的 `plan.get / plan.update / current_plan` 一类协议

截至 `2026-06-27`，上述四项已经完成 MVP 收口：

- 已落地会话级 `planState` 单真源
- 已落地主 Agent 可持续更新的 `plan_current_get / plan_current_update`
- 已落地 WebChat 统一 `plan panel`
- 已落地 `conversation.meta` / `conversation.plan.updated` / `system.doctor -> queryRuntime` 的稳定投影

当前剩余的已不再是“有没有统一 Plan Mode”，而是明确其产品边界：

- 默认不强制进入，保持 Agent 驱动的惰性进入
- 完成后保留终态，不扩多计划历史
- Workflow 继续保持轻量 bridge，不扩独立 viewer
- Goal / Workflow / Subtask 继续保持只读 bridge + 外跳转，不做双向写真源

## 3. 风险、可行性与边界

### 3.1 风险等级

中风险。

### 3.2 主要失败模式

| 失败模式 | 说明 |
|---|---|
| 概念混淆 | 把 Goal / Workflow / Subtask 三条线误认为同一种 planner，导致方案边界失真 |
| UI 误判 | 把后端已有运行时误写成前端已有完整计划界面，造成实现范围虚高 |
| 状态真源分裂 | 新增统一计划模式时，如果不定义唯一真源，容易出现会话态、goal 态、workflow 态彼此漂移 |
| 过度设计 | 在未明确“普通主会话计划模式”范围前，直接把 goal governance 全量搬进聊天层，导致复杂度失控 |

### 3.3 可行性与前提

可行性高，原因是底层原语已经存在，后续主要是“统一建模与补入口”，不是从零搭系统。

关键前提：

1. 明确统一计划模式的作用域是“普通主会话”，不是替代 Goal / Workflow / Subtask。
2. 明确唯一真源应落在会话运行态还是独立计划状态文件，避免前后端各自拼装。
3. 明确最小 UI 收口面，只做“可见、可追踪、可恢复”，不一次性复制全部 goal governance 面板。

### 3.4 粗略工作量

中等。

如果只做“普通主会话统一计划状态 + 最小前端展示 + Agent 更新协议”，工作量可控；如果把 Goal / Workflow / Subtask 全部强行统一成一个总治理框架，工作量会明显放大。

### 3.5 收口边界

本文**包含**：

- 当前仓库计划相关能力盘点
- 四层入口与状态映射
- 缺口识别
- 统一 `plan state / plan panel` 的具体实现方案
- 后续优化建议收口

本文**不包含**：

- 直接落地代码实现
- 直接修改 Goal / Workflow / Subtask 现有实现
- 多计划历史治理系统
- 全自动跨 Goal / Workflow / Subtask 深度双向同步

本文的**完成标准**：

1. 能明确回答“仓库里有没有计划能力”。
2. 能明确回答“这些能力分别暴露在哪一层”。
3. 能明确指出“当前还缺什么统一能力”。
4. 能给出统一 `currentPlan` 的真源、协议、事件与 UI 落点。
5. 能直接指导后续按阶段进入实现，而不是停留在原则描述。

### 3.6 Intended Effect

每一项盘点的目的都不是做文档罗列，而是为后续统一计划模式提供真实边界：

- 盘点 Goal：确认正式治理能力已经存在，不应重复造轮子。
- 盘点 Workflow：确认系统已支持可执行编排，不必把“计划”理解成纯文本 checklist。
- 盘点 Subtask：确认执行中拆解和多 lane 协作已存在，可作为计划执行层复用。
- 标出主会话缺口：把后续优化目标聚焦到“统一计划状态模型”，而不是泛化重写所有任务系统。

## 6. 当前缺口与优化方向

### 6.1 立项时缺口（现已完成 MVP 收口）

当前真正缺的不是“计划能力有没有”，而是“计划能力如何在普通主会话层统一收口”。至少有四个缺口：

1. 缺少统一会话级 plan state。
2. 缺少主 Agent 在执行过程中可持续读写的统一计划协议。
3. 缺少跨 Goal / Workflow / Subtask 的最小映射规则。
4. 缺少面向用户的统一计划 UI。

上述四项现已完成 MVP 收口。当前剩余的重点不再是补基础设施，而是维持边界稳定：

1. 普通会话默认不建 plan。
2. `current plan` 完成后保留终态。
3. workflow 继续维持轻量 bridge。
4. plan 与 Goal / Workflow / Subtask 不做双向写真源。

### 6.2 第一项工作的准确归位

这项前置工作不应被描述成“给普通会话接入统一 Plan Mode”，更准确的表述是：

- **补齐 Dynamic Workflow 的工具入口可见性与可解释性。**

当前代码路径说明了这项工作的真实边界：

1. WebChat 的“调用设置 → 内置工具”并没有维护一份前端静态白名单，而是直接渲染 `tools.list` 返回的 `builtin` 列表。
2. `tools.list` 会把当前运行时里**已注册**的 builtin 工具返回给前端。
3. `run_workflow` 只会在 `WorkflowRuntime` 成功初始化后才注册到 `toolExecutor`。
4. 当前 `WorkflowRuntime` 的装配依赖 global memory manager，因此 `run_workflow` 的出现与否，首先受后端运行态初始化前提影响，而不是单纯的前端漏了一个开关项。

因此，这项工作的最小闭环应是：

1. 明确 `run_workflow` 的注册前提与不可见原因。
2. 满足前提时，确保它稳定出现在 WebChat 的 builtin tools 列表中。
3. 不满足前提时，在 tool settings / doctor / 可观测性里给出明确解释，而不是让用户误以为“功能没做完”或“前端漏接线”。

以上入口问题现已补齐；后续优化重点应正式转入统一 `planState` 本身。

### 6.3 建议优化方向

建议把后续优化拆成两个层次推进，而不是一上来重写现有三条能力线：

1. **Phase 0：先补 Dynamic Workflow 工具入口**。先把 `run_workflow` 在 WebChat 调用设置里的可见性与解释链路补齐。
2. **Phase 1：再补状态模型**。定义 conversation-scoped 的 plan state，明确唯一真源。
3. **Phase 2：再补 Agent 协议**。让主 Agent 能创建、更新、完成、阻塞计划项，而不是只在文本里口述计划。
4. **Phase 3：再补最小 UI**。先做会话内计划摘要、步骤状态、阻塞原因、跳转入口。
5. **Phase 4：最后做跨线桥接**。允许计划项映射到 Goal node、Workflow run、Subtask task，但不要求第一版深度统一治理。

## 7. 建议收口方案

### 7.1 推荐方案

推荐采用“主会话轻量计划层 + 底层复用三条既有能力线”的方案。

理由：

1. 现有 Goal / Workflow / Subtask 已经足够强，不需要推倒重来。
2. 用户真正缺的是“当前任务到底按什么计划推进、推进到了哪一步”的稳定可见性。
3. 先补统一计划状态层，能以最小代价把现有能力组织起来。

### 7.2 不推荐方案

不建议直接把 Goal governance 全量抬升为普通聊天默认模式。

原因：

1. Goal 体系更重，适合长期任务，不适合所有普通会话。
2. Workflow 体系更像显式编排，不适合所有开放式任务。
3. Subtask 体系偏执行拆分，不能单独充当总计划状态。

### 7.3 最小落地闭环

如果后续进入实现，建议按两个大阶段收口：

第一大阶段：

1. `run_workflow` 在 WebChat 内置工具里稳定可见
2. 不可见时有明确原因提示
3. builtin workflow / file workflow 的入口语义可被用户理解

第二大阶段：

1. 会话级 `plan state`
2. 主 Agent 可更新计划步骤
3. 前端显示当前计划与状态
4. 计划项可选跳转到 goal / workflow / subtask

第二大阶段内部再拆成 Phase A / B / C，见第 14 节。

这样可以先完成“工具入口可见性”，再完成“统一计划可见性”，避免把两类问题混成一次大改。

### 7.4 后续计划

下一步建议分两步走：

1. 先落地统一 `planState` 的唯一真源、持久化、事件与 Agent 更新协议。
2. 再把 WebChat 聊天页里的 plan summary / detail panel 接上，并补 Goal / Workflow / Subtask bridge。

优先这样做的原因是：Dynamic Workflow 工具入口问题已经补齐；当前真正缺的闭环已经收缩成“主会话 current plan 的真源与展示”。如果不先把真源立住，后面的 Agent 工具、事件广播和前端面板都会各自拼装，最后再次分裂。

当前还缺的关键闭环是：

- 会话级计划对象的唯一真源
- 主 Agent 可持续更新的统一计划协议
- `conversation.meta` 与 WebSocket 事件的稳定投影
- 计划步骤与 Goal / Workflow / Subtask 的映射规则
- 前端如何显示“当前计划”而不引入新的 UI 膨胀

## 8. 统一 Plan State 目标与定位

### 8.1 目标

统一计划层的目标不是让所有普通会话都强制进入 Plan Mode，而是补一个**可选启用、会话级单真源、主 Agent 可持续更新、前端可稳定展示**的 `currentPlan`。

第一版需要同时满足五个条件：

1. **不强制**：普通闲聊、短问答、单步任务可以没有计划对象。
2. **可持续**：一旦主 Agent 进入复杂任务推进，就能持续更新同一个当前计划对象，而不是每轮只靠文本口述。
3. **可观测**：前端能稳定显示计划标题、步骤状态、当前焦点、阻塞原因与下一步动作。
4. **可桥接**：计划步骤可以显式引用 Goal / Workflow / Subtask，但不把三条能力线硬合并成一个重型治理系统。
5. **可回收**：计划完成、取消、替换后，旧计划不会扩张成多 plan 历史系统。

### 8.2 非目标

第一版明确**不做**：

1. 普通会话默认自动建计划。
2. 多个历史计划并列管理。
3. 把 Goal governance 直接搬成主聊天默认模式。
4. Goal / Workflow / Subtask 的自动双向深度同步。
5. 独立的新顶层导航页或新的主工作区模式。

### 8.3 推荐定位

推荐把统一计划层定位成：

- **主会话上的轻量 orchestration overlay**
- 负责“这次复杂任务当前如何推进”
- 复用现有 Goal / Workflow / Subtask 作为底层执行与治理能力

换句话说，`currentPlan` 解决的是“主 Agent 现在按什么计划推进”，不是“替代所有任务系统”。

### 8.4 推荐真源

推荐把 `currentPlan` 挂在 `ConversationStore` 的 conversation meta 中，字段名使用：

- `planState`

推荐原因：

1. 当前 `conversation.meta` 已经在聚合会话级运行信息，如 `continuationState`、`taskTokenResults`、`loadedDeferredTools`、`compactBoundaries`。
2. `packages/belldandy-agent/src/conversation.ts` 已有 `persistConversationMeta()`、`loadMetaFromFile()`、`loadMetaFromFileAsync()` 这些成熟持久化位点。
3. WebChat 已经在 `apps/web/public/app.js` 的 `loadConversationMeta()` 中拉取会话级 UI 投影，新增 `planState` 成本最低。
4. 第一版只维护一个 `currentPlan`，对象体积可控，不需要单独拉起新的 runtime tree。

### 8.5 不推荐真源

第一版不推荐这两种做法：

1. **独立 `plan-runtime.json` 文件**：
   - 优点是边界清晰。
   - 缺点是会额外引入一条新的持久化、恢复、查询与广播链路，而当前系统已经有会话 meta 聚合点。
2. **直接复用 Goal / Workflow / Subtask 之一作为唯一真源**：
   - 优点是少建一个对象。
   - 缺点是三者都不等于“普通主会话当前计划”，会把作用域再次混淆。

## 9. 数据模型设计

### 9.1 推荐 Schema

建议把 `planState` 定义为单个当前计划对象：

```ts
export type ConversationPlanState = {
  version: 1;
  planId: string;
  revision: number;
  status: "draft" | "active" | "blocked" | "completed" | "cancelled";
  title: string;
  summary?: string;
  mode: "agent" | "manual";
  createdAt: number;
  updatedAt: number;
  updatedBy: "agent" | "user" | "system";
  currentStepId?: string;
  nextAction?: string;
  blocker?: string;
  steps: ConversationPlanStep[];
};

export type ConversationPlanStep = {
  id: string;
  title: string;
  summary?: string;
  status: "pending" | "in_progress" | "blocked" | "completed" | "skipped";
  blocker?: string;
  refs?: ConversationPlanRef[];
  updatedAt: number;
};

export type ConversationPlanRef =
  | { kind: "goal"; goalId: string; nodeId?: string; label?: string }
  | { kind: "workflow"; journalId: string; workflowName?: string; label?: string }
  | { kind: "subtask"; taskId: string; sessionId?: string; label?: string };
```

### 9.2 字段语义

核心字段约束如下：

| 字段 | 用途 | 说明 |
|---|---|---|
| `planId` | 当前计划实例 ID | 同一会话内 replace 新计划时应更换 |
| `revision` | 乐观并发版本号 | 每次 update 成功后递增 |
| `status` | 计划整体状态 | 与步骤状态不是一一自动推导关系 |
| `mode` | 来源模式 | 第一版主要是 `agent`，预留 `manual` |
| `currentStepId` | 当前焦点步骤 | 允许为空，表示当前无明确焦点 |
| `nextAction` | 下一步动作摘要 | 用于摘要卡片与 detail panel 顶部 |
| `blocker` | 当前阻塞原因 | 计划级阻塞，不替代 step blocker |
| `steps` | 有序步骤列表 | 数组顺序即展示顺序，不单独再建排序字段 |
| `refs` | 外部能力桥接 | 只做显式引用，不做第一版深度自动同步 |

### 9.3 归一化与上限建议

为了避免 conversation meta 膨胀，建议在 normalize 层加这些上限：

1. `steps` 默认最多 24 条。
2. 每个 step 的 `refs` 默认最多 8 条。
3. `title` 建议截断到 120 字符以内。
4. `summary` / `nextAction` / `blocker` 建议截断到 500 字符以内。
5. 空字符串统一归一化成 `undefined`。
6. `updatedAt` 统一在服务端写入，不信任客户端/工具传入值。

### 9.4 持久化与实现落点

推荐实现落点：

1. 新建 `packages/belldandy-agent/src/conversation-plan-state.ts`
   - 放 schema、normalize、patch apply、ref merge、状态校验
2. `packages/belldandy-agent/src/conversation.ts`
   - 只做 `Conversation` 类型扩展、meta 读写接线、公开 `getPlanState()` / `updatePlanState()` / `clearPlanState()`
3. 不建议把完整 plan patch 逻辑继续堆进 `conversation.ts`

这样做的原因是：`packages/belldandy-agent/src/conversation.ts` 当前已超过 3000 行，按仓库规则应尽量避免继续在原文件里堆叠新逻辑。

## 10. Agent 协议设计

### 10.1 第一版工具面

推荐第一版只提供两个 builtin tools：

1. `plan_current_get`
2. `plan_current_update`

不建议第一版先开用户直接写入的 `conversation.plan.update` RPC。原因是当前用户诉求首先是“主 Agent 可持续更新计划 + 前端可稳定展示”，不需要同时引入第二套写入口。

### 10.2 `plan_current_get`

建议 schema：

```ts
type PlanCurrentGetInput = {};

type PlanCurrentGetOutput = {
  conversationId: string;
  planState: ConversationPlanState | null;
};
```

语义：

1. 绑定当前运行会话，不额外接收 `conversationId`。
2. 无计划时返回 `planState: null`。
3. 主要用于主 Agent 在继续推进前读取当前计划真源，而不是依赖前文口述。

### 10.3 `plan_current_update`

建议 schema：

```ts
type PlanCurrentUpdateInput = {
  baseRevision?: number;
  ifAbsent?: "create" | "reject";
  seed?: {
    title: string;
    summary?: string;
    mode?: "agent" | "manual";
    status?: "draft" | "active";
  };
  operations: ConversationPlanPatchOperation[];
};

type PlanCurrentUpdateOutput = {
  conversationId: string;
  applied: boolean;
  conflict: boolean;
  planState: ConversationPlanState | null;
};
```

### 10.4 Patch 动作集合

推荐第一版动作集合如下：

```ts
type ConversationPlanPatchOperation =
  | { type: "replace"; plan: Omit<ConversationPlanState, "revision" | "createdAt" | "updatedAt" | "updatedBy"> }
  | { type: "set_header"; title?: string; summary?: string }
  | { type: "set_status"; status: ConversationPlanState["status"]; blocker?: string }
  | { type: "set_focus"; currentStepId?: string; nextAction?: string; blocker?: string }
  | { type: "upsert_step"; step: Omit<ConversationPlanStep, "updatedAt"> }
  | { type: "set_step_status"; stepId: string; status: ConversationPlanStep["status"]; blocker?: string }
  | { type: "attach_ref"; stepId: string; ref: ConversationPlanRef }
  | { type: "clear" };
```

动作设计原则：

1. 默认 patch，不要求每轮整对象重写。
2. 保留 `replace`，用于首次成型或大幅重排。
3. `clear` 只清当前计划，不引入历史档案系统。
4. `set_focus` 用来支撑 UI 的“当前焦点 / 下一步动作”摘要区。

### 10.5 并发与所有权约束

第一版建议采用保守策略：

1. **只有主会话 Agent 拥有写权限**。
2. 子任务 Agent、workflow 内部 lane、goal 专项运行态**不直接写**主会话 `planState`。
3. 它们的进展先通过文本、tool 结果或 bridge refs 暴露，再由主 Agent 汇总更新 `currentPlan`。
4. `baseRevision` 不匹配时返回 `conflict: true` 与当前 `planState`，由调用方决定是否重试。

这样可以避免第一版就进入多 writer 竞争。

## 11. 会话投影与事件模型

### 11.1 `conversation.meta` 扩展

推荐在 `packages/belldandy-core/src/server-methods/workspace-conversation.ts` 的 `conversation.meta` payload 中新增：

```ts
{
  conversationId,
  ...,
  continuationState,
  planState,
  goalSessionEntryBanner,
}
```

接入方式建议保持和 `continuationState` 一样的会话投影层级，而不是单独再建一个 `conversation.plan.get` 给 WebChat 首屏加载。

### 11.2 WebSocket 事件

推荐新增事件：

- `conversation.plan.updated`

建议 payload：

```ts
type ConversationPlanUpdatedEvent = {
  conversationId: string;
  planState: ConversationPlanState | null;
  source: "tool" | "rpc" | "system" | "restore";
  revision?: number | null;
  updatedAt?: number;
  cleared?: boolean;
  reasonCode?: string;
  planLifecycle?: {
    action: "created" | "updated" | "replaced" | "cleared";
    hadExistingPlan: boolean;
    enteredPlanMode: boolean;
    switchedCurrentPlan: boolean;
    retainedTerminalSnapshot: boolean;
    operationTypes: string[];
    previousPlanId: string | null;
    planId: string | null;
    status: string | null;
    revision: number | null;
    stepCount: number;
  };
};
```

命名理由：

1. 当前 WebChat 已有 `conversation.digest.updated`。
2. `goal.update`、`subtask.update` 也使用同样的单事件命名风格。
3. `conversation.plan.updated` 足够直接，且能表达“当前计划快照已更新”。

### 11.3 Doctor / Trace 稳定观测口径

第一版收尾后，`planState` 相关可观测性建议严格分成三层，不再混读：

1. **当前会话业务真源**：
   - `conversation.meta.planState`
   - `conversation.plan.updated.payload.planState`
2. **当前这次计划更新的生命周期语义**：
   - `conversation.plan.updated.payload.planLifecycle`
   - `tool_result.metadata.planLifecycle`
3. **线上运行诊断 / 回溯**：
   - `system.doctor -> queryRuntime.traces[*]`
   - 命中 `method === "message.send"`、`stage === "tool_result_emitted"`、`detail.toolName === "plan_current_update"`

其中需要明确：

1. `planState` 是业务真源。
2. `planLifecycle` 是从一次 update 行为派生出来的**运行观测元数据**，用于回答“这次是不是懒进入了 Plan Mode、是不是替换了 current plan、是不是保留了终态快照”，不是第二份业务真源。
3. `system.doctor -> queryRuntime` 是诊断读面，不承担前端计划展示真源职责。

推荐把 `planLifecycle` 的读法固定为下表：

| 原始字段 | trace 投影字段 | 稳定含义 | 推荐用途 |
|---|---|---|---|
| `action` | `planLifecycleAction` | 本次更新是 `created / updated / replaced / cleared` 哪一种 | 判断是否发生懒进入、替换或清空 |
| `status` | `planStatus` | 更新完成后当前 `planState.status` | 判断当前计划终态 / 活跃态 |
| `planId` | `planId` | 更新完成后的 current plan 实例 ID | 识别当前计划实例 |
| `previousPlanId` | `previousPlanId` | 被 replace 前的旧 current plan ID | 识别是否切换了 current plan |
| `operationTypes` | `planOperationTypes` | 本次 patch 操作类型列表 | 辅助诊断，不作为业务真源 |
| `enteredPlanMode` | `enteredPlanMode` | 是否从“无计划会话”首次进入统一 planState | 诊断惰性进入是否发生 |
| `switchedCurrentPlan` | `switchedCurrentPlan` | 是否切换到了新的 current plan | 诊断 replace 语义是否生效 |
| `retainedTerminalSnapshot` | `retainedTerminalSnapshot` | 当前快照是否为保留展示的终态计划 | 诊断 completed / cancelled 后为何仍显示 |

以下字段保留在原始 `planLifecycle` 中，但第一版不强制投影到 trace detail：

1. `hadExistingPlan`
2. `revision`
3. `stepCount`

推荐读法顺序：

1. 想知道“当前会话现在的计划长什么样”时，只读 `planState`。
2. 想知道“这一次为什么进入 plan / 为什么替换 plan / 为什么完成后还保留”时，读 `planLifecycle`。
3. 想做线上回溯或 doctor 诊断时，读 `system.doctor -> queryRuntime` 的 `tool_result_emitted.detail` 投影，不要从 panel 展示态反推进入策略。

### 11.4 刷新时序

推荐刷新链路如下：

1. 打开会话时，`apps/web/public/app.js` 的 `loadConversationMeta()` 拉取 `conversation.meta`
2. `payload.planState` 下发给新建的 `sessionPlanFeature.setPlanState(...)`
3. 运行中若主 Agent 调用 `plan_current_update` 成功，服务端广播 `conversation.plan.updated`
4. `apps/web/public/app/features/chat-events.js` 把事件转发给 `sessionPlanFeature.handlePlanUpdated(...)`
5. 切换会话、断连或读取失败时清空当前会话 plan view

### 11.5 第一版不做的事件能力

第一版不做：

1. plan patch 级事件流
2. plan history timeline
3. step 级独立 event topic

原因是前端当前只需要消费“最新 current plan 快照”。

## 12. WebChat Plan Panel 设计

### 12.1 设计原则

前端设计遵循三个收口原则：

1. **不新增顶层导航**：计划面板属于聊天页上下文，不新开 Goals / Subtasks 级别的页签。
2. **不强制可见**：没有 `planState` 的普通会话，不展示大块空白计划区。
3. **复用现有样式**：优先复用 `session-digest`、`memory-badge`、modal 结构与交互节奏。

### 12.2 UI 结构

推荐在聊天页加入两层 UI：

1. **Current Plan 摘要卡**
   - 位置：与 `sessionDigestSummary` 同一组会话摘要区
   - 展示：计划标题、整体状态、当前步骤、下一步动作、阻塞标记
   - 行为：点击后打开 detail modal
2. **Current Plan 详情面板**
   - 形态：复用现有 modal 风格，而不是新增新页面
   - 展示：标题、summary、plan status、更新时间、step list、refs chips、blocker、nextAction

### 12.3 空状态与完成态

推荐状态策略：

1. `planState === null`
   - 默认不显示计划卡片
2. `status === "active" | "blocked"`
   - 显示摘要卡
3. `status === "completed" | "cancelled"`
   - 仍保留一个可折叠摘要卡，直到下一次 replace 或 clear

这样能兼顾“普通会话不被强制规划”和“复杂任务完成后仍可回看 closure”。

### 12.4 交互细节

摘要卡推荐最少展示：

1. 计划标题
2. 整体状态 badge
3. 当前步骤标题
4. `nextAction`
5. `blocked` / `completed` 等关键状态标记

详情面板推荐展示：

1. 头部：标题、状态、模式、更新时间
2. 说明区：summary、nextAction、blocker
3. Step 列表：按数组顺序展示，每项带状态 badge
4. Refs：Goal / Workflow / Subtask chips
5. 跳转动作：能跳则跳，不能跳则显示只读标识

### 12.5 前端落点建议

建议新增或改动这些文件：

1. `apps/web/public/app/features/session-plan.js`
   - 新建，负责摘要卡、modal、事件响应、locale refresh

   - 初始化 `sessionPlanFeature`
   - 在 `loadConversationMeta()` 中调用 `setPlanState`

## 13. 与 Goal / Workflow / Subtask 的桥接规则

### 13.1 桥接原则

第一版 bridge 只做三件事：

1. **显式引用**
2. **稳定展示**
3. **有限跳转**

不做：

1. 自动接管 Goal 状态机
2. 自动跟随 Workflow journal 改写 step 状态
3. 自动跟随 Subtask runtime 改写 plan status

### 13.2 三类 Ref 规则

| Ref Kind | 必填字段 | UI 作用 | 第一版自动同步 |
|---|---|---|---|
| `goal` | `goalId` | 展示 goal label，可跳到 Goal detail / base conversation | 不做 |
| `workflow` | `journalId` | 展示 workflowName / journalId，作为执行证据 | 不做 |
| `subtask` | `taskId` | 展示子任务入口，可跳 Subtask detail | 不做 |

### 13.3 推荐展示语义

1. Goal ref
   - 适合表达“此步骤落在某个长期任务节点”
2. Workflow ref
   - 适合表达“此步骤已经通过动态工作流执行”
3. Subtask ref
   - 适合表达“此步骤已下放给某个子任务继续推进”

### 13.4 后续可选增强

如果后续要增强 bridge，推荐优先做“轻量跟随”而不是“直接改真源”：

1. 读取 Goal / Workflow / Subtask 当前状态
2. 在前端把 ref chip 显示为 `running / blocked / done` 等只读 badge
3. 不直接回写 `planState.steps[].status`

这样可以先增强可见性，而不把状态所有权再次搞混。

### 13.5 与编程工作台的接入边界（未来可选）

编程工作台接入后，Plan Mode 仍是普通主会话的可选执行摘要，不升级为跨模块调度器。

1. Headless/IDE/CI 发起的普通 Coding Run 不自动创建 `planState`；只有主 Agent 按既有惰性进入策略明确维护计划时，才显示计划面板。
2. `AgentRunEvent`、Goal 更新、Workflow Journal 和 Subtask 运行态不得直接触发 `conversation.plan.updated`，也不得直接改写 `planState.steps[].status`。
3. 若后续确有展示需求，可在阶段 0 的状态所有权 ADR 通过后新增只读 `coding_run` ref。它至少应包含 `agentRunId`、`source` 与必要的 `conversationId` / `journalId` / `taskId` / `worktreeId` 类型化引用；不保存第二套运行状态，也不提供从 Plan 面板直接控制 run 的能力。
4. Goal、Workflow、Commander/Subtask 的状态仍只通过既有或未来的只读 badge 回流。Coding run 成功不等于 Goal 节点完成，Workflow resume 也不等于 Conversation continue。
5. 任何未来 UI 增强都复用现有聊天页摘要区、ref 跳转和状态高亮，不新增顶层“Coding Plan”导航或第二套前端 store。

这项兼容设计不改变当前 `planState` schema、已完成的 Phase A-C 或收口判断；只有编程工作台公共契约稳定后，才按真实展示需求立项实现。

### 14.5 后续决策题评估

风险等级：中

粗略工作量：小到中

主要失败模式：

1. **进入策略过宽**：把大量普通会话也拉进 `planState`，重新制造“所有对话都像在走 planner”的噪音。
2. **生命周期过短**：计划一完成就自动清空，导致 plan panel 失去收尾与追踪价值。
3. **workflow viewer 过早膨胀**：在只有少量 bridge 需求时，过早扩成独立工作流产品面板。
4. **深层双向同步失控**：让 `planState` 与 Goal / Workflow / Subtask 互相写真源，导致状态漂移、重复治理和回滚困难。

可行性与前提：

1. 当前 `planState` 已经是可选会话级真源，前端也能在无计划时完全隐藏，因此“保持轻量进入”是可行的。
2. 当前 `plan panel` 已经支持 step/ref、Goal / Subtask 跳转、workflow 只读状态回流，因此 bridge 最小闭环已经成立。
3. 当前系统仍缺 workflow 独立 viewer，也缺针对“何时自动建 plan”的运行时策略，因此后续重点应从“补基础设施”转为“定边界”。

收口边界：

1. 本节已完成后续 4 个决策题的评估与确认，并作为后续实现边界。
2. 本节不直接引入新的工作流主界面、不启动深层双向同步实现。
3. 本节的完成标准是明确后续优先路线，而不是继续扩大 Phase D 的实现范围。

Intended Effect：

1. 让统一 `planState` 继续保持“复杂任务时有用、普通会话时安静”的产品边界。
2. 避免在已有 MVP 之上过早长出第二套 workflow UI 或第二套跨系统真源同步。
3. 把下一轮工作聚焦到进入策略和生命周期，而不是继续堆功能。

#### 已确认结论（2026-06-27）

1. **Plan Mode 进入策略**：采用 **Agent 驱动的惰性进入**。默认不建 plan，只有复杂任务才由主 Agent 主动创建 `planState`。
2. **plan 生命周期**：采用 **完成后保留终态**。不做完成即清空，也不扩成多计划历史；当 Agent 制定新计划替换旧计划时，旧的 `current plan` 视为结束。
3. **workflow 展示边界**：短期继续维持 **轻量 bridge**，不做独立 workflow viewer。
4. **plan 与 goal/workflow/subtask 的同步深度**：继续保持 **只读 bridge + 外跳转**，不走双向写真源路线。

#### 决策题 1：Plan Mode 进入策略

可选方向：

1. **全自动进入**：根据复杂度判断，只要像复杂任务就自动创建 `planState`。
2. **纯手动进入**：只有用户明确要求“给我一个计划”或 Agent 明确决定建 plan 时才创建。
3. **Agent 驱动的惰性进入**：默认不建 plan；当主 Agent 判断任务需要多步持续推进时，主动调用 `plan_current_update` 以 `ifAbsent=create` 建立计划。

已确认结论：**Agent 驱动的惰性进入**。

推荐理由：

1. 这条路线最符合“我并不想普通会话也要制定计划”的原始目标。
2. 当前系统已经有 `plan_current_update`，不需要再补后端判定器或前端开关来强制介入。
3. Agent 最清楚当前任务是否进入了“需要持续维护步骤状态”的阶段，比规则引擎更不容易误判。

建议进入条件：

1. 用户明确要求分阶段、里程碑、推进方案、执行计划。
2. 主 Agent 预计任务会跨多轮、跨模块，或者需要显式跟踪阻塞与下一步。
3. 主 Agent 已经准备挂接 Goal / Workflow / Subtask ref，说明任务进入可桥接的执行期。

明确不进入的场景：

1. 闲聊、问答、一次性解释。
2. 单文件小修、小命令、小范围低风险修改。
3. Agent 自己只会做一次线性动作、不需要持续维护执行状态的场景。

#### 决策题 2：Plan 生命周期策略

可选方向：

1. **完成即清空**：计划一结束就自动删除当前 `planState`。
2. **完成后保留终态**：计划完成 / 取消 / 阻塞后，保留当前计划对象作为终态快照，直到被明确替换或清空。
3. **多计划历史归档**：完成后自动转历史，再创建新的 current plan。

已确认结论：**完成后保留终态，不做多计划历史系统**。

推荐理由：

1. plan panel 的一个核心价值就是让用户看到“刚刚是按什么步骤完成的”，完成即清空会直接抹掉这部分价值。
2. 当前 schema 是单个 `current plan`，并没有多计划历史体系；强行上历史会明显扩大范围。
3. 保留终态而不自动清空，既能维持可观测性，也不会引入新的存储模型。

建议生命周期规则：

1. `active / blocked`：持续更新。
2. `completed / cancelled`：保留为只读终态，继续展示在当前会话中。
3. 新任务如果需要新计划：由 Agent 显式 `replace` 旧 `current plan` 并切换到新的 `current plan`；若确需先清空再建，也应显式 `clear + create`，而不是后台静默覆盖。
4. 仅在用户明确要求清空，或新计划明确替换旧计划时，才结束旧的 `current plan`。

#### 决策题 3：Workflow 是否需要独立 Viewer

可选方向：

1. **立即补独立 workflow viewer**：列表、详情、状态、history、journal 全部做成单独 UI。
2. **继续维持当前轻量桥接**：在 `plan panel` 中显示 workflow ref、只读状态回流和高亮，必要时再补局部详情。
3. **中间路线**：不做新页面，只在现有 panel / modal 中增加一个轻量 workflow detail 卡片。

已确认结论：**短期继续维持当前轻量桥接，中期如有明确需求再走局部详情卡片，而不是新顶层 viewer**。

推荐理由：

1. Dynamic Workflow 目前不是普通会话默认模式，立即做独立 viewer 容易让产品重心偏到 workflow 工具本身。
2. 当前后端只有 `workflow.status` 的活跃态读取，并没有完整的前端 history / journal 浏览体系；独立 viewer 需要额外定义真源边界。
3. 现有 `plan panel` 已经能满足“知道当前是否有 workflow、它是否还活着、我该跳到哪条任务线”这类最小需求。

不建议现在就做的内容：

1. 新增顶层 workflow 导航页。
2. 对 `workflow_journal` 直接暴露一套前端浏览器。
3. 把 workflow runtime 扩成第二个与 Goals / Subtasks 平级的大模块。

#### 决策题 4：Plan 与 Goal / Workflow / Subtask 的同步深度

可选方向：

1. **深层双向同步**：plan 改动会写回 Goal / Workflow / Subtask，后者变化也自动改写 plan。
2. **单向自动映射**：底层运行态变化自动投影到 plan，但 plan 不反向写底层真源。
3. **只读 bridge + 外跳转**：plan 只保存 ref 与当前摘要，不接管底层真源。

已确认结论：**继续保持只读 bridge + 外跳转；如未来需要增强，优先做单向只读映射，不做双向写入**。

推荐理由：

1. Goal / Workflow / Subtask 本来就各自有成熟真源，双向同步会把 `planState` 从“会话级执行摘要”抬升为“跨系统总治理真源”，风险过高。
2. 当前 `planState` 的价值是主会话里的统一可见性，不是替代三条既有能力线。
3. 现在已具备 ref、跳转、高亮和 workflow 只读状态回流，说明 bridge 的主要价值已经能在不双写的前提下实现。

建议后续增强顺序：

1. 先保留当前只读 bridge。
2. 如果用户确实需要更多联动，再做“单向只读映射”，例如更丰富的 workflow / goal 状态摘要。
3. 明确不做 plan panel 直接修改 Goal / Workflow / Subtask 真源。

#### 已确认推进顺序

这一步已经完成：当前已按“**先收口 Plan Mode 进入策略 + 生命周期策略，再停止扩 workflow viewer 与跨系统深层同步**”的顺序落地。

已完成顺序：

1. 明确 Agent 何时应创建 `planState`，形成稳定进入规则。
2. 明确 completed / cancelled plan 的保留与替换策略。
3. 在此基础上，明确 workflow 继续保持轻量只读 bridge，不扩独立 viewer。
4. 明确 Goal / Workflow / Subtask 默认继续保持只读 bridge，不进入双向同步路线。

当前剩余内容已全部转为未来可选增强：

1. 如果后续确实出现更强 workflow 可视化需求，再评估局部 detail 卡片，而不是新顶层 viewer。
2. 如果后续确实出现更强跨系统联动需求，再评估单向只读映射增强，而不是双向写真源。
