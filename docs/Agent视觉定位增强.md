# Agent 视觉定位增强

本文档用于说明 `Star Sanctuary` 后续如何增强 Agent 的“看图后定位并操作”能力，目标读者为产品、策划、项目负责人和参与方案评审的同学。本文尽量使用非技术语言描述，不展开代码实现细节。

## 一、这项能力要解决什么问题

我们后续希望 Agent 不只是“能看懂截图里有什么”，而是进一步做到：

- 看网页截图后，找到某个按钮、输入框、状态标签或提示信息
- 看桌面截图后，找到某个窗口、图标、菜单、文字按钮或区域
- 在找到目标之后，执行点击、输入、滚动、切换等操作
- 操作完成后再次观察屏幕，确认结果是否符合预期

简单说，这不是单纯的“看图识别”，而是要让 Agent 逐步具备一种接近人类的“看屏幕做事”能力。

## 二、为什么现有能力还不够

当前仓库已经有较强的截图和看图基础，主要包括：

- 浏览器截图
- 桌面截图
- 摄像头拍照
- 图片理解与摘要
- 重点区域说明
- 指定目标追问

这些能力已经可以回答“这张图里大概有什么”“重点区域是什么”“某个元素可能在哪一块”。

但它们还缺一块关键能力：

- 把“看懂”变成“能精确落点”

也就是说，当前系统更擅长“理解内容”，还不擅长“给出稳定坐标并执行后续操作”。

这也是我们后续要补上的核心环节。

## 三、现有参考项目能带来什么启发

我们分析了 `tmp/dgjh-2.0.0` 这个视觉定位小项目，也参考了 Context7 中的成熟文档资料。

### 1. `dgjh-2.0.0` 的启发

这个项目的核心思路不是“再做一套看图理解”，而是：

- 先看整张图
- 找出几个最可能的候选区域
- 对候选区域局部放大
- 再次识别
- 最后给出目标的大致位置

这条思路非常符合“看懂之后去点”的需求。

它的价值主要体现在：

- 适合寻找带文字线索的按钮、标签、菜单
- 适合从全屏中逐步缩小范围
- 适合输出“可操作位置”而不是只输出“文字描述”

但它本身更像一个实验原型，不适合直接原样接入主仓库。

### 2. Context7 参考带来的启发

通过 Context7 查到的参考资料，给出了两个很重要的方向。

第一，网页场景不要优先走“纯截图点击”。

Playwright 官方最佳实践明确建议：

- 优先按角色、名称、可访问性信息、页面结构去找元素
- 不要把网页定位完全建立在图片识别上

这说明对于网页，最稳妥的方法不是“看图找按钮”，而是：

- 能直接从页面结构里找到，就不要先截图再猜

第二，OCR 技术本身天然支持“文字框定位”。

PaddleOCR 和 Tesseract 的官方资料都表明：

- OCR 不只是返回识别到的文字
- 还可以返回文字所在区域的坐标框、多边形、置信度

这说明在桌面截图、窗口截图、复杂图像中，我们完全可以先借助 OCR 找到文字块，再把它变成候选点击区域。

## 四、我们建议采用什么总体方案

结论是：

- 不建议做“纯视觉点击系统”
- 也不建议再单独做一套与现有图片理解并行的视觉栈
- 最合理的方向是做“混合式视觉定位系统”

这个系统的核心原则是：

- 能走结构化定位时，优先走结构化定位
- 只有结构化定位做不到时，才走视觉定位
- 所有操作完成后，都要再次观察确认

## 五、推荐的能力路线

我们建议把 Agent 的视觉操作能力拆成三层。

### 第一层：观察层

这一层的目标是“先看到世界”。

包括：

- 浏览器页面结构观察
- 浏览器截图
- 桌面截图
- 窗口截图
- 区域截图
- 图片理解

这一层的重点不是点击，而是让 Agent 获得足够的信息。

### 第二层：定位层

这一层的目标是“知道该点哪里”。

建议重点建设以下几类定位能力：

- 文字定位
  - 例如找到“登录”“确定”“保存”“关闭”“继续”
- 描述定位
  - 例如找到“右上角蓝色按钮”“左侧设置菜单”“输入手机号的输入框”
- 区域验证
  - 例如判断某个区域是不是我们想点的目标

这一层是整个方案的核心增强点。

### 第三层：动作层

这一层的目标是“真的去做动作”。

包括：

- 点击
- 双击
- 输入文本
- 滚动
- 快捷键
- 窗口切换

但动作层必须和观察层形成闭环，也就是：

- 动作之后要重新观察
- 确认页面或桌面状态是否发生了预期变化

## 六、网页场景和桌面场景要分开设计

这是整套方案中非常重要的一条原则。

### 1. 网页场景

网页的优先策略应当是：

- 先按页面结构找
- 再按无障碍信息找
- 再按按钮名称、输入框名称、可见文字找
- 最后才退回到截图视觉定位

原因是：

- 网页本身通常有更稳定、更精确、更低成本的元素信息
- 如果网页里能直接拿到按钮、输入框、菜单、链接的结构信息，就没有必要先截图再猜坐标

所以网页的视觉定位更多是“兜底能力”，不是主路径。

适合使用视觉定位兜底的网页场景包括：

- Canvas 页面
- 图片化界面
- 远程桌面页面
- 游戏页面
- 页面结构严重混乱、无可访问性信息时

### 2. 桌面场景

桌面场景没有统一的 DOM 或结构树可以直接用，因此更需要视觉定位能力。

桌面场景建议优先建设：

- 截图后文字定位
- 截图后候选区域定位
- 操作后的二次确认

桌面场景里，视觉定位是主路径，不是兜底。

## 七、建议的产品形态

从产品能力角度，建议把这套能力设计成几类清晰的“动作前能力”。

### 1. 找文字

让 Agent 能说：

- “我已经在屏幕中找到‘登录’按钮”
- “我找到两个‘确定’，优先选择右下角那个”
- “我找到了包含‘允许访问’的系统弹窗”

这是最容易落地、价值最高的一步。

### 2. 找目标

让 Agent 能说：

- “我找到了右上角关闭按钮”
- “我找到了左侧导航栏中的设置入口”
- “我找到了手机号输入框”

这一步比“找文字”更难，因为它不仅需要 OCR，还需要结合视觉理解。

### 3. 找到后确认

让 Agent 能说：

- “我认为这个区域就是你要的目标，置信度高”
- “我找到了候选项，但还不够确定，建议先确认”

这一步很重要，因为它决定了系统是不是会乱点。

### 4. 点完再确认

让 Agent 能说：

- “点击后页面已进入下一步”
- “点击后未出现预期变化，我将重新定位”

没有这个环节，系统在真实任务中会非常不稳定。

## 八、推荐的分阶段实现路线

为了降低风险，建议分阶段推进。

### 第一阶段：最小可用版

目标：

- 让 Agent 能在截图中找到文字并返回位置

重点能力：

- 屏幕截图
- OCR 识别
- 返回文字框位置
- 根据关键词排序候选项

适合解决的问题：

- 找“登录”
- 找“确定”
- 找“允许”
- 找“下一步”
- 找窗口标题

这一阶段投入小、价值大、效果容易验证，建议优先做。

### 第二阶段：描述型定位

目标：

- 让 Agent 不只会找文字，还会找带描述的目标

重点能力：

- OCR 候选区域
- 局部放大复核
- 多模态视觉确认
- 输出更可信的目标区域

适合解决的问题：

- 找“右上角关闭按钮”
- 找“蓝色的确认按钮”
- 找“左侧第二个菜单”
- 找“系统弹窗里的允许按钮”

这一阶段是真正把“看懂”转为“会定位”。

### 第三阶段：定位与动作闭环

目标：

- 让 Agent 能自己做完整操作闭环

重点能力：

- 找目标
- 点击或输入
- 再次截图
- 判断是否成功
- 失败时重试或换策略

适合解决的问题：

- 登录流程
- 安装流程
- 设置修改流程
- 简单桌面操作任务

### 第四阶段：复杂界面增强

目标：

- 应对更复杂、更不规则的界面

重点能力：

- 图标定位
- 非文字按钮定位
- 混合视觉与结构化信息
- 更复杂的候选评分和重试策略

适合解决的问题：

- 图标工具栏
- 图片化系统界面
- Canvas 或远程桌面应用
- 图形化设置面板

## 九、我们建议优先做哪些能力

如果要控制投入并尽快看到效果，建议优先级如下：

### 优先级 1：屏幕截图中的文字定位

原因：

- 最容易做
- 最容易验证
- 能立即覆盖大量真实操作场景

这是整个方案里性价比最高的一步。

### 优先级 2：定位后的点击闭环

原因：

- 没有动作闭环，定位价值有限
- 真正落地必须证明“找到了也能用”

### 优先级 3：网页结构化定位与视觉兜底的统一调度

原因：

- 网页和桌面的最优策略不同
- 如果能统一调度，整体稳定性会明显提升

### 优先级 4：描述型视觉定位

原因：

- 这是面向复杂任务的关键能力
- 但比“找文字”更复杂，适合在后面做

## 十、我们不建议的方向

为了避免走弯路，以下方向不建议优先投入。

### 1. 不建议把所有网页点击都做成截图点击

原因：

- 不稳定
- 成本高
- 容易受主题、分辨率、动画、样式变化影响

网页优先还是应该走结构化定位。

### 2. 不建议一开始就追求“像人一样什么都能看懂”

原因：

- 范围太大
- 很难验证
- 容易陷入泛化问题

更务实的做法是先把“找文字按钮并点击”做好。

### 3. 不建议在现有系统外再维护一整套独立视觉理解系统

原因：

- 重复建设
- 成本高
- 后续调试和维护会非常复杂

更合理的方式是复用现有截图与图片理解能力，只新增“定位”这一层。

## 十一、最终建议

综合来看，最推荐的路线是：

- 继续复用现有截图和看图能力
- 新增“定位能力”作为中间层
- 网页优先结构化定位，视觉作为兜底
- 桌面优先视觉定位
- 所有操作都要求“动作后回看确认”

如果用一句话总结这次方案建议，就是：

- 不要做“纯看图点击”
- 要做“结构化定位 + 视觉定位 + 操作确认”的混合闭环

## 十二、建议的阶段目标总结

建议按以下顺序推进：

1. 先做截图中的文字定位
2. 再做定位后的点击与结果确认
3. 再做网页结构化定位和视觉兜底统一调度
4. 最后做复杂描述型定位和图标定位

这样推进的好处是：

- 价值明确
- 可逐步验证
- 可快速进入真实使用场景
- 技术风险更可控

## 十三、结论

`dgjh-2.0.0` 这个参考项目有启发作用，但它真正值得借鉴的是“候选区域定位和逐层缩小范围”的思路，而不是它的现成代码形态。

对 `Star Sanctuary` 来说，更好的方向不是把它原样接进来，而是：

- 在现有截图与看图能力之上，补出一层专门的视觉定位能力
- 用这层能力把“我知道图里有什么”升级为“我知道该点哪里”

这才是后续让 Agent 逐步具备“仿人类看屏幕操作能力”的正确路线。

## 十四、技术实现设计版

本节作为前文策划方案的技术衔接版本，用于指导后续研发设计、模块拆分、排期评估和验收定义。

虽然本节会比前文更偏实现，但仍然尽量保持“产品、策划、研发都能共同讨论”的表达方式，不直接展开代码实现细节。

## 十五、技术设计总原则

后续技术实现建议遵循以下原则：

- 不重做已有截图与图片理解能力
- 新增“定位层”而不是新增第二套“看图层”
- 网页与桌面采用不同的主路径
- 所有操作必须形成“观察 -> 定位 -> 执行 -> 回看确认”的闭环
- 第一阶段优先解决“找文字并点击”，不要一开始追求全能视觉代理

对应到本仓库现状，建议：

- 继续复用已有浏览器截图、桌面截图、图片理解能力
- 在 `belldandy-skills` 中新增视觉定位工具族
- 保持图片理解与视觉定位共用同一套结果缓存、状态目录和工具注册方式

## 十六、建议的能力分层

技术上建议把能力拆成四层，而不是把所有逻辑揉进一个“大视觉工具”。

### 1. 观察层

职责：

- 获取页面结构信息
- 获取截图
- 获取图片理解结果

建议复用现有能力：

- 浏览器结构观察
- 浏览器截图
- 桌面截图
- 图片理解

这一层的目标是“拿到足够多的信息”，不负责最终决定点哪里。

### 2. 候选生成层

职责：

- 根据目标描述找出若干候选区域

候选来源建议分三类：

- 结构化候选
  - 网页中的按钮、输入框、链接、菜单项
- OCR 候选
  - 截图里识别到的文字块、标题、按钮文案
- 视觉候选
  - 模型认为最像目标的区域

这一层的目标不是“一次命中”，而是“尽量不要漏候选”。

### 3. 候选复核层

职责：

- 对多个候选项做打分、确认、排序

建议综合使用：

- 文本相似度
- 位置特征
- 元素类型判断
- 多模态模型复核
- 历史操作上下文

这一层的目标是“把最值得点的那个排在前面”。

### 4. 动作闭环层

职责：

- 执行动作
- 观察动作结果
- 判断是否成功
- 决定是否重试

这是整个系统走向稳定可用的关键。

## 十七、场景分流设计

### 1. 网页场景主路径

网页优先使用结构化定位，建议顺序如下：

1. 优先使用页面结构定位
2. 其次使用可访问性语义定位
3. 再使用页面可见文本定位
4. 最后使用截图视觉定位兜底

原因：

- 精度更高
- 成本更低
- 对页面样式变化不敏感
- 更容易复现和调试

适合网页主路径的能力包括：

- 找按钮
- 找输入框
- 找链接
- 找表单项
- 找标签页
- 找弹窗操作项

### 2. 桌面场景主路径

桌面优先使用视觉定位，建议顺序如下：

1. 先截图
2. 先做 OCR 文字定位
3. 如果目标不是纯文字，再走视觉候选复核
4. 点击前可做一次局部确认
5. 点击后重新截图确认结果

原因：

- 桌面界面缺少统一结构树
- 截图是最稳定的信息来源
- OCR 对“按钮文案、弹窗文字、窗口标题”非常有效

## 十八、建议新增的能力模块

建议全部落在现有 `packages/belldandy-skills/src/builtin/multimedia/` 和 `packages/belldandy-skills/src/builtin/browser/` 体系中，保持和当前工具注册方式一致。

### 一、桌面视觉定位模块

建议新增：

- `screen-locate-shared`
  - 负责通用数据结构、候选模型、评分模型

- `screen-locate-ocr`
  - 负责截图文字检测、OCR 文本框提取、文字候选整理

- `screen-locate-target`
  - 负责候选筛选、局部放大复核、输出最终定位结果

- `screen-locate-verify`
  - 负责点击前确认、点击后确认、局部区域复查

### 二、网页混合定位模块

建议新增：

- `page-locate-target`
  - 统一网页内的结构化定位和视觉兜底

- `page-locate-fallback`
  - 当 DOM / 可访问性定位失败时，调用截图和视觉候选流程

### 三、执行闭环模块

建议新增：

- `action-verify-shared`
  - 统一处理动作后的回看、确认、重试策略

这个模块不一定一开始单独抽出，但长期建议独立，避免点击、输入、滚动各自重复实现验证逻辑。

## 十九、建议新增的工具能力

为了兼顾可用性和演进空间，建议先从小而明确的工具开始，而不是直接设计一个万能视觉 Agent 工具。

### 第一批建议新增工具

#### 1. `screen_locate_text`

用途：

- 在桌面、窗口或区域截图中查找指定文本并返回位置

适用：

- 找“登录”
- 找“确定”
- 找“保存”
- 找“允许”
- 找窗口标题

输出建议包含：

- 是否找到
- 命中的文字
- 候选数量
- 最佳区域坐标
- 点击中心点
- 置信度
- 证据摘要

这是建议最先落地的工具。

#### 2. `screen_locate_target`

用途：

- 根据描述查找某个视觉目标并返回位置

适用：

- 找“右上角关闭按钮”
- 找“蓝色继续按钮”
- 找“左边的设置菜单”

它的能力会依赖：

- OCR 候选
- 多模态模型对候选区域复核

建议放在第二阶段实现。

#### 3. `screen_verify_target`

用途：

- 对某个已知区域做确认

适用：

- 点击前确认是不是目标
- 点击后确认页面是否变化
- 排除误点风险

这个工具对于稳定性很重要。

#### 4. `page_locate_target`

用途：

- 在网页场景下统一执行结构化定位和视觉兜底

适用：

- 优先找结构化元素
- 结构化失败后再用截图辅助

这是网页和桌面策略分流的核心入口。

### 第二批建议新增工具

在第一批稳定后，再考虑新增：

- `screen_click_target`
- `screen_type_into_target`
- `screen_scroll_to_target`
- `page_click_target`

这些工具的本质是“定位 + 动作 + 回看确认”的组合能力。

不建议一开始就把它们全部做出来，建议先让“定位工具”单独成熟。

## 二十、建议的输入输出形态

为了便于后续 Agent 编排、日志追踪和前端展示，建议所有定位工具尽量统一结果结构。

### 输入建议统一包含

- 目标描述
- 目标类型
- 截图来源
- 搜索范围
- 是否允许视觉兜底
- 是否要求点击前确认

### 输出建议统一包含

- `found`
- `locatorType`
  - 结构化 / OCR / 视觉 / 混合
- `bbox`
- `center`
- `confidence`
- `matchedText`
- `matchedDescription`
- `candidateCount`
- `evidence`
- `nextActionHint`

这样做的价值在于：

- Agent 更容易做后续决策
- 日志更容易复盘
- WebChat 更容易展示“Agent 为什么点这里”

## 二十一、候选定位的核心流程建议

### 桌面文字定位建议流程

建议采用以下流程：

1. 先截图
2. 对整张图进行 OCR
3. 生成文字候选框
4. 按关键词、相似度、位置特征做初筛
5. 对前几个候选区域做局部放大
6. 重新 OCR 或局部视觉复核
7. 输出最佳区域

这就是 `dgjh-2.0.0` 最值得借鉴的部分，但建议在主仓库内重写，而不是直接挪用它的代码。

### 描述型定位建议流程

建议采用以下流程：

1. 先截图
2. 先用 OCR 找文本线索
3. 再把候选区域交给图片理解模型复核
4. 让模型回答“这些候选里哪个最像目标”
5. 输出最可信区域

这样做的好处是：

- 不会把整张大图都交给模型反复猜
- 成本更可控
- 定位结果更稳定

## 二十二、建议的评分策略

定位结果建议不是靠单一规则决定，而是组合评分。

建议综合以下几类分数：

- 文字匹配分
- 模糊匹配分
- 位置偏好分
- 元素类型分
- 视觉复核分
- 历史成功分

例如：

- 文字完全命中“登录”分高
- 靠近常见操作区的按钮可以略加权
- 被模型复核认为“很像目标”的候选再加分
- 历史上多次成功的定位模式可以加权

最终输出给 Agent 的不应该只是“找到”，而应该是：

- 找到了哪个候选
- 为什么优先选它
- 可信度大概有多高

## 二十三、动作后的闭环建议

这一部分必须单独强调，因为它决定系统能不能进入真实任务。

建议所有基于视觉定位的操作，都默认遵循以下闭环：

1. 观察当前状态
2. 定位目标
3. 执行动作
4. 再次观察
5. 判断是否成功
6. 成功则继续，失败则重试或换策略

### 成功判定方式建议

可以优先判断：

- 目标是否消失或状态变化
- 是否进入新页面或新窗口
- 是否出现预期提示文案
- 是否出现新的输入区域
- 是否出现错误信息

### 失败后的处理建议

失败后建议按层级处理：

- 先重拍当前区域
- 再重定位目标
- 再换第二候选
- 最后再考虑换策略或请求用户确认

## 二十四、与现有能力的对接建议

建议在现有基础上这样衔接：

### 1. 与截图能力对接

- 桌面场景复用现有 `screen_capture`
- 浏览器场景复用现有 `browserScreenshotTool`
- 不新增重复截图工具

### 2. 与图片理解能力对接

- 复用现有 `image_understand`
- 用于候选复核、局部确认、动作后变化确认
- 不新增第二套独立视觉理解模型链路

### 3. 与浏览器能力对接

- 浏览器优先沿用现有结构化页面工具
- 只有结构化失效时才调截图视觉定位

### 4. 与工具注册体系对接

- 继续在 `belldandy-skills` 工具体系中注册
- 保持和现有 `image_understand`、`screen_capture` 一致的 contract 风格
- 方便后续在 WebChat 和 Gateway 统一暴露

## 二十五、建议的分阶段研发顺序

### 第一阶段：文字定位 MVP

目标：

- 做出 `screen_locate_text`

范围：

- 只处理截图中的文字类目标
- 先支持桌面、窗口、区域截图
- 输出 bbox、center、confidence

不做：

- 图标定位
- 复杂描述型定位
- 自动点击

验收重点：

- 能找到按钮文案
- 能找到窗口标题
- 候选排序基本合理

### 第二阶段：点击闭环 MVP

目标：

- 做出“找文字后点击并验证”

范围：

- 定位目标
- 触发点击
- 截图回看
- 判断是否成功

验收重点：

- 至少能稳定完成若干固定流程
- 点击失败能触发重试或次优候选

### 第三阶段：描述型定位 MVP

目标：

- 做出 `screen_locate_target`

范围：

- 支持“右上角按钮”“左侧菜单”“蓝色按钮”这类描述
- 引入局部区域视觉复核

验收重点：

- 在非纯文字场景下有明显提升
- 不明显增加误点率

### 第四阶段：网页统一调度版

目标：

- 做出 `page_locate_target`

范围：

- 先结构化定位
- 结构化失败再截图定位
- 返回统一结果结构

验收重点：

- 网页元素定位稳定性提升
- 视觉兜底只在必要时触发

## 二十六、测试与验收建议

建议从一开始就把验收标准分成三层。

### 1. 单点能力测试

验证：

- OCR 结果是否能输出稳定文本框
- 定位工具是否能返回正确区域
- 置信度是否基本合理

### 2. 流程级测试

验证：

- 找文字 -> 点击 -> 回看 是否闭环
- 常见固定流程是否能跑通

### 3. 真实任务测试

验证：

- 在真实网页或桌面软件里是否能重复完成任务
- 是否存在误点、漏点、点错后无法恢复

建议优先选这几类任务作为首批验收场景：

- 登录弹窗确认
- 安装下一步流程
- 设置项开关切换
- 简单桌面窗口操作

## 二十七、风险与边界

需要提前明确，这套能力不是“一步到位万能视觉 Agent”，它有边界。

### 主要风险

- 复杂界面中文字识别不稳定
- 纯图标按钮没有文字线索时难度上升
- 分辨率、缩放、主题变化会影响定位稳定性
- 动画和异步加载会影响点击时机

### 控制方式

- 第一阶段只做文字目标
- 优先做确定性高的任务
- 所有点击都要求回看确认
- 需要时要求 Agent 主动说明不确定性

## 二十八、最终技术建议

从工程落地角度，最推荐的方案不是：

- 再做一个独立“万能视觉 Agent 模块”

而是：

- 复用现有截图与看图能力
- 新增统一的“定位层”
- 新增统一的“动作后确认层”
- 让网页走结构化优先、桌面走视觉优先

可以用一句话概括这份技术方案：

- 把“截图理解”升级成“截图理解 + 可执行定位 + 动作闭环”

这将是 `Star Sanctuary` 走向“仿人类看屏幕操作能力”的最稳妥、最可扩展、也最适合逐步落地的路线。
