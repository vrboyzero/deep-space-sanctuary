# 多代理策划案编写工作流方案

## 1. 结论摘要

结论先说：

- 本方案应明确定位为：**基于 Star Sanctuary 指挥模式（Commander Governance）的游戏策划案多 Agent 工作流**，而不是普通文档写作流程。
- 核心目标不是“尽快生成一篇文案”，而是把用户的想法、草稿、纪要、竞品参考或配置草案，转化为**结构标准化、逻辑清晰、可评审、可开发、可追踪、可归档**的正式游戏策划案。
- 推荐采用“**Commander 主控 + 多专业 Agent 并行 lane + 强制大纲确认 + review / rework / approval 闭环**”的治理模式。
- 在大纲、正文、美术资源清单等关键节点，Agent 在开始制作前应先读取对应模板；模板应支持用户在指定路径下覆盖、替换与调优。
- 主流程建议固定为：**输入识别 → 需求拆解 → 研究与补证 → 方向分析 → 大纲生成与确认 → 正文编写 → 专项拆解补全 → 多视角审查 → 修订成稿 → 终审批准 → 终稿归档**。
- 相比上一版通用流程，本版进一步纳入以下能力：
  - 标准策划案结构
  - 版本记录与待确认事项
  - 配置表、美术资源、埋点、边界条件、渠道差异、风控设计
  - 详细数值平衡推演
  - UI 原型与视觉稿生产
  - 程序技术方案细化
  - 上线排期、资源排期与跨部门执行管理
  - 长期记忆与历史方案复用

一句话定义：

**让 Star Sanctuary 的 Commander 以多 Agent 治理方式，先拆解、再确认、后编写、再审查，最终交付一份真正可落地的游戏策划方案，而不是一篇“看起来完整”的 AI 文档。**

## 2. Goal 与适用范围

### 2.1 Goal

把用户的原始输入稳定转化为一份正式策划案，并确保它具备以下属性：

- 结构完整
- 目标明确
- 流程可检查
- 配置可拆解
- 协作可分发
- 评审可回溯
- 修改可留痕
- 终稿可归档

该流程的目标不是一次性生成“好看的正文”，而是按固定治理链路完成：

- 先把需求理解对
- 再把资料和前提补齐
- 再把方案方向收敛
- 再把大纲冻结
- 再把正文与专项清单补全
- 最后通过审查、返工与批准收口

### 2.2 适用范围

适用于：

- 新玩法策划
- 活动策划
- 系统功能策划
- 版本模块策划
- 现有设计的迭代改版方案
- 详细数值平衡推演
- UI 原型与视觉稿生产
- 程序技术方案细化
- 上线排期、资源排期与跨部门执行管理

输入来源可包括：

- 一句话功能想法
- 初版策划草稿
- 会议纪要
- 竞品参考
- 活动规则
- 配置表草稿
- 历史方案
- 截图或界面描述

可覆盖的任务类型包括：

- 新功能策划案
- 旧方案优化
- 活动方案撰写
- 系统规则补全
- 配置表整理
- 埋点需求整理
- 美术需求拆解
- 方案评审检查

### 2.3 输出边界

本方案覆盖的是“策划案编写与审查工作流”的全链路治理，不等于：

- 替代最终业务负责人拍板
- 替代研发排期系统或项目管理系统
- 自动承诺数值、产能或上线结果一定正确

对于高不确定项，本流程要求：

- 明确标成“待确认”
- 记录影响范围
- 在终稿或评审结论中保留未决项

## 3. 设计前提：基于 Star Sanctuary 指挥模式

### 3.1 基本定位

本工作流默认运行在 Star Sanctuary 的**指挥模式**下，即：

- `governanceMode=commander`
- 由内建或自定义的 `commander` Agent 负责主控编排
- 多个专业 Agent 以 delegated lanes 形式并行或串行完成专项任务
- 最终通过 fan-in review、acceptance gate、rework、approval 收口

### 3.2 与现有系统能力的对齐

当前仓库内已有的相关治理能力包括：

- 内建 `commander` / `verifier` worker profile
- `commander` 只开放只读、治理、浏览、记忆、会话编排等能力
- `commander` 对 `workspace-write / patch / command-exec` 存在硬拦截
- capability plan 已支持：
  - `governanceMode`
  - `commanderAgentId`
  - `preferredAgents`
  - `finalApprovalMode`
  - `reworkRevisionCount`
- 指挥模式运行时已支持在 goal run 侧生成：
  - `commander-plan.md`
  - `work-order/*.md`
  - `review-results/review-*.md`
- 已有 `goal_commander_decide`、acceptance gate 与 rework 语义

因此，本方案推荐继续**复用现有 Commander 治理链路**，而不是另起一套新的多 Agent runtime。

### 3.3 治理原则

这套工作流必须遵守以下治理原则：

- `Commander` 负责拆解、派发、收口、升级，不直接承担正文大面积生产
- 专业 Agent 分 lane 输出中间产物，避免所有能力混在一个 Agent 中
- 阶段切换依赖显式产物与审查结论，不依赖“模型感觉差不多了”
- 大纲确认是强制闸门，未确认前不进入完整正文生成
- review 结果必须进入 rework 或 accept 分支，不能只产生一堆意见后自然消失
- 任务期工作痕迹默认留在 runtime artifacts 中，不直接晋升为长期记忆

### 3.4 模板读取前提

对于关键节点，推荐沿用当前 Star Sanctuary 全局模板目录的统一管理思路。

建议的模板解析顺序为：

1. 当前任务或节点显式指定的 `templatePath`
2. 当前任务或节点显式指定的 `templateId`
3. `~/.star_sanctuary/experience-templates/game-design/` 下命中的项目 / 类型模板
4. `~/.star_sanctuary/experience-templates/game-design/general/` 下的通用模板
5. 若该节点模板为必需项，则阻断并等待用户处理；若为非必需项，则记录告警后使用最小骨架回退

建议与当前环境保持一致：

- 全局模板根目录：`~/.star_sanctuary/experience-templates/`
- 当前环境对应路径：`H:\.star_sanctuary\experience-templates\`

对本工作流，推荐在该目录体系下新增策划案模板子目录：

- `~/.star_sanctuary/experience-templates/game-design/`

说明：

- 本工作流的策划案模板**不建议**放在项目仓库 `docs/` 下管理。
- 项目内文档可以说明模板规范，但真正执行时读取的模板应来自 `.star_sanctuary` 全局模板目录。

模板一旦被解析，Commander 应把以下信息写入运行时治理产物：

- `templateId`
- `templatePath`
- `templateSource`
- `templateVersion` 或 `templateHash`
- `resolvedAt`

## 4. 需求说明映射结论

根据 [游戏策划案AI撰写助手需求说明.txt](E:/project/star-sanctuary/docs/游戏策划案AI撰写助手需求说明.txt)，本工作流需要解决的核心问题可归纳为 5 类：

1. 标准化问题  
策划案结构不统一，评审成本高。

2. 落地性问题  
AI 容易生成“看似完整”的文档，但缺流程、配置、边界、埋点、风控等关键落地内容。

3. 偏航问题  
多轮讨论后，方案容易偏离初始目标。

4. 追踪问题  
缺少版本记录、修改原因、待确认事项和影响范围，协作容易混乱。

5. 拆解问题  
程序、美术、数据、测试等协作方所需信息分散在正文里，不能直接执行。

因此，工作流设计上必须补齐以下强约束：

- 在正文前增加结构化拆解阶段
- 将大纲确认设为强制 gate
- 为专项内容配置独立 lanes
- 在审查阶段主动检查目的、玩家行为、边界、渠道兼容、经济与风控风险
- 在交付阶段附带变更记录、待确认事项和协作拆解清单

## 5. 核心角色与 Agent 分工

建议将 Agent 角色拆成“治理层 + 生产层 + 审查层 + 资产层”。

| Agent 角色 | 层级 | 主要职责 | 关键输出 |
| --- | --- | --- | --- |
| Commander Agent | 治理层 | 解析任务、选择模板、规划 lane、分发 work order、汇总结果、做 accept/rework/escalate 决策 | commander plan、模板绑定结果、阶段状态、收口决策 |
| Requirement Intake Agent | 生产层 | 识别输入类型、补问缺口、形成结构化需求卡 | 需求卡、待确认问题 |
| Research Agent | 生产层 | 收集竞品、案例、历史方案、规范与限制条件 | 研究资料包、事实依据列表 |
| Analysis Agent | 生产层 | 拆解目标、用户、场景、流程、经济、风险与方向方案 | 分析报告、推荐方向 |
| Outline Agent | 生产层 | 读取大纲模板后生成标准策划案大纲并补章节缺口 | 大纲、章节说明、缺漏项 |
| Draft Writer Agent | 生产层 | 读取正文模板后按确认的大纲撰写正文 | 初稿正文 |
| Config Agent | 生产层 | 生成配置表、字段解释、来源与公式说明 | 配置表清单 |
| UX / UI Agent | 生产层 | 产出界面结构、交互说明、文本原型、视觉稿需求描述 | 页面说明、交互规则、原型描述 |
| Economy / Balance Agent | 生产层 | 做数值目标、奖励、消耗、平衡推演 | 数值假设、平衡说明、风险提示 |
| Tech Spec Agent | 生产层 | 整理程序实现要点、状态流转、接口依赖、兼容规则 | 技术约束、实现注意事项 |
| Art Asset Agent | 生产层 | 读取美术资源模板后拆解资源、动效、尺寸、优先级 | 美术资源清单 |
| Data / Telemetry Agent | 生产层 | 整理埋点、漏斗、查询用途与关键指标 | 埋点清单、查询清单 |
| QA / Edge Case Agent | 生产层 | 整理异常路径、边界条件、测试关注点 | 边界条件清单、测试要点 |
| Delivery / PM Agent | 生产层 | 补上线排期、资源排期、跨部门协作项 | 排期建议、协作清单 |
| Review Panel Agents | 审查层 | 从玩法、商业化、落地、表达、风控等视角并行审查 | 审查意见、问题级别、返工建议 |
| Final Editor Agent | 审查层 / 生产层 | 合并意见、统一口径、完成终稿整理 | 修订稿、终稿、变更摘要 |
| Memory Curator Agent | 资产层 | 判定哪些项目知识适合进入长期记忆，哪些仅保留为任务期痕迹 | 记忆候选、过期建议、引用依据 |

说明：

- `Commander Agent` 是唯一主控，其他 Agent 不直接横向互相调度。
- 模板选择由 `Commander Agent` 负责绑定，具体模板读取由对应 lane Agent 在执行前完成。
- 同一节点默认只绑定一个主模板；如需换模板，应显式记录为新一轮版本或 rework。
- `Review Panel Agents` 至少建议拆 4 个视角：
  - 玩法与用户体验
  - 商业化与经济系统
  - 研发 / 美术 / 数据 / 测试落地
  - 风控 / 渠道 / 兼容性 / 运营风险
- `Memory Curator Agent` 不参与正文生产，只负责“哪些信息值得长期复用”的后处理判断。

## 6. 标准产物模型

为了避免“每轮都有输出，但无法收口”，建议固定阶段产物。

### 6.1 主文档产物

- 需求卡
- 研究资料包
- 分析报告
- 大纲
- 正文初稿
- 修订稿
- 终稿

### 6.2 专项附属产物

- 版本记录
- 配置表
- 美术资源清单
- 数据埋点与查询清单
- 边界条件清单
- 渠道差异与版本兼容说明
- 风控设计说明
- 待确认事项汇总
- 数值平衡推演说明
- UI 原型 / 视觉稿说明
- 技术方案细化说明
- 上线与资源排期建议
- 跨部门协作拆解清单

### 6.3 治理产物

在 Star Sanctuary 指挥模式下，推荐 runtime 侧至少产出：

- `commander-plan.md`
- `work-order/<lane>.md`
- `review-results/review-<lane or node>.md`

作用分别为：

- `commander-plan.md`
  - 记录目标、分工、当前阶段、收口标准、out-of-scope
- `work-order/*.md`
  - 记录每个专业 Agent 的任务边界、交付格式、验证提示
- `review-results/*.md`
  - 记录审查结论、acceptance gate 判断、返工原因和下一步建议

### 6.4 模板绑定产物

为了保证“读了哪个模板、为什么这么写”可追踪，建议为关键节点补充模板绑定产物。

建议新增：

- `template-bindings.json`
- 或等价的 `template-resolution.md`

至少记录：

- `nodeId` / `laneId`
- `stageId`
- `templateId`
- `templatePath`
- `templateSource`
  - `explicit_path`
  - `explicit_id`
  - `state_override`
  - `repo_default`
  - `fallback_skeleton`
- `required`
- `resolvedAt`
- `templateVersion` 或 `templateHash`

### 6.5 关键模板清单（建议）

结合当前流程，建议优先定义以下模板文件：

- `outline-template.md`
- `draft-template.md`
- `art-resource-template.md`
- `config-table-template.md`
- `telemetry-template.md`
- `edge-case-template.md`
- `risk-control-template.md`
- `tech-spec-template.md`
- `release-plan-template.md`
- `review-checklist-template.md`

其中至少以下 3 类建议作为关键模板：

- 大纲模板
- 正文模板
- 美术资源需求模板

## 7. 推荐工作流

本节给出推荐的主流程。该流程默认由 `Commander Agent` 编排。

### 7.1 总体阶段图

`S0 输入识别 → S1 需求拆解 → S2 研究与补证 → S3 方向分析 → S4 大纲生成 → Gate B 大纲确认 → S5 正文编写 → S6 专项拆解补全 → S7 多视角审查 → S8 修订成稿 → S9 终审批准 → S10 终稿归档`

### 7.2 阶段表

| 阶段 | 设置目的 | 主控 / 主 Agent | 核心动作 | 阶段产物 | 完成判定 |
| --- | --- | --- | --- | --- | --- |
| S0 输入识别 | 先识别任务类型，不直接开写 | Commander + Requirement Intake Agent | 判断输入属于新功能、旧案优化、活动方案、规则补全、配置表整理、埋点整理、美术拆解或方案评审，并记录是否存在显式模板偏好 | 输入分类结果、初始需求卡、模板偏好 | 任务类型明确 |
| S1 需求拆解 | 把模糊诉求转成结构化问题空间 | Requirement Intake Agent | 从目标、用户、场景、入口、流程、奖励、配置、界面、渠道、兼容、风控、埋点、待确认等维度拆解 | 结构化需求卡、待确认清单 | 关键缺口已标记，不再盲猜 |
| S2 研究与补证 | 给后续分析补事实依据 | Research Agent | 收集竞品、案例、历史方案、项目规则、已有模板与约束信息 | 研究资料包、依据列表 | 支撑方案讨论的证据足够 |
| S3 方向分析 | 把“想法”收敛成推荐方向 | Analysis Agent | 提炼功能目标、目标用户、用户价值、系统关系、量化目标、风险与备选方案，并输出推荐意见 | 分析报告、方向建议 | 有明确推荐方案与理由 |
| S4 大纲生成 | 在长文前先冻结结构 | Outline Agent | 先读取大纲模板，再按标准章节生成策划案大纲，补全版本记录、流程、交互、配置、埋点、风控、待确认等章节 | 大纲 v1、模板绑定记录 | 大纲完整且可评审 |
| Gate A 需求冻结 | 确认前提成立 | 人工 + Commander | 检查需求目标、范围、限制、待确认项是否可接受 | 需求冻结结论 | 允许进入大纲确认前的下一步 |
| Gate B 大纲确认 | 阻止错误结构进入正文 | 人工 + Commander | 审核大纲结构、章节顺序、缺漏点与写作边界 | 大纲确认结论 | 明确 accept 或 rework |
| S5 正文编写 | 生成标准策划案主体 | Draft Writer Agent | 先读取正文模板，再按确认后的大纲撰写完整正文，显式标记待确认项 | 正文初稿 v1、模板绑定记录 | 正文结构完整、可审查 |
| S6 专项拆解补全 | 补齐可开发、可协作信息 | Config / UX / Balance / Tech / Art / Data / QA / Delivery Agents | 各 lane 先读取对应专项模板，再并行补齐配置表、界面交互、数值说明、技术细化、美术清单、埋点、边界条件、排期与协作信息 | 专项清单包、模板绑定记录 | 文档具备跨职能可执行信息 |
| S7 多视角审查 | 主动暴露设计、经济、落地问题 | Review Panel Agents + Verifier | 先读取审查清单模板，再并行审查目的一致性、玩家行为、边界、风控、渠道差异、落地风险、表达问题 | 审查报告、must-fix / should-fix / defer 列表、模板绑定记录 | 关键问题被归类 |
| S8 修订成稿 | 合并意见并收敛版本 | Final Editor Agent | 根据审查结果修订正文与专项清单，补版本记录与变更摘要 | 修订稿 v2+ | must-fix 基本关闭 |
| S9 终审批准 | 做最终 accept / rework / escalate | Commander + 人工审批 | 基于 acceptance gate 与审查结果决定是否定版 | 终审结论、批准记录 | 可进入终稿或退回修订 |
| S10 终稿归档 | 输出最终交付与后续复用资产 | Final Editor + Memory Curator Agent | 生成终稿、变更摘要、协作影响说明，并判断哪些知识进入长期记忆 | 终稿、归档信息、记忆候选 | 交付完成且后续可追踪 |

### 7.3 模板读取节点与策略

基于当前流程，建议将模板分成“必需模板”和“推荐模板”两类。

### 7.4 模板路径、替换与回退方案

建议采用“显式指定 + 全局模板目录 + 通用回退”的三级机制。

推荐优先级：

1. 节点显式指定 `templatePath`
2. 节点显式指定 `templateId`
3. `~/.star_sanctuary/experience-templates/game-design/` 中命中的项目 / 类型模板
4. `~/.star_sanctuary/experience-templates/game-design/general/` 中的通用模板
5. 若节点为必需模板且仍未命中，则阻断并提示用户
6. 若节点为推荐模板且仍未命中，则回退到最小骨架并记录风险

推荐路径约定：

- 全局模板目录：`~/.star_sanctuary/experience-templates/game-design/`
- 当前环境建议路径：`H:\.star_sanctuary\experience-templates\game-design\`

推荐文件组织方式：

- 通用模板：
  - `~/.star_sanctuary/experience-templates/game-design/general/outline-template.md`
  - `~/.star_sanctuary/experience-templates/game-design/general/draft-template.md`
- 任务类型模板：
  - `~/.star_sanctuary/experience-templates/game-design/event/outline-template.md`
  - `~/.star_sanctuary/experience-templates/game-design/system/draft-template.md`
  - `~/.star_sanctuary/experience-templates/game-design/economy/config-table-template.md`

用户可通过以下方式更换模板：

- 直接替换 `~/.star_sanctuary/experience-templates/game-design/` 下的同名模板文件
- 在任务创建或 Commander plan 中显式指定 `templateId`
- 在特定节点显式指定 `templatePath`

推荐的回退规则：

- 先尝试任务类型模板
- 再回退到 `general`
- 对必需模板仍未命中时，不允许继续生成该节点产物
- 对推荐模板未命中时，允许继续，但必须在版本记录或审查结果中标明“本轮使用了 fallback skeleton”

## 10. 正文与专项内容标准

### 10.1 文档基础信息

至少包括：

- 文档名称
- 所属项目
- 功能模块
- 当前版本
- 创建人
- 更新人
- 更新时间
- 文档状态

文档状态建议遵循：

`草稿中 → 待评审 → 评审修改中 → 待开发 → 开发中 → 已上线 → 已归档 → 已废弃`

### 10.2 版本变更记录

每次修改必须记录：

- 版本号
- 修改时间
- 修改人
- 修改内容
- 修改原因
- 影响范围

建议对关键版本额外记录：

- 使用的关键模板 `templateId`
- 模板来源路径 `templatePath`
- 是否发生模板切换
- 模板切换带来的结构或字段变化

### 10.3 功能目标

每个功能至少绑定一个目标：

- 留存
- 收入
- 活跃
- 体验
- 转化
- 回流
- 消耗
- 社交

同时应说明：

- 目标用户是谁
- 预期影响是什么
- 与现有系统有什么关系
- 是否有量化目标

### 10.4 功能流程

必须覆盖完整用户路径：

`入口 → 触发条件 → 用户操作 → 系统反馈 → 奖励/结果 → 退出/结束`

多条件分支建议用表格或判断树表达。

### 10.5 界面与交互

至少包括：

- 页面列表
- 核心信息层级
- 按钮行为
- 状态反馈
- 弹窗规则
- 文本原型图

弹窗规则至少说明：

- 弹出时机
- 弹出频率
- 弹窗优先级
- 关闭方式
- 是否支持不再提醒
- 按钮跳转目标
- 异常处理方式

### 10.6 配置表

所有可配置项必须表格化，字段至少包括：

- 字段名
- 字段类型
- 是否必填
- 控制端：前端 / 服务端 / 中台
- 字段说明
- 示例值
- 计算公式或来源

### 10.7 美术资源清单

如涉及界面、图标、动效、奖励展示，应输出：

- 资源名称
- 使用位置
- 资源类型
- 尺寸规格
- 动效要求
- 优先级
- 备注

### 10.8 数据埋点与查询清单

每个功能必须补充数据需求，至少包括：

- 曝光事件
- 点击事件
- 核心操作事件
- 转化漏斗事件
- 异常行为事件

每条埋点至少说明：

- 事件名
- 触发条件
- 上报参数
- 统计维度
- 查询用途

### 10.9 边界条件

必须覆盖：

- 网络异常
- 数据异常
- 重复点击
- 快速切换
- 强制退出
- 跨天 / 跨周 / 活动结束
- 多设备登录
- 并发操作

每个异常场景都要说明：

- 用户侧表现
- 系统侧处理

### 10.10 渠道差异与版本兼容

如果涉及多渠道或多平台，至少说明：

- APP 是否支持
- 小游戏是否支持
- 有实物渠道是否支持
- 无实物渠道是否支持
- 老版本用户是否可见
- 是否需要强制更新
- 老版本数据如何处理

### 10.11 风控设计

涉及以下内容时必须触发风控专项审查：

- 虚拟货币
- 实物奖励
- 兑换券
- 多乐币
- 付费权益
- 抽奖
- 排行榜
- 邀请裂变
- 回流奖励

风控部分至少说明：

- 可能被薅羊毛的路径
- 工作室批量操作风险
- 异常行为识别方式
- 发奖限制
- 权益回收规则
- 退款处理规则

### 10.12 待确认事项

所有不确定内容必须集中汇总到文档末尾，字段至少包括：

- 序号
- 待确认内容
- 影响范围
- 负责人
- 当前状态

## 11. 三个强制审查规则

这部分不是可选建议，而是工作流必须执行的审查规则。

### 11.1 目的校验

每个设计都必须检查是否服务核心目标。

示例：

- 如果目标是提升曝光，就不应该默认隐藏入口
- 如果目标是提升留存，就不应只设计一次性奖励
- 如果目标是提升付费，就必须说明转化路径与权益价值

### 11.2 玩家行为审视

每个涉及玩家操作的设计都必须检查：

- 玩家会不会用
- 玩家为什么用
- 玩家用了之后会怎样

也就是要明确：

- 路径是否过长
- 入口是否明显
- 操作是否符合习惯
- 驱动力来自奖励、成长、社交、炫耀、好奇还是任务压力
- 是否有正反馈和循环
- 是否会一次性体验后遗忘

### 11.3 强观点输出

AI 不能只列方案，必须给出推荐结论和不推荐理由。

输出口径建议为：

- 我建议采用方案 A，因为它更符合提升留存的目标，并且对现有经济系统冲击更小。
- 不建议采用方案 B，因为它虽然短期点击率更高，但会提高薅羊毛风险。

## 12. 关键闸门与 Commander 决策闭环

为了避免流程失控，建议固定 4 个关键闸门。

### Gate A：需求冻结

位置：

- `S1-S3` 后

作用：

- 确认目标、范围、输入类型、关键限制与待确认问题已可接受

建议默认决策：

- 不通过则 `rework`

### Gate B：大纲确认

位置：

- `S4` 后

作用：

- 确认结构对、章节全、缺口清楚

建议默认决策：

- 未确认前禁止进入完整正文生成

### Gate C：专项补全验收

位置：

- `S6-S7` 后

作用：

- 确认配置、埋点、美术、边界、风控、兼容性等落地信息已基本补齐

建议默认决策：

- 存在关键缺失则 `rework`

### Gate D：终稿批准

位置：

- `S9` 后

作用：

- 由用户或负责人明确决定终稿 accept / rework / escalate

与 Star Sanctuary 的对齐建议：

- Commander 汇总所有 lane 结果后，通过现有 acceptance gate 判断基础是否成立
- 再由 `goal_commander_decide` 显式做：
  - `accept`
  - `rework`
  - `escalate`

### 13.1 可进入长期记忆的信息

- 奖励体系

- `defer`
- 原因：当前文档阶段先定义工作流治理，不在本轮扩展长期记忆落库策略细节

## 16. 行为验收描述（轻量）

### 验收描述 1

Given 用户只提供一句模糊的功能想法  
When 指挥模式工作流完成 `S0-S4`  
Then 系统应输出结构化需求卡、待确认问题清单和标准大纲，而不是直接生成完整正文

### 验收描述 2

Given 用户已确认大纲  
When 工作流进入 `S5-S6`  
Then 产出的策划案除正文外，还应包含配置表、界面交互说明、埋点清单、边界条件和待确认事项

### 验收描述 3

Given 方案涉及奖励、货币、渠道差异或版本兼容  
When 工作流完成 `S7` 审查  
Then 审查结果中应显式指出风控风险、渠道差异和兼容性影响，而不是仅评价文案质量

### 验收描述 4

Given Commander 已汇总所有 lane 结果  
When 工作流进入 `S9`  
Then 必须形成 accept / rework / escalate 三选一的显式决策，而不是停留在“建议继续修改”的模糊状态

### 验收描述 5

Given 终稿准备归档  
When 工作流完成 `S10`  
Then 用户应同时拿到终稿正文、版本变更摘要、协作影响说明和待确认风险列表

### 验收描述 6

### 验收描述 7

Given 当前任务命中了“美术资源拆解 lane”，但 `art-resource-template.md` 缺失  
When 工作流进入 `S6`  
Then 系统应阻断该 lane 的正式输出，并提示用户补模板或显式指定替代模板，而不是生成自由格式的美术清单

## 17. 风险、失败模式与回滚

### 17.1 风险等级

**中偏高。**

原因：

- 流程阶段较多
- 专项 lane 较多
- 容易因过度并行导致上下文不一致
- 若缺少 gate，极易产出“格式很全但方向不对”的文档

### 17.2 主要失败模式

- Commander 任务拆解不准，lane 分派失真
- 用户自定义模板过旧或字段不兼容，导致产物结构漂移
- 同一阶段混用多个模板，导致章节和表头不一致
- 必需模板缺失但未阻断，最终输出难以落地
- 大纲阶段过早放行，导致正文返工过大
- 专项 lane 输出格式不统一，无法合并
- 审查只看表达，不看目标、经济、风控和边界
- 长期记忆引用旧规则污染新方案
- 用户把“待确认”误当成已定需求

### 17.3 最小回滚路径

若工作流跑偏，建议按以下顺序回退：

1. 回退到最近一次已确认的大纲版本
2. 保留研究资料与需求卡，不保留失真的正文扩写
3. 对问题 lane 单独 `rework`，不要整案重做
4. 必要时仅保留 Commander 的结构化结论，由人工重新指定方向
