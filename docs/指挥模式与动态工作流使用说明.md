# 指挥模式与动态工作流使用说明

本文件说明 Star Sanctuary 中两种任务编排机制——**指挥模式**与**动态工作流（Dynamic Workflows, DW）**——的使用方式、适用场景和配置方法。

- 面向普通用户：重点看"快速上手"和"内置工作流"
- 面向开发者：重点看"工作流脚本编写"和"API 参考"

关联设计文档：`docs/计划中/动态工作流-DW设计与技术方案.md`

---

## 1. 两种模式简介

### 1.1 指挥模式（现有）

贝露丹蒂在对话中实时决定把任务拆给哪些子 Agent 完成，像一个项目经理边思考边安排。

- **适用场景**：需要随机应变、显式拆分、并行审查的对话式任务
- **触发方式**：用户显式开启 chat commander，或在提示中明确要求"用指挥官 / 多 Agent / 并行审查"
- **并发上限**：默认 3（由 `BELLDANDY_SUB_AGENT_MAX_CONCURRENT` 控制）
- **局限**：步骤多时主模型上下文压力大；任务中断后必须从头再来；无硬性费用上限

### 1.2 动态工作流（DW）

给贝露丹蒂配一份**任务说明书（工作流脚本）**，说明书提前写清各步骤的执行顺序、并行方式和汇总逻辑，贝露丹蒂严格按说明书执行。

- **适用场景**：步骤固定、规模较大、需要可靠重跑的任务
- **触发方式**：通过 `run_workflow` 工具或 `workflow.*` RPC 显式触发
- **并发上限**：默认 6（由 `BELLDANDY_WORKFLOW_MAX_CONCURRENT` 控制）
- **优势**：断点续传、预算控制、进度透明、中间结果独立存档

### 1.3 两种模式的关系

两种模式**不冲突，可以同时开启**。工作流里的每个步骤，仍然可以利用指挥模式来调度一个小团队完成。

普通对话默认仍走主 Agent，不会自动升级为指挥模式或动态工作流。

## 2. 快速上手

### 2.1 使用内置工作流

Star Sanctuary 内置了两个开箱即用的工作流，无需编写脚本即可调用。

#### code-audit（代码安全审计）

并行扫描多个模块的安全隐患，交叉验证后汇总完整审计报告。

**参数：**

| 参数 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `targetDir` | string | `"src"` | 扫描目标目录 |
| `modules` | string[] | `["auth","api","storage","ui"]` | 要扫描的模块列表 |

**执行阶段：**

1. 并行扫描各模块的安全隐患
2. 交叉验证（质疑可能的误报）
3. 汇总完整安全审计报告

#### parallel-research（并行研究）

并行研究多个主题，汇总综合研究报告。

**参数：**

| 参数 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `topics` | string[] | **必填** | 要研究的主题列表 |
| `depth` | string | `"standard"` | 研究深度：`"quick"` / `"standard"` / `"deep"` |

**执行阶段：**

1. 并行研究多个主题
2. 汇总综合研究报告

### 2.2 通过对话触发

在对话中告诉贝露丹蒂使用工作流，她会通过 `run_workflow` 工具触发。例如：

> "用 code-audit 工作流扫描 src 目录下的 auth 和 api 模块"

> "用 parallel-research 工作流并行研究 RAG 系统和 AI Agent 框架，深度设为 deep"

### 2.3 通过 RPC 触发

客户端可通过 WebSocket 发送 `workflow.run` 请求：

```jsonc
{
  "type": "req",
  "method": "workflow.run",
  "params": {
    "workflowName": "code-audit",
    "sourceKind": "builtin",
    "args": { "targetDir": "src", "modules": ["auth", "api"] },
    "parentConversationId": "conv-001",
    "channel": "gateway"
  }
}
```

### 2.4 查看可用工作流

```jsonc
{ "type": "req", "method": "workflow.list", "params": {} }
```

返回 `fileWorkflows`（用户自定义脚本）和 `builtinWorkflows`（内置工作流）两个列表。

## 3. 工作流脚本编写

### 3.1 脚本位置

用户自定义脚本放在 `~/.star_sanctuary/workflows/` 目录下，支持 `.ts`、`.mjs`、`.js` 三种扩展名。

```
~/.star_sanctuary/workflows/
├── my-audit.ts          # TypeScript 脚本（自动编译）
├── my-research.mjs      # ES Module 脚本
└── my-batch.js          # CommonJS 脚本
```

### 3.2 脚本结构

每个脚本必须有一个 `default export` 的异步函数，接收 `WorkflowContext` 参数，返回字符串作为工作流输出。

```typescript
// ~/.star_sanctuary/workflows/my-workflow.ts
import type { WorkflowContext } from "@belldandy/agent";

export default async function myWorkflow(ctx: WorkflowContext): Promise<string> {
  const { targetDir = "src" } = ctx.args as { targetDir?: string };

  ctx.phase("阶段1：扫描");
  const result = await ctx.agent(`扫描 ${targetDir} 目录`, { callKey: "scan/0" });

  ctx.phase("阶段2：汇总");
  const summary = await ctx.agent(`汇总以下扫描结果：\n${result}`, { callKey: "summary/0" });

  return summary;
}
```

### 3.3 WorkflowContext API 参考

`WorkflowContext` 是工作流脚本的唯一编程接口，提供以下方法：

#### `agent(prompt, opts?)`

启动一个子 Agent 并等待结果。支持缓存命中跳过。

| 参数 | 说明 |
|---|---|
| `prompt` | 给子 Agent 的指令文本 |
| `opts.callKey` | 稳定调用键，用于断点续传缓存命中。循环中建议显式传入 |
| `opts.role` | Agent 角色（如 `"researcher"`、`"coder"`） |
| `opts.model` | 覆盖当前会话的全局模型设定 |
| `opts.allowedToolFamilies` | 允许的工具族 |
| `opts.maxToolRiskLevel` | 最大工具风险等级 |

```typescript
const result = await ctx.agent("扫描 auth 模块", { callKey: "scan/0/auth" });
```

#### `parallel(tasks)`

并发屏障：同时执行多个任务，等全部完成后返回结果数组。单个失败不影响其他任务。

```typescript
const results = await ctx.parallel([
  () => ctx.agent("扫描 auth", { callKey: "scan/0" }),
  () => ctx.agent("扫描 api", { callKey: "scan/1" }),
  () => ctx.agent("扫描 storage", { callKey: "scan/2" }),
]);

const okResults = results.filter(r => r.ok).map(r => r.value);
const errors = results.filter(r => !r.ok).map(r => r.error);
```

#### `parallelMap(items, mapper)`

带并发上限的数据项映射。每个 item 天然带 index，可稳定生成 `callKey`。

```typescript
const topics = ["RAG", "AI Agent", "Vector DB"];
const results = await ctx.parallelMap(
  topics,
  (topic, index) => ctx.agent(`研究主题：${topic}`, { callKey: `research/${index}` }),
);
```

#### `pipeline(items, ...stages)`

无屏障流水线：每个 item 独立流经所有 stage，处理快的 item 不必等慢的即可进入下一 stage。某个 item 在某 stage 失败后跳过后续 stage。

```typescript
const files = ["a.ts", "b.ts", "c.ts"];

const results = await ctx.pipeline(
  files,
  // stage 1：读取文件内容
  async (file) => await ctx.agent(`读取 ${file} 的内容`, { callKey: `read/${file}` }),
  // stage 2：分析问题
  async (content) => await ctx.agent(`分析以下代码的问题：\n${content}`, { callKey: `analyze` }),
  // stage 3：生成修复建议
  async (analysis) => await ctx.agent(`根据分析结果生成修复建议：\n${analysis}`, { callKey: `fix` }),
);

// results 是 WorkflowTaskResult[]，每个 item 独立成功或失败
const fixes = results.filter(r => r.ok).map(r => r.value);
```

**pipeline 与 parallelMap 的区别：**

| 特性 | `parallelMap` | `pipeline` |
|---|---|---|
| 屏障 | 有：全部 item 完成 stage 1 后才进 stage 2 | 无：item 独立流经各 stage |
| 吞吐 | 受最慢 item 影响 | 处理快的 item 可连续推进 |
| 适用 | 单步并行处理 | 多步流水线（如 读取→分析→修复） |

#### `workflow(nameOrRef, args?)`

嵌套调用另一个工作流并等待结果。深度限制 1 层（子工作流内部不能再嵌套）。当前只支持 builtin 模式。

```typescript
// 字符串形式（默认 builtin）
const childResult = await ctx.workflow("code-audit", { targetDir: "lib" });

// 对象形式
const childResult = await ctx.workflow({
  kind: "builtin",
  name: "parallel-research",
  args: { topics: ["RAG", "Vector DB"], depth: "deep" },
});
```

子工作流继承父级的并发上限（`maxConcurrent`），使用独立的 journal 和 budgetGuard。

#### `phase(title)`

标记当前阶段，推送到前端进度树。

```typescript
ctx.phase("阶段1：并行扫描");
// ... 执行阶段1 ...
ctx.phase("阶段2：交叉验证");
// ... 执行阶段2 ...
```

#### `log(msg)`

推送日志消息到前端。

```typescript
ctx.log(`正在扫描 ${modules.length} 个模块...`);
```

#### `args`

工作流启动时传入的静态参数（只读）。

```typescript
const { targetDir = "src", modules = ["auth", "api"] } = ctx.args as {
  targetDir?: string;
  modules?: string[];
};
```

### 3.4 WorkflowTaskResult 结构

`parallel`、`parallelMap`、`pipeline` 返回的结果数组中，每项是以下联合类型：

```typescript
// 成功
{
  ok: true;
  value: T;          // 结果值
  taskId: string;    // 任务标识
  cacheHit: boolean; // 是否命中缓存
  tokenCount?: number;
  durationMs?: number;
}

// 失败
{
  ok: false;
  error: string;       // 错误信息
  taskId: string;
  failureKind?: string;
  durationMs?: number;
}
```

## 4. 断点续传与缓存

### 4.1 基本原理

每次 `ctx.agent()` 调用都会计算一个稳定指纹（fingerprint），基于 `scriptHash + callKey + prompt + model + args` 等字段。指纹相同的调用会命中 Journal 缓存，直接返回旧结果，跳过实际 Agent 调用。

### 4.2 断点续传

工作流执行完毕后返回 `journalId`。如果工作流因中断、预算超限或手动停止而未完成，可以用相同的 `journalId` 重新运行，已完成的步骤会自动命中缓存跳过。

```jsonc
// 第一次运行（中途中断）
{
  "method": "workflow.run",
  "params": { "workflowName": "code-audit", "sourceKind": "builtin", "args": { "modules": ["auth", "api", "storage", "ui"] } }
}
// 返回 { journalId: "wf_abc123...", success: false, error: "budget exceeded" }

// 断点续传
{
  "method": "workflow.run",
  "params": {
    "workflowName": "code-audit",
    "sourceKind": "builtin",
    "args": { "modules": ["auth", "api", "storage", "ui"] },
    "resumeJournalId": "wf_abc123..."
  }
}
// 已完成的 agent() 调用命中缓存，只执行未完成的部分
```

**注意**：断点续传时 `args` 必须与首次运行一致，否则 fingerprint 不同不会命中缓存。

### 4.3 跨版本缓存迁移（P6a 新增）

当工作流脚本升级导致 `scriptHash` 变化时，默认情况下断点续传会因 fingerprint 不匹配而失效。跨版本迁移策略允许在 `callKey + prompt` 不变的前提下复用旧记录。

**迁移规则：**

| 字段变化 | 是否迁移 | 原因 |
|---|---|---|
| `scriptHash` 变化，`callKey + prompt` 不变 | 迁移 | 脚本内容修改但该步骤的输入和预期输出不变 |
| `callKey` 变化 | 不迁移 | 步骤身份改变，无法对应旧记录 |
| `prompt` 变化 | 不迁移 | Agent 输入改变，结果不可复用 |
| `workflowVersion` 变化 | 不迁移 | 语义可能不兼容 |
| 旧记录 `status != done` | 不迁移 | pending/error/skipped 不含可复用结果 |

**使用方式**：迁移自动在 `resumeJournalId` 存在时触发，无需额外配置。只需保证 `callKey` 和 `prompt` 在脚本升级后不变即可复用旧结果。

**典型场景**：脚本只修改了最终报告格式（如 `return` 语句），但中间各步骤的 `agent()` 调用 `callKey` 和 `prompt` 没变。resume 时中间步骤自动复用，只重新执行格式化逻辑。

## 5. 预算控制

### 5.1 预算参数

通过 `budget` 字段设置费用上限，超额时自动中止：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `maxTokens` | 环境变量 | 总 Token 上限 |
| `maxAgentCalls` | 50 | 最大 `agent()` 调用次数 |
| `maxRetries` | 2 | 单节点最大重试次数 |
| `maxWallClockMs` | 600000 (10分钟) | 单次工作流总耗时上限 |
| `maxConcurrent` | 6 | 并发上限（只能调低，不能超过环境变量硬上限） |
| `onExceeded` | `"abort"` | 超限行为：`"abort"`（中止）或 `"warn"`（警告继续） |

### 5.2 环境变量

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `BELLDANDY_WORKFLOW_MAX_CONCURRENT` | `6` | DW 并发上限硬顶 |
| `BELLDANDY_WORKFLOW_MAX_QUEUE_SIZE` | `20` | DW 等待队列上限 |
| `BELLDANDY_WORKFLOW_TIMEOUT_MS` | `600000` | DW 单次工作流总耗时上限 |
| `BELLDANDY_WORKFLOW_AGENT_TIMEOUT_MS` | `300000` | DW 单次 `agent()` 调用超时 |
| `BELLDANDY_WORKFLOW_MAX_AGENT_CALLS` | `50` | DW 单次工作流最大 `agent()` 调用次数 |
| `BELLDANDY_WORKFLOW_MAX_DEPTH` | `2` | DW orchestrator 最大深度 |

注意：`BELLDANDY_SUB_AGENT_MAX_CONCURRENT`（默认 3）是指挥模式的并发上限，动态工作流不触碰此变量。

### 5.3 设置预算示例

```jsonc
{
  "method": "workflow.run",
  "params": {
    "workflowName": "code-audit",
    "sourceKind": "builtin",
    "args": { "modules": ["auth", "api", "storage", "ui", "network", "config"] },
    "budget": {
      "maxAgentCalls": 20,
      "maxTokens": 500000,
      "maxConcurrent": 4
    }
  }
}
```

## 7. 安全注意事项

### 7.1 inline 脚本默认关闭

动态工作流默认不允许执行 Agent 生成的内联脚本（inline）。如需启用，必须显式设置 `allowInlineScript: true`，且脚本会经过白名单 AST 安全扫描，禁止 `import`、`require`、`eval`、`process`、`fs`、`child_process` 等危险操作。

### 7.2 沙盒边界

`WorkflowContext` 不暴露文件系统或网络原语，沙盒边界在 API 层实现。工作流脚本只能通过 `agent()` 调用子 Agent，不能直接读写文件或发起网络请求。

### 7.3 确定性要求

工作流脚本应保持确定性——避免使用 `Date.now()`、`Math.random()` 等非确定性 API。inline 脚本的安全扫描会直接禁止这些调用。`callKey` 和 `prompt` 的稳定性直接影响断点续传和跨版本迁移的正确性。

## 8. 完整脚本示例

### 8.1 多阶段代码审计（使用 parallel + pipeline）

```typescript
// ~/.star_sanctuary/workflows/multi-stage-audit.ts
import type { WorkflowContext } from "@belldandy/agent";

export default async function multiStageAudit(ctx: WorkflowContext): Promise<string> {
  const { targetDir = "src", modules = ["auth", "api", "storage"] } = ctx.args as {
    targetDir?: string;
    modules?: string[];
  };

  // 阶段1：并行扫描各模块
  ctx.phase("阶段1：并行扫描");
  ctx.log(`扫描 ${modules.length} 个模块：${modules.join(", ")}`);
  const scanResults = await ctx.parallel(
    modules.map((m, index) => () =>
      ctx.agent(
        `扫描 ${targetDir}/${m} 目录中的安全隐患，重点关注：\n` +
        `1. 输入验证缺失\n2. 权限检查遗漏\n3. 敏感信息泄露\n4. 注入风险\n` +
        `输出结构化的风险清单。`,
        { callKey: `scan/${index}/${m}` },
      ),
    ),
  );

  const validScans = scanResults.filter(r => r.ok).map(r => r.value);

  // 阶段2：用 pipeline 流水线处理每个扫描结果（验证→修复建议）
  ctx.phase("阶段2：验证与修复建议");
  const pipelineResults = await ctx.pipeline(
    validScans,
    // stage 1：验证扫描结果
    async (report) => await ctx.agent(
      `以下是安全扫描报告，请质疑其中可能的误报：\n\n${report}`,
      { callKey: "verify" },
    ),
    // stage 2：生成修复建议
    async (verification) => await ctx.agent(
      `根据以下验证结果，生成具体修复建议：\n\n${verification}`,
      { callKey: "fix" },
    ),
  );

  const fixes = pipelineResults.filter(r => r.ok).map(r => r.value);

  // 阶段3：汇总报告
  ctx.phase("阶段3：汇总报告");
  return await ctx.agent(
    `请根据以下修复建议，生成完整的安全审计报告：\n\n` +
    fixes.join("\n\n---\n\n"),
    { role: "researcher", callKey: "final/report" },
  );
}
```

### 8.2 嵌套调用子工作流（使用 workflow composition）

```typescript
// ~/.star_sanctuary/workflows/comprehensive-review.ts
import type { WorkflowContext } from "@belldandy/agent";

export default async function comprehensiveReview(ctx: WorkflowContext): Promise<string> {
  const { topics = [] } = ctx.args as { topics?: string[] };

  ctx.phase("阶段1：并行研究");
  // 嵌套调用 parallel-research 内置工作流
  const researchResult = await ctx.workflow("parallel-research", {
    topics,
    depth: "deep",
  });

  ctx.phase("阶段2：代码安全审计");
  // 嵌套调用 code-audit 内置工作流
  const auditResult = await ctx.workflow("code-audit", {
    targetDir: "src",
    modules: ["auth", "api"],
  });

  ctx.phase("阶段3：综合汇总");
  return await ctx.agent(
    `请综合以下研究结果和安全审计结果，生成全面的项目评估报告：\n\n` +
    `## 研究结果\n${researchResult}\n\n` +
    `## 安全审计\n${auditResult}`,
    { role: "researcher", callKey: "final/summary" },
  );
}
```

## 9. 常见问题

### Q: 工作流和指挥模式有什么区别？

工作流是"按说明书执行"，步骤和顺序提前写好，确定性高、可重跑、可断点续传。指挥模式是"边想边安排"，灵活但不可重跑、无断点续传。

### Q: 什么时候该用工作流，什么时候该用指挥模式？

- 步骤固定、规模较大、需要可靠重跑 → 工作流
- 需要随机应变、对话式协作 → 指挥模式
- 两者可以组合：工作流的某个步骤内部可以用指挥模式调度小团队

### Q: 工作流中断后怎么恢复？

用相同的 `journalId` 通过 `resumeJournalId` 参数重新运行。已完成的 `agent()` 调用会命中缓存自动跳过。

### Q: 脚本升级后旧缓存还能用吗？

如果 `callKey` 和 `prompt` 没变，跨版本迁移会自动复用旧结果。如果 `callKey` 或 `prompt` 变了，对应步骤需要重新执行。

### Q: 如何控制费用？

通过 `budget` 参数设置 `maxAgentCalls` 和 `maxTokens`。超额时工作流自动中止，已完成步骤保留在 Journal 中可供 resume。

### Q: pipeline 和 parallelMap 有什么区别？

`parallelMap` 有屏障——所有 item 完成 stage 1 后才一起进 stage 2。`pipeline` 无屏障——每个 item 独立流经所有 stage，处理快的不用等慢的。多步流水线用 `pipeline`，单步并行用 `parallelMap`。

### Q: workflow() 嵌套能嵌几层？

最多 1 层。父工作流可以调用子工作流，但子工作流内部不能再调用 `workflow()`。子工作流内部的 `agent()` 调用不受此限制。
