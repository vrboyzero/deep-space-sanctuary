# 沙箱配置方法与沙箱问题说明

本文档回答两件事：

1. `BELLDANDY_COMMAND_SANDBOX_BACKEND` / `BELLDANDY_COMMAND_SANDBOX_OCI_RUNTIME` / `BELLDANDY_COMMAND_SANDBOX_OCI_IMAGE` 这三个变量**到底该怎么配**，尤其是「本地镜像的 64 位 digest」怎么获得；
2. 这套沙箱在使用中暴露出来的**问题、成因与可选调整方案**，以及当前的处置决定。

- 适用版本：`v0.5.6` 及以后（判定逻辑由 `e0e83ef4` 引入，`v0.5.4` 起存在）。
- 相关代码：`packages/belldandy-skills/src/command-sandbox.ts`、`packages/belldandy-core/src/coding-runtime-preflight-doctor.ts`、`packages/belldandy-core/src/server-methods/system-doctor.ts`。
- 相关文档：`.env.example`（第 1234-1239 行）、`docs/开发使用说明.md`（第 435 / 490 / 492 行）。

---

## 1. 一分钟结论

| 你的选择 | 结果 |
| --- | --- |
| **不配置**（三个变量保持注释） | 设置页「系统检查」的 `Coding Runtime Preflight` 长期显示红叉（1 条阻塞）；**编码运行（coding run）里的 shell 命令会被拒绝**；日常 WebChat 聊天、普通对话里的 `run_command` **完全不受影响**（照常在宿主机执行）。 |
| **配置好** | 红叉转绿；编码运行里的 shell 在容器内执行（禁网、只读 rootfs、工作区按需只读/可写）。代价是**必须让 Docker Desktop 常驻**，否则该项会再次变红（原因码变为 `runtime_unavailable`）。 |

一句话：这是「能力未启用」的告示，不是故障。**不配不影响日常使用。**

配置失败时 Doctor 会直接点名是哪一个变量不合格，并把「取 digest」的两条命令一并给出；具体见 2.2 与 2.5。

## 2. 配置方法

### 2.1 三个变量的含义与硬约束

配置位置：`<stateDir>/.env.local`（本机为 `H:\.star_sanctuary\.env.local`）。该文件里本来就有这三行的注释模板，取消注释并替换取值即可。**实际只需要两行**——`_OCI_RUNTIME` 可以整行不写。

```ini
BELLDANDY_COMMAND_SANDBOX_BACKEND=oci
# 仅在用 podman 时才需要下面这行；省略即按 docker 处理
# BELLDANDY_COMMAND_SANDBOX_OCI_RUNTIME=docker
BELLDANDY_COMMAND_SANDBOX_OCI_IMAGE=node@sha256:<你本地镜像的 64 位 digest>
```

| 变量 | 允许取值 | 约束来源 |
| --- | --- | --- |
| `BELLDANDY_COMMAND_SANDBOX_BACKEND` | **必须精确等于 `oci`** | `command-sandbox.ts:153`；其它任何值（含 `docker`、`native`）都会被判为 `backend_value_invalid` |
| `BELLDANDY_COMMAND_SANDBOX_OCI_RUNTIME` | **可省略**（省略即 `docker`）；写了则必须是 `docker` 或 `podman` | `command-sandbox.ts:157-160` |
| `BELLDANDY_COMMAND_SANDBOX_OCI_IMAGE` | 必须匹配 `^[a-z0-9][a-z0-9._/-]*(?::tag)?@sha256:[a-f0-9]{64}$`，**即必须带 digest** | `command-sandbox.ts:11`（正则）、`:162-166` |

取值约束之外，还有两条**运行期**前提：

- **镜像必须已在本地**：沙箱用 `docker run --pull=never` 启动（`command-sandbox.ts:377`），运行时不会联网拉取；
- **镜像里必须有 `node`**：沙箱以 `--entrypoint <计划里的可执行文件>` 直接执行命令（`command-sandbox.ts:415-417`），JS/TS 编码任务默认跑 `node` / `npm`。

### 2.2 本地镜像的 64 位 digest 怎么获得

**主方法（推荐，读的是你本机镜像的真实身份）**

```powershell
# 1) 准备一个镜像（本项目的惯例是 node:22-bullseye）
docker pull node:22-bullseye

# 2) 读出它在本机的 RepoDigest —— 这就是要填进第三个变量的那一串
docker image inspect node:22-bullseye --format "{{index .RepoDigests 0}}"
```

输出形如：

```text
node@sha256:959fa6e5c12f4b08f58808f953c7a6a05f1f72629b57ef3a648b8809362fdad9
```

**把整串（含 `node@`）原样粘到 `BELLDANDY_COMMAND_SANDBOX_OCI_IMAGE=` 后面**，不要再加引号或空格。

**为什么不能只写 `node:22-bullseye`**

tag 是可变的。同一个 tag 在不同时间指向不同内容，实测数据：

| 时间 | `node:22-bullseye` 指向的 manifest-list digest |
| --- | --- |
| 2026-08（本项目历史记录） | `sha256:62f550497561d6285e10abd952730db89c905be990237eaf8744137929c72844` |
| 2026-09-13（本次实测） | `sha256:959fa6e5c12f4b08f58808f953c7a6a05f1f72629b57ef3a648b8809362fdad9` |

两个 digest 目前都还能从 registry 拉取（本次实测均返回 HTTP 200），但它们**不是同一个东西**。沙箱的全部承诺是「我执行的代码被关在一个内容确定的环境里」，用可变 tag 这个承诺就不成立，所以代码层面直接拒收不带 digest 的取值。**因此不要照抄任何文档（包括本文档）里的 digest**——用 2.2 节第 2 步从你自己本地镜像读出来的那个。

**可选方法（不拉取镜像，直接查 registry）**

```powershell
docker buildx imagetools inspect node:22-bullseye
```

输出里的 `Digest:` 一行即为该 tag 当前指向的 manifest-list digest。注意：这条命令会访问 registry（需要联网），且需要 buildx 插件；**本文档未实测该命令**（写文档时本机 Docker daemon 未启动）。

**镜像选型建议**

- 优先用**非 slim** 变体（如 `node:22-bullseye`）：它基于 buildpack-deps，通常自带 `git` 与常见构建工具，能覆盖大多数编码任务；`-slim` 变体只有最小运行时，跑 `git`、编译类命令会失败。
- Node 主版本建议与宿主机一致（本项目要求 Node ≥ 22.12.0），避免同一份代码在容器内外行为不同。

### 2.3 生效与验证

**改完必须重启 Gateway**：`.env.local` 只在启动时读取，不重启不生效。

**第一步：确认 Docker daemon 在跑**

```powershell
docker version --format "{{.Server.Version}}"
```

失败时会报 `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`——这就是 daemon 没启动，先去启动 Docker Desktop。

**第二步：跑 Doctor 看三项是否转绿**

```bat
cd /d H:\star-sanctuary-dist-v0.5.6
set BELLDANDY_STATE_DIR=H:\.star_sanctuary
node packages\belldandy-core\dist\bin\bdd.js doctor
```

配置前（本机实测输出）：

```text
- OCI Sandbox Configuration: unavailable (not_configured)
- OCI Runtime: unknown (configuration_unavailable)
- OCI Local Image: unknown (configuration_unavailable)
```

配置成功后应变为：

```text
- OCI Sandbox Configuration: available (configuration_valid)
- OCI Runtime: available (runtime_available)
- OCI Local Image: available (local_image_available)
```

并且该检查从 `✗ Coding Runtime Preflight` 转为 `✓`（`startup ready: yes`）。

**第三步（建议）：证明隔离真的生效**

「检查通过」只说明配置能被解析、daemon 与镜像都在，**不说明隔离正确**。源码检出里有会真起容器的自检脚本：

```bat
cd /d H:\deep-space-sanctuary-0.5.6\deep-space-sanctuary-main
corepack pnpm install
corepack pnpm verify:command-sandbox-oci
```

它会实际验证 rootfs 只读、workspace 只读/可写、`network none`、tmpfs 可写、资源上限与容器回收。

> 注意：该命令只能在**源码检出**里跑。release-light 压缩包按设计不含 `scripts/` 目录（开发脚本已被打包计划排除），在载荷里执行只会报 `Cannot find module ...\scripts\verify-command-sandbox-oci-fixture.mjs`。

### 2.4 沙箱实际的隔离参数

`buildOciSandboxInvocation`（`command-sandbox.ts:344-426`）生成的命令形如：

```text
docker run --init --pull=never --name <lease> --cidfile <file> \
  --label com.star-sanctuary.command-sandbox.lease=<leaseId> \
  --network none --read-only --cap-drop ALL \
  --security-opt no-new-privileges \
  --pids-limit 256 --memory 1g --cpus 2 \
  --tmpfs /tmp:rw,nosuid,nodev,noexec,size=64m \
  --mount type=bind,src=<工作区>,dst=/workspace[,readonly] \
  --workdir <容器内 cwd> \
  --entrypoint <计划里的可执行文件> <镜像@digest> <参数...>
```

默认资源上限：内存 `1024 MiB`、CPU `2`、PID `256`、tmpfs `64 MiB`（`command-sandbox.ts:428-435`）。

两点平台差异：

- **Windows 下不加 `--user`**：`resolveOciSandboxContainerUser` 对 `win32` 直接返回 `undefined`（`command-sandbox.ts:73`），容器按镜像默认用户（通常是 root）运行，写回工作区由 Docker Desktop 的挂载映射处理；Linux/macOS 下会带上宿主 uid/gid，保证绑定挂载写回的属主正确。
- `network none` 是硬编码的，没有「放行某个域名」之类的开关。

### 2.5 常见失败对照表

Doctor 只给出 `status (reasonCode)`。按下表定位（判定逻辑见 `coding-runtime-preflight-doctor.ts:188-244`，action 文案与取 digest 命令见同文件 `:168-186`）。v0.5.6 及更早只区分 `not_configured` 与笼统的 `invalid_configuration`，本文档 4.1 的改动把后者拆成了三条具体原因：

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| `unavailable (not_configured)` | 三个变量全空 | 属正常默认态；按第 2 节配置，或接受现状（见第 1 节） |
| `incompatible (backend_value_invalid)` | `BELLDANDY_COMMAND_SANDBOX_BACKEND` 有值但不等于 `oci`（例如写成了 `docker`、`native`） | 改成字面量 `oci` |
| `incompatible (runtime_unsupported)` | `BELLDANDY_COMMAND_SANDBOX_OCI_RUNTIME` 填了 `docker`/`podman` 之外的值 | 改成 `docker` 或 `podman`，或直接删掉该行（默认 `docker`） |
| `incompatible (image_digest_missing)` | `BELLDANDY_COMMAND_SANDBOX_OCI_IMAGE` 缺值、或没带 `@sha256:<64hex>`（例如只写了 `node:22-bullseye`） | 按 2.2 节取 digest 后填入完整引用 |
| `unavailable (runtime_unavailable)` | 配置合法，但 `docker version --format {{.Server.Version}}` 探测失败——通常是 Docker Desktop 没启动 | 启动 Docker Desktop 后重跑 Doctor；**不需要重启 Gateway**（探测是请求时执行的） |
| `unavailable (local_image_unavailable)` | daemon 可用，但 `docker image inspect <配置的 digest 引用>` 失败——镜像不在本地，或 digest 与本地镜像不一致 | 按 2.2 节重新 `docker pull` 并核对 digest |
| `unknown (configuration_unavailable)` | 派生项：配置解析失败时，运行时与本地镜像无法探测，固定为 `unknown` 且**不计入阻塞数** | 先修配置，这两项会自动变成 `available` |

### 2.6 回滚

把 `H:\.star_sanctuary\.env.local` 里这三行重新注释掉并重启 Gateway，即回到「未配置」默认态；若已经拉过镜像，可自行 `docker image rm` 清理。**回滚不涉及任何数据迁移**，也不会影响 WebChat 的日常使用。

## 3. 重要问题说明

以下问题是 2026-09-13 在「用户实测红叉 → 定位配置方法」过程中暴露的。第 1、2、3 条是**体验缺陷（均已于同日修复，见 5.3）**，第 4、5 条是**刻意设计的代价**，第 6 条是**配套工具的可达性问题**。

### 问题 1：配置不合格时不告诉你是哪个字段不合格（体验缺陷，已部分缓解）

- 现象（修复前）：漏 digest、backend 拼错这两种完全不同的错误，Doctor 全都只报 `invalid_configuration`；运行期拒绝命令时给的是同一句笼统文案（`command-sandbox.ts:101-102`：`Command execution is unavailable because this coding run requires an OS sandbox, but no usable sandbox backend is configured.`）。
- 原因：`resolveOciCommandSandboxConfig` 原本是「解析成功/失败」二值返回，三条约束的失败被压成了同一个 `undefined`，调用方只能映射成单一 `invalid_configuration`。
- **已解决（2026-09-13，方案 A）**：新增 `evaluateOciCommandSandboxConfig`（`command-sandbox.ts:145-168`）保留失败原因，Doctor 直接透传成 `backend_value_invalid` / `runtime_unsupported` / `image_digest_missing` 三个 `reasonCode`，并在 `setup.action` 里点名该改哪一个变量。旧接口 `resolveOciCommandSandboxConfig` 改为它的投影，判定行为逐字不变。
- 残留：运行期（真正执行命令那一刻）的 `error` 文案仍是统一的那一句，具体原因只在 `metadata.commandSandboxReason` 里；本次未改运行期文案，因为那属于命令结果契约，会影响既有断言。

### 问题 2：`BELLDANDY_COMMAND_SANDBOX_OCI_RUNTIME` 可以完全不写（体验缺陷）

- 现象：runtime 的默认值本来就是 `docker`（`command-sandbox.ts:157`），但文档与 `.env.example` 都把它列为必填项，给人「三个变量都不能少」的错觉。
- 影响：纯粹是心智负担，不写不会出错。
- **已解决（2026-09-13，方案 B）**：`.env.example` 与本文档 2.1 节都标明该变量可省略（只有用 podman 才需要写），示例里也已注释掉；`runtime_unsupported` 的修复建议同步写明「omit the variable to keep the docker default」。

### 问题 3：`--pull=never` 的操作代价没有被提前告知（体验缺陷）

- 现象：`--pull=never` 是硬编码的（`command-sandbox.ts:377`），配好变量但忘了 `docker pull`，会在**编码运行真正执行命令那一刻**才失败，而不是在配置或启动阶段。
- 原因：Doctor 的本地镜像探测只做 `image inspect`（`probeLocalOciImage`，`gopls-oci-admission.ts:303-313`），用途是「报告现状」；原来的 `setup.commands` 给的也是探测命令（`docker image inspect --format {{.Id}} <configured-digest-image>`），而不是取 digest 的命令。
- **已解决（2026-09-13，方案 A）**：`setup.commands` 改为可直接照抄的三条——`docker pull <image>:<tag>`、`docker image inspect <image>:<tag> --format "{{index .RepoDigests 0}}"`、`bdd doctor --json`；同时把关键命令**内联进 `setup.action`**，因为 CLI 文本输出与 WebChat 徽标都只显示 action，只在 commands 里给会变成悬空引用（真实 CLI 输出已核对）。
- 残留：Doctor 仍然只做只读探测，**不会替你拉镜像**（这是刻意的不变量，见问题 4），所以「先 pull 再配」这条顺序仍要用户自己保证。

### 问题 4：`--pull=never` 与 digest 固定是刻意的不变量（不是缺陷）

- 出处：`docs/计划中/SS达到9分以上竞品机制研究.md:267` 明确写着「不降低 `commandSandbox=required`……**不自动拉取 OCI image**」；`docs/project-map.md` 第 116 / 329 / 673 / 713 行反复记录「digest-pinned 与 `--pull=never`、network none、cap-drop、资源上限」这一组不变量（第 116 行以「不自动拉取镜像」表述）。
- 判断：允许 tag 或允许运行时拉取，会让「检查时的镜像」与「执行时的镜像」可能不是同一个，沙箱的隔离承诺随之失效。**建议保持不动。**

### 问题 5：编码运行没有「我接受风险、直接跑宿主机」的逃逸阀（刻意，但影响面需要说清）

- 现象：`buildCodingRunLaunchSpec` 对任何带 `codingRun` 的请求都无条件设置 `commandSandbox: "required"`（`query-runtime-message-send.ts:1101-1106`）；`gateway-main.ts:4348/4370` 的能力探测同样按 `required` 探测；`production-task-capability-owner.ts:91-96` 在请求了 command-exec 工具时把 `sandbox` 记为必需能力，一旦不可用即把整个运行判 `blocked`。
- 与普通聊天的区别：**普通对话不带 `codingRun`，因此不携带 `commandSandbox`，`run_command` 照常在宿主机执行**（`command-sandbox.ts:238`：只有 `required` 才拦截）。也就是说「宿主机执行」这条路并没有被关闭，只是不适用于编码运行。
- 判断：这是安全姿态决策——编码运行由模型发起、命令内容不可预知，fail-closed 是唯一有意义的默认。是否提供显式危险开关属于**策略变更，需要用户明确决策**（见 4.5 方案 E），不适合由实现方顺手放开。

### 问题 6：dist 载荷里跑不了隔离自检脚本（配套工具可达性）

- 现象：release-light 载荷保留了 154 条 npm scripts，其中 `verify:command-sandbox-oci` 指向 `scripts/verify-command-sandbox-oci-fixture.mjs`，但载荷按设计不含 `scripts/` 目录（打包计划已明确排除开发脚本），执行只会报 `Cannot find module`。
- 影响：用压缩包安装的用户即使配好了沙箱，也无法做隔离自检，只能跑 Doctor 的三项探测（证明力更弱）。
- 缓解：本文档 2.3 节已指明该命令需要源码检出。

## 4. 调整方案

风险等级说明：**低** = 纯报错/文档层，不改任何判定；**中** = 改判定取值面，需补测试；**高** = 改变安全语义，必须由用户明确决策。

### 4.1 方案 A（已完成，低风险）：让失败可定位

**状态：已实施（2026-09-13）。** 实施结果见 5.3；下面保留原始方案描述以便追溯。

- 内容：
  1. 把 `resolveOciCommandSandboxConfig` 的失败拆成具体原因（`backend_value_invalid` / `runtime_unsupported` / `image_digest_missing`），透传到 Doctor 的 `reasonCode`；
  2. 在 `coding-runtime-preflight-doctor.ts` 的 `setup.action` / `setup.commands` 里给出**取 digest 的命令**（`docker pull …` + `docker image inspect --format "{{index .RepoDigests 0}}" …`），而不是只给探测命令。
- 前置依赖：无。
- 工作量：改 1 个解析函数 + 1 个 Doctor 投影 + 2 处测试，约 100 行以内。
- 闭包边界：只改报错与提示文案，**不改任何放行/拒绝判定**；`oci` 字面量、digest 强制、`--pull=never` 全部保持。
- 预期效果：问题 1、3 的「无法自助定位」部分消除；用户不必再读源码或本文档第 2.1 节才能知道错在哪。

### 4.2 方案 B（已完成，低风险）：runtime 变量改为可省略

**状态：已实施（2026-09-13）。** 实施结果见 5.3。

- 内容：文档与 `.env.example` 明确标注 `_OCI_RUNTIME` 可省略（默认 `docker`），或在示例中直接注释掉该行。
- 前置依赖：无。工作量：改两段注释。
- 闭包边界：不动代码。
- 预期效果：消除问题 2 的心智负担。

### 4.3 方案 C（中风险）：提供「钉镜像」的小工具

- 内容：新增 `bdd sandbox pin <image-tag>`（或等价脚本）：`docker pull` → 读 `RepoDigests[0]` → 打印/写回 `.env.local` 对应行。
- 前置依赖：需要确定写回 `.env.local` 的边界（是否保持注释与顺序、是否要求用户确认）。
- 工作量：新增 1 个 CLI 子命令 + 测试，约 200-300 行。
- 闭包边界：只做「取 digest 并写入配置」，不自动启动容器、不改沙箱判定。
- 预期效果：把「电子身份证」这件事工具化，问题 1、3 的操作面基本消失。

### 4.4 方案 D（不建议）：放宽 digest 或允许运行时拉取

- 内容：接受可变 tag，或在执行时允许 `docker pull`。
- 为什么不建议：与既有不变量直接冲突（见问题 4 的出处），会让「检查时」与「执行时」的镜像可能不一致。
- 结论：**否决**。如确需放宽，属于安全姿态变更，应由用户明确决策，并同步修改 `docs/project-map.md`、`.env.example` 与相关计划文档中的既有结论。

### 4.5 方案 E（高风险，需用户明确决策）：为编码运行提供显式危险开关

- 内容：新增类似 `BELLDANDY_COMMAND_SANDBOX_ALLOW_HOST_EXECUTION=true` 的开关，显式打开后编码运行的 `commandSandbox: "required"` 降级为宿主机执行。
- 前置依赖：需要同步确认权限模型（`plan` / `accept-edits` / `confirm`）、审计日志字段与 WebChat 上的显式提示。
- 工作量：跨 `belldandy-core` + `belldandy-skills`，约 300-500 行 + 测试；**必须**默认关闭且带醒目文档。
- 闭包边界：仅影响编码运行的命令执行路径，不改变普通对话的既有行为。
- 预期效果：给「我知道风险、要跑宿主机」的场景一条明路；代价是引入一条可能被误开的高危通路。
- 当前决定：**不做**（用户 2026-09-13 明确选择「不配置、不改语义」）。
