## 1. 背景

本文最初编写时，仓库里两块能力都处在“有基础，但没闭环”的状态：

1. 梦境记忆已经独立落盘与组织，但还没有真正接入 `memory_search` 的默认索引入口，也没有 dream 专属检索语义。
2. 长期任务（goal）类型层已经支持 `archived` 状态，但服务端方法与 WebChat 入口没有补齐，因此用户无法完成归档，更无法安全删除。

本文目标不是一次性做“大重构”，而是给出两套**最小可落地设计**，并据此完成第一阶段落地。

## 3. 方案 A：梦境记忆接入 `memory_search` / 向量检索

### 3.1 目标

让 dream 相关内容能够：

1. 被默认索引；
2. 进入向量检索与关键词混合检索；
3. 具备独立 `memoryType` 或等价 dream 分类；
4. 在 `memory_search` 中可被过滤、可读、可解释。

### 3.2 非目标

本轮不包含：

- 重做 dream 生成逻辑；
- 改 dream 文件格式；
- 做复杂的 dream 专属召回器；
- 引入额外 dream 图谱、主题聚类、跨 dream 推理；
- 大改 `memory_search` 输出协议。

### 3.3 候选方案

#### 方案 A1：只补索引路径

做法：

- 在 `resolveMemoryIndexPaths()` 中把以下内容纳入默认入口：
  - `DREAM.md`
  - `dreams/`
  - 可选：`dream-runtime.json`

优点：

- diff 最小；
- 很快能让 dream 内容进入向量库。

缺点：

- dream 仍会落为 `memoryType = "other"`；
- 结果解释差，无法稳定过滤；
- 排序上无法与普通 memory 区分。

结论：

- 可作为临时补丁，不推荐作为正式落地方案。

#### 方案 A2：补索引路径 + 补 dream 专属分类

做法：

- 在默认索引入口中加入：
  - `DREAM.md`
  - `dreams/`
- 在 `MemoryIndexer.loadIndexableContent()` 中新增 dream 分类：
  - `DREAM.md -> dream_index`
  - `dreams/**/*.md -> dream_note`
  - `dream-runtime.json -> dream_runtime` 可选
- 在 `memory_search` 过滤层增加对 dream 类型的支持。

优点：

- 改动面仍小；
- 检索结果可解释；
- 可以在不破坏现有 memory 检索的前提下增加 dream 召回。

缺点：

- 需要扩展类型、过滤器、部分展示文案；
- 若把 `dream-runtime.json` 直接纳入召回，可能引入噪声。

结论：

- **推荐**。这是最小可落地且长期不会太别扭的方案。

#### 方案 A3：完全独立 dream_search

做法：

- 不改 `memory_search`，另建 `dream_search`。

优点：

- 语义清晰；
- 不影响现有 memory 检索。

缺点：

- 用户心智分裂；
- 代码重复；
- dream 与普通记忆无法统一召回和排序。

结论：

- 当前阶段不推荐。

### 3.4 推荐方案

推荐采用 **A2：补索引路径 + 补 dream 专属分类**。

原因：

- 与现有 `MemoryManager additionalRoots/additionalFiles` 机制天然兼容；
- 不需要改动梦境写入协议；
- 可以直接复用已有向量索引、rerank、结果展示链路；
- 既满足“能检索”，也满足“知道检索到的是 dream”。

### 3.5 最小设计

#### 3.5.1 索引入口调整

修改点：

- `packages/belldandy-core/src/memory-index-paths.ts`

建议默认增加：

- `additionalFiles`
  - `path.join(stateDir, "DREAM.md")`
- `additionalRoots`
  - `path.join(stateDir, "dreams")`

不建议本轮默认加入：

- `dream-runtime.json`

原因：

- `dream-runtime.json` 更像运行态聚合数据，适合诊断或派生，不适合作为面向模型的主检索语料；
- 直接纳入向量检索容易重复或污染召回。

#### 3.5.2 memoryType 扩展

建议把 `memoryType` 从当前：

- `core | daily | session | other`

扩展为：

- `core`
- `daily`
- `session`
- `dream_index`
- `dream_note`
- `other`

分类建议：

- `DREAM.md -> dream_index`
- `dreams/**/*.md -> dream_note`

意图：

- `dream_index` 表示梦境摘要导航页；
- `dream_note` 表示可被直接召回的具体梦境正文；
- 后续排序和过滤可以用类型区分，而不是继续堆路径判断。

#### 3.5.3 检索与过滤行为

建议在 `memory_search` 的 filter 中增加 dream 可见性，但保持向后兼容：

方案一：

- 直接允许 `memoryType` 传 dream 相关枚举。

方案二：

- 新增 `sourceKind` / `memoryDomain=dream|memory|session`。

推荐先做方案一，原因是改动小。

建议行为：

- 默认查询时，dream 内容与其他 memory 一起参与召回；
- 当用户明确按 type 过滤 dream 时，只返回 `dream_index` / `dream_note`；
- `dream_index` 排序权重低于具体 `dream_note`，避免目录页压住正文；
- 同一次结果里如果 `dream_index` 与某条 dream 正文高度重复，可在 rerank 后做轻量去重。

#### 3.5.4 结果展示

建议在结果元信息中显式展示：

- `memoryType`
- `sourcePath`
- 可读标签，如：
  - `Dream Index`
  - `Dream Note`

意图：

- 让用户和模型都知道“这是一条梦境记忆”，减少与普通 `MEMORY.md` 混淆。

### 3.6 实现影响面

建议最小涉及：

- `packages/belldandy-core/src/memory-index-paths.ts`
- `packages/belldandy-memory/src/indexer.ts`
- `packages/belldandy-memory/src/types.ts` 或对应 `memoryType` 定义位置
- `packages/belldandy-memory/src/manager.ts`
  - 若存在对 `memoryType` 的过滤校验、展示映射、统计聚合，需要同步
- `packages/belldandy-skills/src/builtin/memory.ts`
  - 更新工具描述与过滤参数说明

可选补充：

- 相关 inventory / source report / test 文件

### 3.7 风险级别

中低风险。

### 3.8 主要失败模式

1. dream 文件被索引，但过滤器未同步，导致工具层无法按 dream 类型检索。
2. `DREAM.md` 与 dream 正文重复召回，结果变“吵”。
3. 若误把 `dream-runtime.json` 纳入召回，可能把结构化运行态噪声送给模型。
4. memoryType 扩展后，旧的测试或前端展示假设仍把未知类型当错误处理。

### 3.9 可行性与前置依赖

可行性高。

前置依赖：

- 现有 memory 索引链路已可扩展 `additionalRoots/additionalFiles`
- 现有向量索引不依赖固定三种 memoryType 才能工作
- 需要补 2 类测试：
  - 索引分类测试
  - `memory_search` 过滤/展示测试

### 3.10 工作量评估

小到中。

预计拆分：

1. 路径入口补齐
2. 类型扩展与索引分类补齐
3. 工具过滤与展示补齐
4. 定向测试补齐

### 3.11 完成标准

满足以下行为即算完成：

- Given stateDir 下存在 `DREAM.md` 与 `dreams/*.md`
- When 执行 memory 索引
- Then dream 内容会进入索引并生成可检索 chunk

- Given 用户执行 `memory_search`
- When 查询命中某条梦境内容
- Then 结果会明确标记 dream 类型，而不是全部显示为 `other`

- Given 用户按 dream 类型过滤
- When 执行查询
- Then 只返回梦境相关内容

### 3.12 本轮结论

技术债决策：`fix_now`

原因：

- 这不是“锦上添花”，而是 dream 数据已经存在但无法被主检索能力稳定利用，属于明显闭环缺口；
- 方案可以小步落地，不需要先做大重构。

### 3.13 实施结果（已完成）

已落地内容：

1. 默认 memory 索引入口已加入：
   - `DREAM.md`
   - `dreams/`
2. `MemoryType` 已扩展为：
   - `core`
   - `daily`
   - `session`
   - `dream_index`
   - `dream_note`
   - `other`
3. `MemoryIndexer` 已实现分类：
   - `DREAM.md -> dream_index`
   - `dreams/**/*.md -> dream_note`
4. `memory_search` 已支持：
   - dream 类型过滤
   - `[Dream Index]` / `[Dream Note]` 结果标签
5. 相关定向测试已补齐并通过。

当前仍保留的后续优化：

1. 尚未对 `dream_index` 做专门降权。
2. 尚未对 dream 目录页与 dream 正文的重复结果做专门去重。

## 4. 方案 B：长期任务归档 / 删除

### 4.1 目标

补齐长期任务生命周期中的两个动作：

1. `archive`：软归档，默认从主视图隐藏，但保留内容与审计信息；
2. `delete`：硬删除，只允许对已归档 goal 执行，并要求明确确认。

### 4.2 非目标

本轮不包含：

- 完整的回收站系统；
- 支持已删除恢复；
- 复杂的级联保留策略编辑器；
- 大规模存储压缩与后台 GC；
- 多租户权限系统重构。

### 4.3 候选方案

#### 方案 B1：只做 `goal.delete`

优点：

- 接口最少。

缺点：

- 风险高；
- 用户容易误删；
- 没有“先隐藏、后确认”的缓冲层。

结论：

- 不推荐。

#### 方案 B2：只做 `goal.archive`

优点：

- 安全；
- 实现简单；
- 能解决“列表越来越长”的主要痛点。

缺点：

- 不能真正清理历史任务目录与 registry；
- 长期仍会累积数据。

结论：

- 可单独上线，但不是完整闭环。

#### 方案 B3：两阶段设计：`goal.archive` + `goal.delete`

做法：

- `goal.archive` 负责软归档；
- `goal.delete` 只允许对已归档 goal 执行；
- 前端默认只暴露 archive，delete 放到归档态详情里并二次确认。

优点：

- 安全与可清理兼顾；
- 复用现有 subtask archive 心智；
- 生命周期最清楚。

缺点：

- 比只做 archive 多一点实现量；
- 需要明确删除范围。

结论：

- **推荐**。

### 4.4 推荐方案

推荐采用 **B3：两阶段设计**。

原因：

- goal 已经有 `archived` 状态类型，补软归档最顺；
- delete 只有在 archived 之后才开放，可以显著降低误删风险；
- 符合“最小可落地”原则，不需要先引入回收站。

### 4.5 最小设计

#### 4.5.1 新增服务端方法

建议新增：

- `goal.archive`
- `goal.delete`

建议语义：

##### `goal.archive`

输入：

- `goalId`
- `reason?`

行为：

- 读取 goal
- 若不存在，返回 `not_found`
- 若已是 `archived`，返回当前 goal，保持幂等
- 若状态为 `executing` 或 `reviewing`，默认拒绝归档
  - 除非后续明确支持 `force`
- 更新：
  - `status = "archived"`
  - `updatedAt`
  - `pausedAt` 可补齐
  - `activeConversationId = undefined`
  - `activeNodeId = undefined`
- 将归档原因与时间写入 runtime/header 或 progress 记录
- 发出 goal 更新事件，供前端刷新

##### `goal.delete`

输入：

- `goalId`
- `confirmText?`

行为：

- 读取 goal
- 若状态不是 `archived`，拒绝删除
- 执行硬删除：
  - 从 goal registry 移除
  - 删除该 goal 的 runtime/doc/root 目录
  - 清理绑定关系和可安全清理的派生文件
- 发出删除事件，供前端从列表移除

#### 4.5.2 GoalManager 层设计

建议新增：

- `archiveGoal(goalId, input?)`
- `deleteGoal(goalId, input?)`

并在 `goals/registry.ts` 增加：

- `removeGoalRegistryEntry(stateDir, goalId)`

设计原则：

- `archive` 改状态，不删文件；
- `delete` 先校验状态，再删 registry，再删目录；
- 需要沿用现有 goal mutation lock，避免并发删除/恢复/暂停冲突。

#### 4.5.3 存储与删除边界

推荐删除范围：

- `goal.goalRoot`
- `goal.runtimeRoot`
- `goal.docRoot`
- registry entry
- 该 goal 的 runtime binding / handoff / progress / task graph / review / checkpoint 等 goal 专属文件

推荐暂不删除：

- 已经发布到全局 memory / method / skill 的产物
- 已独立成为其他系统资产的内容
- 通用会话总索引中与该 goal 相关但无法安全确定唯一归属的数据

原因：

- 最小方案应先保证“删除 goal 自身目录是安全的”；
- 涉及跨系统资产的级联删除，应单独设计保留策略。

#### 4.5.4 列表与 UI 行为

建议前端行为参考 subtask archive：

- 默认列表隐藏 archived goal
- 增加“显示归档”开关
- 活跃态详情：
  - 提供“归档”按钮
- 归档态详情：
  - 展示 archived badge
  - 展示 `archivedAt` / `archiveReason`
  - 提供“删除”按钮
  - 删除前弹出明确确认

顶部导航和主视图不新增新页面，优先复用现有长期任务面板。

#### 4.5.5 状态约束

建议最小状态规则：

- `planning / paused / blocked / completed -> archived`
- `executing / reviewing -> 默认不可 archived`
- `archived -> delete`

是否支持 `archived -> resume`：

- 本轮建议**不支持直接 resume**
- 如用户要继续，后续可单独设计 `goal.unarchive` 或“复制为新 goal”

原因：

- 先把生命周期收敛；
- 否则 archive 很容易退化成另一个 pause。

### 4.6 风险级别

归档：低风险  
删除：中风险

### 4.7 主要失败模式

1. registry 删了，但目录未删干净，形成悬挂数据。
2. 目录先删了，但 registry 未更新，导致列表里出现坏链接。
3. 删除时误删非本 goal 独占目录。
4. 前端没有“显示归档”开关，用户会误以为任务消失。
5. 仍在运行的 goal 被归档，导致会话绑定、事件流、UI 状态不同步。

### 4.8 可行性与前置依赖

可行性高。

前置依赖：

- goal 路径必须由 `resolveGoalPaths` 或 header 中现有路径字段稳定给出
- 需要补一个 registry remove helper
- 需要目标目录删除前做路径归属校验
- 需要 WebChat goal 列表支持 `includeArchived`

### 4.9 工作量评估

中等。

预计拆分：

1. server method + manager 方法补齐
2. registry remove helper
3. 安全删除实现
4. 前端归档显示/过滤/UI 操作补齐
5. 定向测试

### 4.10 完成标准

满足以下行为即算完成：

- Given 一个 `planning` 或 `completed` 的 goal
- When 用户执行 `goal.archive`
- Then goal 状态变为 `archived`，默认列表中隐藏，但在“显示归档”打开后可见

- Given 一个 `executing` 的 goal
- When 用户尝试归档
- Then 系统明确拒绝并说明原因

- Given 一个已归档 goal
- When 用户执行 `goal.delete`
- Then registry entry 被移除，goal 专属目录被删除，前端列表同步移除

- Given 一个未归档 goal
- When 用户执行 `goal.delete`
- Then 系统拒绝删除

### 4.11 建议的实现顺序

推荐分两步上线：

1. 第一步上线 `goal.archive`
   - 先解决列表膨胀与生命周期缺口
2. 第二步上线 `goal.delete`
   - 在归档态下补最终清理能力

这样做的意图：

- 先交付低风险价值；
- 再补高风险不可逆动作；
- 便于用户先验证 archive 心智是否符合预期。

### 4.12 本轮结论

技术债决策：`split_task`

原因：

- 归档本身应尽快补齐，属于明显缺口；
- 删除属于不可逆动作，虽然可以一并设计，但实现与验证建议拆成第二步。

## 6. 额外小任务

以下两项不属于前两大主题的主设计，但都已在现有实现上观察到明确的补强价值，且适合以小 diff 方式并行推进。

### 6.1 DeepSeek Auto 缺候选时的运行时兜底收口

状态：`done`

#### 背景

当前 DeepSeek 虚拟路由已经有两层保护：

- `models.list` 只有在 `flash` 和 `pro` 候选同时存在时才展示 `deepseek:auto / deepseek:flash / deepseek:pro`
- `resolveModelConfig()` 对未知 `modelRef` 会 fallback 到 `primary`

这意味着正常 UI 路径下通常不会直接报错，但仍存在一个边界：

- 若历史配置、残留会话或手工请求继续传入 `deepseek:auto`
- 且当前已没有完整的 `flash/pro` 候选
- `message.send` 这一层可能仍把虚拟 id 继续向下传，最后由 agent 侧“静默回退到 primary”

这不会立刻炸，但会带来两个问题：

1. 降级点不够前置，不利于诊断；
2. observability 可能显示虚拟路由 id，而不是真正落到的 `primary`。

#### 最小修补设计

建议在 `message.send` 路由决策后补一层显式收口：

- 当请求的是 `deepseek:auto / deepseek:flash / deepseek:pro`
- 且 `resolveDeepSeekTierRoute()` 未能解析出真实 `resolvedModelId`
- 则不要继续把虚拟 id 透传给 agent
- 直接在 `query-runtime-message-send.ts` 内将 `effectiveModelId` 收口为 `primary` 或 `undefined`

推荐同时保留 explainability：

- `deepseekRoute.routeMode = "deepseek_virtual"`
- `deepseekRoute.degraded = true`
- `deepseekRoute.reason = "deepseek_tier_candidates_incomplete"`
- 新增或沿用 evidence，明确是“候选缺失后显式回退到 primary”

#### 意图与效果

- 让降级发生在 core 路由层，而不是拖到 agent profile 解析层；
- 让 WebChat / token observability / 调试日志看到的“实际模型选择”更真实；
- 保持当前“不报错”的优点，同时去掉静默漂移。

#### 影响面

- `packages/belldandy-core/src/query-runtime-message-send.ts`
- `packages/belldandy-core/src/server.test.ts`

#### 风险级别

低风险。

原因：

- 本质是把已有的隐式 fallback 前移为显式 fallback；
- 不改变正常候选完整时的路由结果；
- 不影响非 DeepSeek provider。

#### 主要失败模式

1. route verdict 显示为 degraded，但最终 effectiveModelId 仍未与之同步；
2. 显式 `deepseek:pro` 缺失时，原本允许 fallback 到 `flash` 的逻辑被误伤；
3. policy disabled 路径被误改，导致本应 passthrough 的行为变化。

#### 完成标准

- Given 当前没有完整的 `deepseek-v4-flash` / `deepseek-v4-pro` 候选
- When 收到 `modelId = "deepseek:auto"` 的 `message.send`
- Then 请求不会报错，且会在 core 层显式降级到 `primary`

- Given 同样场景
- When 查看 token usage / route observability
- Then 可看到 degraded 原因，并且 effective model 不再停留在虚拟 id

#### 技术债决策

`fix_now`

#### 实施结果

已完成结果：

1. `message.send` 的 `effectiveModelId` 已在 core 层显式收口。
2. 当 DeepSeek 虚拟路由未能解析出真实候选时：
   - 非 policy-disabled 路径下不再继续透传 `deepseek:auto / deepseek:flash / deepseek:pro`
   - 若存在 `primaryModelConfig`，则显式回退为 `primary`
   - 若不存在 `primaryModelConfig`，则保持 `undefined`
3. `token.usage.deepseekRoute.effectiveModelId` 已与实际回退结果同步，不再停留在虚拟 id。
4. 已补定向回归测试，确认：
   - 正常候选完整时原有 `flash / pro` 分流未被破坏
   - 候选无法解析时会显式回退到 `primary`
   - `BELLDANDY_DEEPSEEK_ROUTE_POLICY_ENABLED=false` 时仍保持 passthrough

### 6.3 WebChat 操作面板增加“一键指挥模式”开关

状态：`done`

#### 背景

当前 Commander 相关运行时配置已经具备：

- `BELLDANDY_COMMANDER_MODE`
- `BELLDANDY_GOAL_EXECUTION_MODE`
- `BELLDANDY_GOAL_GOVERNANCE_MODE`

并且它们已接入 `config.update` 白名单与 hot reload。

但在实际使用中，这组设置仍藏在设置页深处；用户如果想把后续长期任务快速切到“指挥官治理 + 多智能体并行执行”，操作路径偏长，且容易漏改某一项。

#### 最小实现设计

在 WebChat 顶部“操作”面板中新增一个轻量开关卡片：

1. 标题：`指挥模式`
2. 说明文：用简洁文字说明“会把后续新任务切到指挥官治理与多智能体并行执行”
3. 开启时一键写入：
   - `BELLDANDY_COMMANDER_MODE=on`
   - `BELLDANDY_GOAL_EXECUTION_MODE=multi_agent_parallel`
   - `BELLDANDY_GOAL_GOVERNANCE_MODE=commander`
4. `BELLDANDY_COMMANDER_AGENT_ID` 不在该快捷开关里修改，继续沿用用户现有设置
5. 关闭时优先恢复“开启前的非指挥官设置”；若没有恢复快照，再保守回退到：
   - `BELLDANDY_COMMANDER_MODE=off`
   - `BELLDANDY_GOAL_EXECUTION_MODE=auto`
   - `BELLDANDY_GOAL_GOVERNANCE_MODE=auto`

#### 恢复策略

推荐在前端本地缓存开启前的三项旧值：

- `BELLDANDY_COMMANDER_MODE`
- `BELLDANDY_GOAL_EXECUTION_MODE`
- `BELLDANDY_GOAL_GOVERNANCE_MODE`

这样关闭时可以“回到用户原本状态”，而不是强行写死成某一种默认组合。

#### 重启与告知

根据现有实现方案文档，这组设置已经支持 hot reload：

- 保存后**不需要重启服务**
- 影响范围仅限“后续新的 capability planning / commander 决策”
- 不会追改历史已生成节点

因此本任务默认行为应是：

1. 切换成功后直接提示“无需重启”
2. 不自动调用 `system.restart`
3. 若服务端异常返回 `restartRequired=true`，再补一个异常提示，引导用户去设置页手动重启

#### 影响面

- `apps/web/public/index.html`
- `apps/web/public/styles.css`
- `apps/web/public/app/bootstrap/dom.js`
- `apps/web/public/app/features/settings-runtime.js`
- 新增一个小型 controller（建议独立文件）
- `apps/web/public/app/i18n/zh-CN.js`
- `apps/web/public/app/i18n/en-US.js`

#### 风险级别

低风险。

原因：

- 仅涉及已有配置项的快捷写入；
- 不改后端治理逻辑，只改 WebChat 入口；
- 不需要新增服务重启或迁移链路。

#### 主要失败模式

1. 开关状态与设置页字段不同步，造成认知混乱；
2. 关闭时没有恢复旧值，误把用户原本策略抹平；
3. 误触发重启路径，破坏“热更新即可生效”的预期。

#### 完成标准

- Given 用户打开 WebChat 顶部“操作”面板
- When 查看新增开关
- Then 能看到“指挥模式”入口与一行简洁说明文

- Given 当前是普通模式
- When 打开该开关
- Then 三项 Commander 相关设置会被一键切为推荐预设，且无需重启服务

- Given 用户曾通过该开关启用指挥模式
- When 再次关闭
- Then 会优先恢复开启前缓存的非指挥官设置

#### 技术债决策

`fix_now`
