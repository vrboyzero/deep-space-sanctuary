# 星辰功能优化需求分析与评估

## 1. 系统提示词聚焦提示功能（向量检索 + 辅助模型）

### 1.1 目标

解决长系统提示词时，主模型（Agent）注意力不足的问题。通过一个辅助模型 + 向量检索/语义匹配，在每次用户输入时检查 stateDir 下的 `AGENTS.md` 和 `SOUL.md`，提取与当前用户意图相关的精简内容，作为提示注入给主模型。

### 1.2 现状分析

**系统提示词加载流程**（已确认）：

```
stateDir 解析 (star-sanctuary-distribution/src/state-dir.ts:62-82)
  ↓
loadWorkspaceFiles(stateDir) → 加载 8 个文件
  (SOUL.md, IDENTITY.md, USER.md, AGENTS.md, TOOLS.md, MEMORY.md, BOOTSTRAP.md, HEARTBEAT.md)
  (belldandy-agent/src/workspace.ts:383-439)
  ↓
buildSystemPromptResult({ workspace, ... }) → 组装 SystemPromptSection[]
  优先级排序: AGENTS.md(P10) → SOUL.md(P20) → ... → 截断
  (belldandy-agent/src/system-prompt.ts:318-712)
  ↓
ToolEnabledAgent({ systemPrompt }) → run() → messages[0] = system prompt
  (belldandy-agent/src/tool-agent.ts:629-665)
```

**关键发现**：
- AGENTS.md 和 SOUL.md 已经作为 `SystemPromptSection` 被静态注入（优先级 10 和 20）
- 系统提示词组装支持 `maxChars` 截断（通过 `BELLDANDY_MAX_SYSTEM_PROMPT_CHARS`），低优先级 section 会被丢弃
- 已有注入开关：`BELLDANDY_INJECT_AGENTS`、`BELLDANDY_INJECT_SOUL`（默认 `true`）
- 系统提示词在 Gateway 启动时一次性构建并缓存到 `agentWorkspaceCache`
- 目前不存在任何"根据用户输入动态调整系统提示词"的机制

### 1.3 方案建议

**核心思路**：引入一个轻量的"提示词聚焦"环节，在 `agent.run()` 的 `before_agent_start` 钩子中执行。

**方案 A（推荐）：基于现有混合检索的语义匹配**

```
用户输入 → 分词/向量化 → 在 AGENTS.md + SOUL.md 中做语义搜索
  → 返回 top-K 相关段落 → 格式化为精简提示 → 作为 prompt delta 注入
```

- 复用已有的 `MemoryManager.search()` 混合检索能力（FTS5 + sqlite-vec + RRF 融合）
- 需要先将 AGENTS.md 和 SOUL.md 拆段存入 vector store（一次性索引）
- 命中段以 `system-prelude` delta 形式注入："当前输入匹配了以下系统约束：..."

**方案 B：辅助模型判断（更重）**

```
用户输入 → 辅助模型(lighter model) → 阅读 AGENTS.md + SOUL.md
  → 输出匹配的章节/规则要点 → 注入主模型 system prompt
```

- 每个请求增加一次辅助模型调用，延迟和 token 开销较大
- 辅助模型配置：可复用 `failoverClient` 中的轻量模型
- 适合 AGENTS.md/SOUL.md 非常长（>10K tokens）且主模型确实容易遗漏的场景

**推荐方案 A**，理由：
- 延迟低（纯 DB 查询，无需额外 LLM 调用）
- 复用现有基础设施
- 辅助模型方案可作为后续升级（当语义检索不够精确时）

### 1.4 实现要点

| 要点 | 说明 |
|------|------|
| 索引时机 | Gateway 启动时索引 AGENTS.md / SOUL.md 到独立的 vector table |
| 匹配粒度 | 按章节/段落分块，每个 chunk 200-400 tokens |
| 注入方式 | 作为 `AgentPromptDelta`（`deltaType: "system-prelude"`）注入，优先级介于 P0-P10 之间 |
| 配置开关 | `BELLDANDY_PROMPT_FOCUS_ENABLED`，默认 `true` |
| 匹配阈值 | 相似度 > 0.6 的段落才注入，避免噪音 |
| 注入上限 | 最多注入 3 条匹配段落，总长度不超过 600 tokens |

## 2. Methods 与 Skills 列表注入 Agent（类似工具调用）

### 2.1 问题背景

目前 methods 和 skills 通过以下方式暴露给 Agent：
- **Methods**：通过 `method_list`、`method_search`、`method_read`、`method_create` 四个工具
- **Skills**：通过 `skills_search`、`skills_list`、`skill_get` 三个工具 + 高优先级 skill 直接注入 system prompt

问题：Agent 不会主动调用 `method_list` / `skills_search`，除非用户明确要求使用某个 method/skill，或 SOUL.md 中的方法论指引被正确注意。

### 2.2 工具调用流程（已确认）

```
[定义] Tool = { definition: ToolDefinition, execute(), contract? }
  ToolDefinition = { name, description, parameters (JSON Schema) }
  ↓
[注册] ToolPoolAssembler → ToolExecutor (Map<name, Tool>)
  ↓
[过滤] ToolExecutor.getDefinitions() → OpenAI tool definitions[]
  格式: { type: "function", function: { name, description, parameters } }
  ↓
[发送] ToolEnabledAgent.run() ReAct 循环:
  POST /chat/completions { messages, tools: [...], tool_choice: "auto" }
  ↓
  LLM 返回 { tool_calls: [{ id, function: { name, arguments } }] }
  ↓
  toolExecutor.execute(request) → 可用性检查 → tool.execute(args, context) → ToolCallResult
  ↓
  追加 tool_result 到消息历史 → 继续循环
```

### 2.3 是否适合把 Methods/Skills 也走类似流程？

**不适合**。原因：

| 对比维度 | Tools（函数调用） | Methods / Skills（知识资产） |
|----------|------------------|---------------------------|
| 本质 | 可执行的动作 | 参考文档/指引 |
| LLM 交互 | OpenAI native `tool_calls`（结构化 JSON） | 需要 Agent"阅读"全文 |
| 调用时机 | 触发频率高，每次推理都可能调用 | 触发频率相对低，更多是"查询-阅读" |
| 参数格式 | 严格 JSON Schema | 关键词搜索 / 按名称读取 |
| 结果格式 | 结构化 JSON 返回值 | Markdown 全文 |

**Method/Skill 与 Tool 的本质区别**：Tool 是"手脚"（执行动作），Method/Skill 是"经验与套路"（知识指引）。

### 2.4 推荐方案：System Prompt 注入列表摘要

不走 OpenAI native tool_calls 流程，而是将可用的 methods/skills **摘要列表**以 system prompt 方式注入：

```
# Available Methods（可用方法）
- <方法名1>：<一句话描述>（路径：methods/xxx.md）
- <方法名2>：<一句话描述>（路径：methods/xxx.md）

# Available Skills（可用技能）
- <技能名1>：<一句话描述>（路径：skills/xxx/SKILL.md）
- <技能名2>：<一句话描述>（路径：skills/xxx/SKILL.md）
```

**注入方式**：
- 在 `buildSystemPromptResult()` 中新增 `MethodList` / `SkillList` section（优先级约 65）
- 内容由 `MethodologyManager` / `SkillRegistry` 在 Gateway 启动时生成
- 每个条目包含：名称 + 一句话摘要 + 路径，不需要全文
- Agent 看到列表后，通过 `method_read` / `skill_get` 按需读取全文

**与工具调用的关系**：
- 不冲突。列表注入是"让 Agent 知道自己有什么"，工具调用是"Agent 通过工具去获取具体内容"
- 列表精简（每条 1 行），不会显著增加 system prompt 长度
- 相当于把当前 SOUL.md 中"开始任务前检查 method_list"的静态指引，变成了动态呈现的可用清单

### 2.5 实现要点

| 要点 | 说明 |
|------|------|
| 注入内容 | 名称 + 摘要 + 路径，每条 ≤ 120 字符 |
| 数量上限 | 最多 20 条（超过按最近更新时间截断） |
| 更新时机 | Gateway 启动时扫描 `stateDir/methods/` 和 `stateDir/skills/` |
| 排序 | 按 updated_at 降序，最近使用的优先 |
| 配置开关 | `BELLDANDY_INJECT_METHOD_SKILL_LIST`，默认 `true` |

## 3. Methods / Skills 草稿编写模板

### 3.1 现状分析

**已有模板**：

| 模板类型 | 文件 | 用途 |
|---------|------|------|
| method-synthesis.md | `docs/experience-templates/method-synthesis.md` | 草稿**合成**时使用 |
| skill-synthesis.md | `docs/experience-templates/skill-synthesis.md` | 草稿**合成**时使用 |
| 硬编码 | `experience-promoter.ts:buildMethodDraft()` | 从任务**自动生成**初稿（字符串拼接） |
| 硬编码 | `experience-promoter.ts:buildSkillDraft()` | 从任务**自动生成**初稿（字符串拼接） |

**关键发现**：
- 合成走模板文件，加载逻辑在 `memory-experience.ts:1510-1532`
- 自动生成初稿走硬编码函数，不使用模板文件
- 但两者的**输出规范完全一致**（同样的 8/6 个章节、同样的 JSON 结构、同样的质量标准）

### 3.2 问题

- 合成与创建的输出格式由两套独立机制保证，存在漂移风险
- 用户自定义章节结构需要同时改两处（模板 + 代码）

### 3.3 推荐方案：复用合成模板，不新增独立创建模板

**结论：不需要新增 `method-create.md` / `skill-create.md`。直接用现有 `method-synthesis.md` / `skill-synthesis.md`。**

二者对输出的要求完全一致，模板定义的是"草稿长什么样"，与"从什么数据来源生成"无关。二者的唯一区别是 system prompt 中的任务描述：

| 场景 | 任务描述 |
|------|---------|
| 合成（synthesis） | "阅读多个相似经验草稿，综合生成一个新的..." |
| 创建（auto-generate） | "阅读单个任务的执行记录，提炼为经验草稿..." |

改动方案：

```
experience-promoter.ts

buildMethodDraft(title, summary, task, snapshot, now):
  1. 加载模板 → resolveExperienceSynthesisTemplate() 复用
  2. 构建 create 场景的 user prompt（单任务数据）
  3. 调用 LLM 生成草稿
  4. 成功 → 返回 LLM 输出
  5. 失败 → 回退到当前硬编码逻辑（码兜底）
```

具体改动：
1. `ExperiencePromoter` 注入 LLM 调用能力（复用 failoverClient 的接口）
2. `buildMethodDraft()` / `buildSkillDraft()` 优先调 LLM + 合成模板生成
3. 当前硬编码逻辑完整保留，作为 LLM 失败 / 超时 / 辅助模型不可用时的兜底
4. 模板加载函数 `resolveExperienceSynthesisTemplate()` 可直接复用，不需要新增函数

### 3.4 不需要新增模板文件

现有两个模板文件已覆盖创建所需的所有输出规范：
- `method-synthesis.md`：定义了 8 个章节结构 + JSON 输出格式 + 质量标准
- `skill-synthesis.md`：定义了 6 个章节结构 + frontmatter 规范 + JSON 输出格式 + 质量标准

唯一需要新增的是 `buildMethodDraft()` / `buildSkillDraft()` 内部调用 LLM 时所用 user prompt 的任务描述文本（约 5-10 行），作为函数内部常量即可，不需要独立文件。

## 4. 已导入 Methods / Skills 的再合成（更新旧资产）

### 4.1 现状分析

**当前合成流程**：

```
已完成的 Task
  ↓
ExperiencePromoter.promoteTask() → status="draft" candidate（数据库）
  ↓
experience.candidate.synthesize.preview → 查找相似 candidate（Jaccard/Dice 相似度）
  ↓
experience.candidate.synthesize.create → LLM 合成 → 新 draft candidate（数据库）
  ↓
experience.candidate.accept → 发布到文件系统
  method: → {stateDir}/methods/{filename}.md
  skill:  → {stateDir}/skills/{name}/SKILL.md
```

**关键约束**（memory-experience.ts:847-854）：

```typescript
if (seedCandidate.status !== "draft") {
  return invalid(req.id, `Only draft candidates can be synthesized. Current status: ${seedCandidate.status}.`);
}
```

当前合成入口只接受 `status === "draft"` 的 candidate。已发布（accepted）的 method/skill 是文件系统上的 `.md` 文件，不在 candidate 表中。

### 4.2 问题分析

已通过 accept 发布到 `stateDir/methods/` 和 `stateDir/skills/` 的资产，**不在体验数据库中作为 candidate 存在**，当前合成流水线无法定位它们。

### 4.3 方案设计

**核心思路**：将已发布的 method/skill 文件"反序列化"为 synthetic candidate，作为合成种子。

#### 方案：文件系统 → Candidate 桥接 + 合成流水线复用

```
用户选择某个已发布的 method/skill 文件
  ↓
从文件系统读取 .md 文件 → 解析 frontmatter + 内容
  ↓
构建虚拟 ExperienceCandidate（status="published", draftOrigin="published"）
  ↓
experience.candidate.synthesize.preview
  → 在数据库中查找与此资产相似的其他 candidate（draft 状态）
  → 同时在文件系统中查找相似的其他已发布 method/skill
  ↓
experience.candidate.synthesize.create
  → 种子 = 已发布资产的虚拟 candidate
  → 源 = 相似的其他 candidate + 其他已发布资产
  → LLM 合成 → 生成新的 draft candidate
  ↓
用户审阅新的 draft candidate
  → accept → 更新/覆盖原文件
  → reject → 丢弃
```

#### 关键改动点

| 改动 | 文件 | 说明 |
|------|------|------|
| 新增 `findSimilarPublishedAssets()` | `experience-synthesis.ts` | 在 `stateDir/methods/` 和 `stateDir/skills/` 中查找相似资产（复用现有 Jaccard/Dice 评分） |
| 新增 `buildVirtualCandidateFromFile()` | `memory-experience.ts` | 从 `.md` 文件构建虚拟 ExperienceCandidate |
| 修改 `synthesize.preview` | `memory-experience.ts:759` | 接受 `assetPath` 参数，支持从文件系统启动预览 |
| 修改 `synthesize.create` | `memory-experience.ts:827` | 放宽 seedCandidate 检查，支持 `status="published"` 的虚拟 candidate |
| 新增 WebChat/UI 入口 | WebChat settings | 在方法/技能管理界面增加"更新合成"按钮 |

#### 交互流程

1. 用户在 WebChat 或方法管理界面选择一个已发布的 method/skill
2. 点击"更新合成"（resynthesize）
3. 系统读取该文件，扫描数据库中相关 candidate + 文件系统中相似资产
4. 展示候选预览（相似度排序）
5. 用户确认后，LLM 合成生成新 draft
6. 新 draft 发布时**覆盖**原文件（需用户确认）

#### 风险与注意事项

| 风险 | 缓解措施 |
|------|---------|
| 合成可能丢失原有精修内容 | accept 前需要人工对比审阅；默认生成的是 draft，不直接覆盖 |
| 跨 candidate + 已发布资产的匹配精度 | 复用现有 0.62 相似度阈值，支持预览拒绝 |
| LLM 合成质量波动 | 复用现有 0.2 低温 + 8000 token 预算 + JSON 格式恢复机制 |
| 文件名冲突 | 合成后生成新的 candidate，发布时由用户决定覆盖旧文件或创建新文件 |

## 5. 记忆数据库内容去重

### 5.1 现状分析

**数据库结构**（`memory.sqlite`）：

| 表 | 用途 | 去重机制 |
|----|------|---------|
| `chunks` | 记忆片段（含 content, memory_type, visibility 等） | **无全局去重** |
| `chunks_fts` | FTS5 全文索引 | 随 chunks 同步 |
| `chunks_vec` | sqlite-vec 向量索引 | 运行时创建 |
| `tasks` | 任务记录 | 已通过 `task_id` 唯一 |
| `experience_candidates` | 经验候选 | 已有 task_id + type 唯一约束 |
| `meta` | 元数据 | key-value |
| `embedding_cache` | 向量缓存 | 按 content_hash 去重 |

**现有去重机制**：

| 去重点 | 位置 | 方式 | 范围 |
|--------|------|------|------|
| 经验 candidate 精确匹配 | `experience-dedup.ts:findExactCandidateMatch()` | slug/title 精确匹配 | 仅 candidate 表 |
| 经验 candidate 模糊匹配 | `experience-dedup.ts:computeSimilarityScore()` | Jaccard/Dice 系数，阈值 0.55 | 仅 candidate + 已发布资产 |
| 持久化记忆提取去重 | `manager.ts:1886-1893` | 混合搜索，分数 > 0.85 则跳过 | 仅 memory evolution 提取时 |
| Session 级去重 | `store.ts:isSessionMemoryExtracted()` | meta 表标记 | 防止重复提取同一 session |
| 任务 tool action 去重 | `manager.ts:findRecentDuplicateToolAction()` | toolName + actionKey | 仅任务级 |
| Chunk 插入 | `store.ts:upsertChunk()` | `ON CONFLICT(id) DO UPDATE` | 仅按 id 去重（content 可能不同但 id 相同） |

**核心问题**：`chunks` 表缺乏内容层面的去重。随着使用时间增长，大量相似甚至相同内容被反复索引（不同 source_path / 不同 id），`chunks` 表会无限制膨胀。

### 5.2 可行性分析

#### 技术可行性：**高**

1. 已有基础设施：
   - FTS5 全文索引（`chunks_fts`）可用于快速相似度计算
   - sqlite-vec 向量检索可用于语义相似度
   - `embedding_cache` 已有 content_hash 去重的模式
   - `computeSimilarityScore()` 已有 Jaccard/Dice 文本相似度算法

2. 去重策略选择：

| 策略 | 实现 | 精度 | 性能 | 风险 |
|------|------|------|------|------|
| **内容哈希** | SHA256(content) → 相同哈希即重复 | 100% | 极高 | 仅检测完全相同的条目 |
| **Jaccard 相似度** | token 级别 | 中 | 中 | 需遍历对比，大规模时慢 |
| **向量语义相似度** | embedding + cosine similarity | 高 | 低 | 需要 embedding provider，耗时 |
| **FTS5 近似搜索** | 按 content 分词搜索 | 中 | 高 | 适合快速粗筛 |

**推荐策略**：内容哈希（精确） + FTS5 近似匹配（模糊），分两阶段执行：
1. 第一阶段：SHA256 哈希匹配，完全相同的直接合并
2. 第二阶段：对剩余条目，用 FTS5 + Jaccard 组合做模糊匹配

#### 辅助模型执行流程

```
用户触发"记忆去重"命令
  ↓
Phase 1: 哈希精确去重
  - 计算所有 chunk 的 SHA256(content)
  - 找到哈希相同的组
  - 每组合并为 1 条（保留最早的 created_at，合并 metadata）
  - 记录删除的 chunk IDs
  ↓
Phase 2: FTS5 模糊扫描
  - 对剩余 chunk 按相似度聚类（Jaccard > 0.85）
  - 每个集群选出代表性条目
  - 调用辅助模型：判断相似条目是否真的重复，还是细微差异有意义
  - 辅助模型输出：{ keep: chunkId, merge: [chunkId, ...], reason }
  ↓
Phase 3: 执行合并
  - 删除被合并的 chunk
  - 更新保留 chunk 的 metadata（追加 merged_from 记录）
  - 重建 FTS5 索引
  - 可选：重建向量索引
```

### 5.3 风险分析

| 风险 | 等级 | 说明 | 缓解措施 |
|------|------|------|---------|
| **误删有意义差异** | 高 | 相似但细节不同的记忆被错误合并 | Phase 2 必须经辅助模型确认，不可全自动 |
| **FTS5 索引破坏** | 中 | `DELETE` 可能不同步 FTS5 trigger | 在事务中执行，操作前备份 |
| **向量索引破坏** | 中 | chunks_vec 需要重建 | 去重后执行 `rebuildVectorIndex()` |
| **无回滚机制** | 高 | SQLite 不擅长大规模回滚 | 操作前自动备份 memory.sqlite → memory.sqlite.bak |
| **大表性能** | 中 | chunks > 100K 时全表 SHA256 慢 | 分批处理，每批 5000 条 |
| **辅助模型幻觉** | 中 | 辅助模型可能误判"不重复" | 阈值设保守（> 0.85），可疑条目跳过并在报告中列出 |

### 5.4 必要的前置条件

1. **备份机制已就绪**：操作前自动备份 `memory.sqlite`
2. **辅助模型可用**：需要配置辅助模型的 API（可复用 failoverClient）
3. **元数据追踪**：所有被合并的条目在保留条目中记录 `merged_from: [id1, id2, ...]`
4. **报告输出**：操作完成后输出去重报告（合并了多少条、减少了多少存储）

### 5.5 建议

1. 先用 **Phase 1（纯哈希去重）** 做 MVP，这种无风险且效果立竿见影
2. Phase 2 模糊去重作为可选增强，默认关闭，由辅助模型逐条确认
3. 提供 dry-run 模式：只输出报告，不执行实际删除
4. 去重命令应作为独立的运维命令（如 `pnpm bdd memory dedup [--dry-run] [--fuzzy]`）

## 补充：BELLDANDY_MEMORY_ENABLED 记忆总开关

### 现状

**`BELLDANDY_MEMORY_ENABLED` 当前对运行时无任何实际控制力。**

经代码确认：
- 变量仅在 `config-channel.ts:68,88` 的 `SAFE_UPDATE_KEYS` 白名单中出现（WebChat 设置面板的读写）
- 不在 `gateway.ts` 的任何运行时分支、`manager.ts`、`store.ts` 中出现

### 实际控制记忆行为的变量（运行时生效）

| 变量 | 默认值 | 控制内容 | 归属系统 |
|------|--------|---------|---------|
| `BELLDANDY_CONTEXT_INJECTION` | `"true"` | 注入近期记忆 `<recent-memory>` | 记忆注入 |
| `BELLDANDY_AUTO_RECALL_ENABLED` | `"false"` | 自动语义召回 `<auto-recall>` | 记忆注入 |
| `BELLDANDY_EMBEDDING_ENABLED` | `"false"` | 向量检索（embedding provider） | 记忆基础设施 |
| `BELLDANDY_MEMORY_EVOLUTION_ENABLED` | `"false"` | 从会话提取持久化记忆 | 记忆写入 |
| `BELLDANDY_TASK_MEMORY_ENABLED` | `"false"` | 任务记录写入 tasks 表 | 记忆写入 |
| `BELLDANDY_MEMORY_SUMMARY_ENABLED` | `"false"` | L0 摘要生成 | 记忆基础设施 |
| `BELLDANDY_INJECT_MEMORY` | `"true"` | 注入 MEMORY.md 到 system prompt | **系统提示词注入** |

### 关键区分：记忆注入 ≠ 系统提示词注入

需要严格区分两类注入：

| 类别 | 变量 | 注入内容 | 来源 |
|------|------|---------|------|
| **记忆注入**（动态上下文） | `CONTEXT_INJECTION` / `AUTO_RECALL_ENABLED` | `<recent-memory>` / `<auto-recall>` 块 | memory.sqlite 检索结果 |
| **系统提示词注入**（静态配置） | `INJECT_AGENTS` / `INJECT_SOUL` / `INJECT_MEMORY` | AGENTS.md / SOUL.md / MEMORY.md 文件内容 | stateDir 下的配置文件 |

`BELLDANDY_MEMORY_ENABLED` 总开关**只应影响记忆注入相关的子开关**，**不应影响系统提示词注入**。即：

- **应关闭**：`CONTEXT_INJECTION`、`AUTO_RECALL_ENABLED`、`MEMORY_EVOLUTION_ENABLED`、`EMBEDDING_ENABLED`、`MEMORY_SUMMARY_ENABLED`、`TASK_MEMORY_ENABLED`
- **不应触碰**：`INJECT_AGENTS`、`INJECT_SOUL`、`INJECT_MEMORY`（这些属于 prompt 配置，与记忆数据库无关）

### 实现方案

**关键设计决策：代码层覆盖局部变量，不动 env 原有值。**

这不是"把 6 个 env 变量也设置成 false"，而是在 gateway.ts 运行时，读取各子开关的 env 值后，再用总开关做一层覆盖。子变量原有 env 值不变、`.env.local` 不变。`BELLDANDY_MEMORY_ENABLED=false` → 运行时代码强制覆盖 → `BELLDANDY_MEMORY_ENABLED=true`（或删除）→ 各子开关自动恢复自身的 env 配置值。**无回退问题。**

**实现难度：极低。** 在 `gateway.ts` 现有子开关读取逻辑之后，加一层短路覆盖：

```typescript
// gateway.ts 现有逻辑（约第 537-543 行）
const injectAgents = (readEnv("BELLDANDY_INJECT_AGENTS") ?? "true") !== "false";
const injectSoul = (readEnv("BELLDANDY_INJECT_SOUL") ?? "true") !== "false";
const injectMemory = (readEnv("BELLDANDY_INJECT_MEMORY") ?? "true") !== "false";

// 各子开关各自从 env 读取原始值（保持不变）
let contextInjectionEnabled = readEnv("BELLDANDY_CONTEXT_INJECTION") !== "false";
let autoRecallEnabled = readEnv("BELLDANDY_AUTO_RECALL_ENABLED") === "true";
// ... 其他子开关同理

// 新增：记忆总开关——运行时覆盖，不修改 env 原始值
const memoryEnabled = readEnv("BELLDANDY_MEMORY_ENABLED") !== "false";
if (!memoryEnabled) {
  contextInjectionEnabled = false;    // 关闭 <recent-memory> 注入
  autoRecallEnabled = false;          // 关闭 <auto-recall> 注入
  memoryEvolutionEnabled = false;     // 关闭会话记忆提取
  embeddingEnabled = false;           // 关闭向量检索
  memorySummaryEnabled = false;       // 关闭摘要生成
  taskMemoryEnabled = false;          // 关闭任务记录
  // 注意：injectAgents / injectSoul / injectMemory 不受影响
  //       这 3 个变量读的是各自 env，不走总开关
}
```

**回退行为验证**：

| 操作 | 子开关实际值 | 说明 |
|------|-----------|------|
| 设 `BELLDANDY_MEMORY_ENABLED=false` | 全部强制为 `false`（代码覆盖） | 各子开关 env 原始值不变 |
| 改为 `BELLDANDY_MEMORY_ENABLED=true` | 恢复各子开关 env 原始值 | 无需记忆之前的值，自动恢复 |
| 删除 `BELLDANDY_MEMORY_ENABLED` | 等同于 `true`（默认值） | 同上 |

改动量：gateway.ts 加约 12 行代码，不需要触碰 MemoryManager 或任何下游模块。所有子功能各自已有独立的开关保护，总开关只是运行时批量覆盖。

### 纯开发模式的推荐配置

开发任务需要高纯度上下文，不应被历史记忆污染。推荐两种配置方式：

**方式一：总开关一键关闭（实现后可用）**

```env
BELLDANDY_MEMORY_ENABLED=false
# 如需保留任务统计（时间/token 记录），追加：
# BELLDANDY_TASK_MEMORY_ENABLED=true
```

**方式二：手动关闭各子开关（当前可用）**

```env
BELLDANDY_CONTEXT_INJECTION=false
BELLDANDY_AUTO_RECALL_ENABLED=false
BELLDANDY_MEMORY_EVOLUTION_ENABLED=false
BELLDANDY_TASK_MEMORY_ENABLED=false
```

注意：`INJECT_MEMORY`（即 MEMORY.md 的注入）属于系统提示词配置，不属于记忆注入，不在此开关范围内。如果 MEMORY.md 中有开发相关的长期记忆（如常用命令、项目约定），关闭反而有损；如果 MEMORY.md 里全是生活闲聊，可在开发开始前手动重置该文件。

### 建议

1. 优先实现总开关 `BELLDANDY_MEMORY_ENABLED`，改动小、收益明确
2. 总开关只覆盖记忆注入相关变量，不触碰系统提示词注入（`INJECT_AGENTS`、`INJECT_SOUL`、`INJECT_MEMORY`、`TOOLS.md` 等）
3. 保留 `TASK_MEMORY_ENABLED` 细粒度覆盖能力：即使总开关关闭，用户仍可单独开启任务统计

## 7. 当前五项需求复核与记忆树方案评估（2026-05-18）

本节基于当前代码再次复核，不沿用旧结论。重点回答：

1. 普通任务生成 method / skill 草稿当前是否使用模型。
2. WebChat 首页“页面多开”按钮的实现计划。
3. `BELLDANDY_MEMORY_ENABLED=false` 时是否应恢复“关闭记忆但保留任务统计”。
4. `memory.sqlite` 去重清理后文件大小不变，以及重复内容可能回写的原因。
5. 对比 `tmp/openhuman-main` 的分层记忆树机制，给出 Star Sanctuary 的数据源盘点和落地建议。

### 7.0 本轮需求理解（记忆清洗 + 打分分层 + 专属数据资产）

基于本轮新增说明，我对目标的理解不是“继续扩展 `memory.sqlite` 的 dedup 工具”，而是把 Star Sanctuary 现有分散的个体私有数据，整理成一条**低风险、旁路、可解释、可回滚**的记忆资产流水线。

#### 7.0.1 目标重述

目标可以拆成四层：

1. **先盘点和统一来源**  
   不只看 `memory.sqlite`，而是回到原始或近原始来源：`.star_sanctuary/sessions`、`.star_sanctuary/memory`、`MEMORY.md`、task / activity / experience 表，以及会话侧的 `.digest.json`、`.session-memory.json`、`.transcript.jsonl`、`.meta.json` 等私有数据。

2. **先清洗，再入树，而不是先删库**  
   不直接让大模型对 `memory.sqlite` 做清理删除；而是先把来源数据标准化、去噪、去重、轻压缩，再在现有 `memory.sqlite` 上生成新的分层记忆资产层。  
   默认优先在现有 `memory.sqlite` 内扩表演进；只有在迁移风险过高时，才临时使用旁路库做过渡验证。

3. **引入打分与准入机制**  
   不是所有内容都同权进入长期记忆。需要像 OpenHuman 一样，为 leaf 记录打分、准入状态、解释信号和生命周期，决定哪些内容保留为 raw、哪些进入 summary、哪些归档、哪些仅保留 provenance。

4. **形成 Agent 与用户的专属数据资产**  
   最终产物不是“多一个数据库”，而是形成可查询、可追溯、可压缩、可同步的专属资产层，覆盖：
   - Agent 个体日记
   - 用户与 Agent 的对话轨迹
   - 任务执行与复盘
   - 方法 / 技能 /经验资产
   - 用户偏好、项目脉络、关键实体与长期目标

#### 7.0.2 我理解的约束

| 约束 | 理解 |
|------|------|
| 风险控制优先 | 不做“大模型直接清理 `memory.sqlite` 并删除内容”的高风险方案 |
| 单库优先演进 | 优先在现有 `memory.sqlite` 上扩展记忆树 schema；只有迁移风险过高时才允许短期旁路 |
| 先做私有数据 | 优先处理 Agent 个体与用户私有数据，不先扩大到团队共享或公共渠道 |
| 轻压缩且可调 | 压缩不是越强越好，默认应从安全档开始，并且可调 |
| 需要可解释 | 每条保留/丢弃/压缩建议要有分数、信号或理由，不能黑盒 |
| 必须保留回溯 | raw source、source ref、time range、agent scope 不能丢 |

#### 需求 1 的实现方案计划

如果目标是“确认当前用什么模型”，当前结论已经闭合：普通草稿不调用模型，合成草稿调用 primary model。

如果目标是“普通草稿全部统一到 synthesis 模板机制”，建议补齐 **Memory task promote 链路的模板统一**，但明确保持普通草稿为本地代码生成，不新增普通草稿模型调用。

**模型边界必须明确：**

| 链路 | 是否引入模型 | 状态 |
|------|------|------|
| Goal-derived 普通 Method / Skill candidate | 否 | 已按 synthesis 模板骨架本地生成 |
| Memory task direct promote 普通 Method / Skill candidate | 否 | 待接入同一套模板骨架 |
| Method / Skill synthesis 合成草稿 | 是 | **已实现**，调用 primary model |

也就是说：**只有合成才会引入模型，普通草稿不引入模型。** 后续不新增 `BELLDANDY_EXPERIENCE_DRAFT_MODEL` 之类的普通草稿模型配置，避免把任务结束或人工 promote 链路拖进模型延迟、模型成本和输出解析风险。

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|
| A. 只修正文档，承认两条入口差异 | 无代码风险 | 直接提升链路继续与 goal 链路存在分叉 | 可作为短期状态说明 |
| B. 把 `ExperiencePromoter.promoteTask()` 也改为 template-aware 本地代码生成 | 保持无模型、低延迟、低成本；能消除普通草稿结构分叉 | 需要处理 `@belldandy/memory` 与 core 模板解析的依赖边界 | **优先推荐** |
| C. 普通草稿也接入 LLM | 理论上草稿质量可能更高 | 违背当前边界；会引入延迟、成本、失败回退、输出解析和任务收尾阻塞风险 | **不采用** |

##### 统一模板机制实施计划

PLAN

Goal  
让 Memory task direct promote 链路生成的普通 Method / Skill candidate，也按 `method-synthesis.md` / `skill-synthesis.md` 的 Markdown 骨架和章节规范输出；普通草稿仍然只由本地代码生成，模型只用于 synthesis 合成。

Constraints  
- 不引入普通草稿模型调用，不新增普通草稿模型配置。
- 不改变 `experience.candidate.synthesize.create` 的合成模型链路；该链路已实现并继续使用 primary model。
- 不让 `@belldandy/memory` 反向依赖 `@belldandy/core`，避免包依赖倒置。
- 不改变 promote 的用户确认、去重、candidate 存储和 publish 审批语义。
- 模板缺失、模板不合格或路径不可用时，必须回退现有硬编码生成结果。

Steps  
1. 在 `@belldandy/memory` 内新增 template-aware draft builder，或抽出一个不依赖 core 的公共模板工具，支持读取并抽取 synthesis 模板里的 fenced Markdown skeleton。

3. 将 direct promote 的 `buildMethodDraft()` / `buildSkillDraft()` 拆为两层：template-aware builder 优先生成；legacy builder 作为 fallback 保留。
4. Method 生成必须覆盖 `## 0. 元信息` 到 `## 8. 更新记录`；Skill 生成必须覆盖 frontmatter、`## 快速开始`、`## 决策路由`、`## 输入`、`## 输出`、`## 参考指引`、`## NEVER`。
5. 保留现有 dedup、qualityScore、sourceTaskSnapshot、metadata 与 `experience_candidates` 写入行为，避免把模板统一扩大成候选生命周期重构。
6. 更新 direct promote 相关测试，断言 `task_promote_method` / `task_promote_skill_draft` 或 `experience.candidate.generate` 生成结果包含 synthesis 模板章节，并新增模板缺失 fallback 测试。
7. 同步文档：说明普通草稿不使用模型；只有合成草稿调用 primary model。

Validation  
- Unit：`packages/belldandy-memory/src/experience-promoter.test.ts` 覆盖 method / skill direct promote 的模板结构与 fallback。
- Integration：`packages/belldandy-core/src/server.memory-experience.test.ts` 覆盖 `experience.candidate.generate` 返回的 direct promote candidate 内容结构。
- Regression Focus：确认 `experience.candidate.synthesize.create` 仍是唯一模型调用链路，普通 promote 不发起 OpenAI/primary model 请求。
- Manual：WebChat 手动生成 task method / skill candidate 后，候选内容章节与 synthesis 模板一致，仍可进入后续审阅/发布流程。

##### 风险与回滚

| 风险 | 影响 | 缓解方式 |
|------|------|------|
| 包依赖边界处理不当 | `@belldandy/memory` 反向依赖 core，造成架构倒置或循环依赖 | 模板解析工具放在 memory 包或更底层公共包；不要 import core |
| promote 链路被改成 async | 大量调用点和测试需要连带修改，增加回归面 | 保持同步生成；模板内容可同步读取或在构造时准备 |

| 旧测试依赖硬编码文案 | 测试失败但业务行为是预期变更 | 更新测试断言为结构性断言，减少依赖具体句子 |
| 普通草稿被误接入模型 | 引入延迟、成本、失败回退和上下文污染风险 | 明确非目标；测试或代码审查确认 direct promote 不调用 model client |

风险等级：低到中。主要风险是包依赖边界、模板路径解析和结构校验，不涉及数据破坏。

完成边界：Goal-derived 与 direct task promote 两条普通草稿入口都按 synthesis 模板结构输出；普通草稿全程不调用模型；只有 synthesis 合成草稿调用 primary model。

| 文件 | 当前行为 |
|------|------|
| `packages/belldandy-core/src/memory-runtime-switches.ts:24-35` | `BELLDANDY_MEMORY_ENABLED=false` 会把 `contextInjection`、`autoRecall`、`embedding`、`summary`、`evolution`、`taskMemory`、`taskSummary`、`deepRetrieval` 全部压成 `false` |
| `packages/belldandy-core/src/memory-runtime-switches.test.ts` | 测试明确要求 master 关闭时所有 runtime memory features 都关闭 |
| `packages/belldandy-core/src/bin/gateway.ts:3125-3330` | `taskMemoryEnabled` 为 true 时才注册任务开始、工具调用记录、任务完成、经验候选自动沉淀、task dedup guard 等 hook |
| `packages/belldandy-core/src/context-injection.ts:200-312` | 任务摘要进入 `<work-overview>` / `<recent-tasks>` 的前提是 `contextInjectionEnabled=true` |

这意味着当前 `BELLDANDY_MEMORY_ENABLED=false` 是“硬关闭整个 memory runtime”，不会保留任务统计。

#### 为什么建议恢复

关闭记忆的原始目标是让 Agent 在开发或任务执行时不受历史上下文污染。这个目标主要对应：

- 关闭 `<recent-memory>` 注入。
- 关闭 `<auto-recall>` 语义召回。
- 关闭会话 durable extraction。
- 关闭后台摘要和 embedding 这类会扩散历史记忆的能力。

但任务统计本身更像“执行遥测”和“任务复盘底账”，不等于把历史记忆注入当前上下文。只要不同时开启 context injection，它不会自动污染当前 prompt。

保留任务统计的收益：

| 能力 | 对纯开发/纯任务的价值 | 是否会污染当前上下文 |
|------|------|------|
| task 记录、duration、token、toolCalls、artifactPaths | 便于判断任务是否完成、哪里失败、后续怎么复盘 | 否，除非被注入或查询 |
| task activities / workRecap / resumeContext | 支持任务恢复、回看执行轨迹 | 默认不注入时不污染 |
| experience auto promotion | 让成功任务沉淀 method/skill candidate | 不直接注入，但会产生候选资产 |
| task dedup guard | 避免重复执行近期已成功的高风险工具动作 | 可能影响执行，应保留独立开关 |

推荐语义：

```env
BELLDANDY_MEMORY_ENABLED=false
BELLDANDY_TASK_MEMORY_ENABLED=true
BELLDANDY_TASK_SUMMARY_ENABLED=false
BELLDANDY_CONTEXT_INJECTION=false
BELLDANDY_AUTO_RECALL_ENABLED=false
BELLDANDY_MEMORY_EVOLUTION_ENABLED=false
```

含义：不召回、不注入、不提取长期记忆，但保留任务过程统计。

#### 推荐实现方式

不要让 `BELLDANDY_MEMORY_ENABLED=false` 静默恢复所有任务能力。更稳的方式是增加一个明确 carve-out：

```env
BELLDANDY_MEMORY_ENABLED=false
BELLDANDY_TASK_MEMORY_ENABLED=true
BELLDANDY_TASK_STATS_WHEN_MEMORY_DISABLED=true
```

代码策略：

| 子能力 | master=false 时建议 |
|------|------|
| `contextInjectionEnabled` | 强制 false |
| `autoRecallEnabled` | 强制 false |
| `embeddingEnabled` | 强制 false |
| `summaryEnabled` | 强制 false |
| `evolutionEnabled` | 强制 false |
| `deepRetrievalEnabled` | 强制 false |
| `taskMemoryEnabled` | 允许 `BELLDANDY_TASK_STATS_WHEN_MEMORY_DISABLED=true && BELLDANDY_TASK_MEMORY_ENABLED=true` 时保留 |
| `taskSummaryEnabled` | 默认仍 false；如需开启，应另设显式 carve-out，因为它会额外调用 LLM |

风险：

1. `taskMemoryEnabled=true` 会启用 `task dedup guard`，可能阻止重复工具动作；已有 `BELLDANDY_TASK_DEDUP_GUARD_ENABLED=false` 可关闭。
2. `experienceAutoPromotionEnabled=true` 时，任务完成后仍可能生成 method/skill candidate；如果只想要统计，可关闭 `BELLDANDY_EXPERIENCE_AUTO_PROMOTION_ENABLED=false`。
3. 需要更新 `memory-runtime-switches.test.ts`，否则现有测试会继续要求 master=false 时 task memory 也关闭。

结论：**恢复“关闭记忆但保留任务统计”能让 Agent 在纯开发/纯任务状态下更稳定推进任务**，因为它保留执行轨迹与复盘资产，同时不必把历史记忆注入当前上下文。实现时必须把“统计记录”和“记忆召回/注入/提取”拆开。

### 7.4 需求 4：`memory.sqlite` 去重清理后文件大小不变的原因

**先给答案：文件大小不变不代表清理无效。当前更可能有两个原因同时存在。**

#### 原因 A：SQLite 删除行后默认不会缩小数据库文件

当前 `memory.dedup.apply` 会：

1. 备份 `memory.sqlite` 到 `stateDir/artifacts/memory-dedup-backups/`。
2. 删除重复 `chunks`。
3. 迁移 `task_memory_links`。
4. 删除对应 `chunks_vec` 行。
5. 触发必要的 FTS 自愈 rebuild。

代码证据：

| 行为 | 文件 |
|------|------|
| apply 要求 `confirmed=true` | `packages/belldandy-core/src/server-methods/memory-experience.ts:227-243` |
| 备份路径 | `packages/belldandy-core/src/server-methods/memory-experience.ts:239` |
| 删除 chunk / relink task links / 删除 vec | `packages/belldandy-memory/src/store.ts:1143-1276` |
| 当前未执行 `VACUUM` | `packages/belldandy-memory/src/store.ts` 中没有 `VACUUM` 调用 |

SQLite 的 `DELETE` 只把页面放入 freelist，数据库文件会保留这些空闲页供后续写入复用。要缩小磁盘文件，通常需要在安全窗口执行 `VACUUM` 或配置 `auto_vacuum`。当前代码没有做这一步。

因此：

| 观察 | 解释 |
|------|------|
| `chunks` 数量下降，但 `memory.sqlite` 文件大小没变 | 正常，释放页进入 freelist |
| 后续写入一段时间文件大小没有继续增长 | 说明 SQLite 复用了 freelist |
| 想看到文件变小 | 需要停机/低风险窗口执行 `VACUUM`，并注意 WAL/SHM 文件 |

#### 原因 B：源文件没清洗时，重复 chunk 可能被再次索引回来

当前 memory DB 不是唯一源头。默认索引路径来自：

| 来源 | 文件 |
|------|------|
| `stateDir/sessions` | `packages/belldandy-core/src/memory-index-paths.ts:23` |
| `stateDir/memory` | `packages/belldandy-core/src/memory-index-paths.ts:13` |
| `stateDir/MEMORY.md` | `packages/belldandy-core/src/memory-index-paths.ts:14` |
| 可选 `team-memory` | `packages/belldandy-core/src/memory-index-paths.ts:17-19` |

Indexer 会把这些源文件重新拆 chunk，并用 `replaceSourceChunks(filePath, chunks)` 替换同一 source 的索引。也就是说：

- 如果重复内容来自 `memory/*.md`、`MEMORY.md`、`sessions/*.jsonl` 等源文件；
- 而清理只删除了 `memory.sqlite` 里的派生 chunk；
- 源文件原文仍保留重复内容；
- 那么启动索引或 watcher 检测到变化时，重复内容可能重新进入 `chunks`。

这不是“清理代码没起作用”，而是**只清理了派生索引，没有清理源数据**。

#### 当前去重能力边界

| 能力 | 当前状态 |
|------|------|
| 完全相同内容去重 | 已有，`hash_only_exact`，归一化为 `trimmed_lf` |
| 模糊相似内容去重 | 未实现 |
| 源文件同步清洗 | 未实现 |
| `VACUUM` 缩库 | 未实现 |
| 操作前备份 | 已实现 |
| dry-run preview | 已实现 |

#### 最小验证方式

建议用以下指标判断清理是否真的生效，而不要只看文件大小：

```sql
SELECT COUNT(*) FROM chunks;
PRAGMA page_count;
PRAGMA freelist_count;
SELECT COUNT(*) FROM chunks_fts;
```

业务侧验证：

1. 清理前执行 `memory.dedup.preview`，记录 `duplicateGroups` / `removableChunks`。
2. 清理后再次执行 `memory.dedup.preview`，确认同一 filter 下重复组下降。
3. 如果一段时间后重复组回来，检查重复组里的 `sourcePath`，大概率是源文件仍含重复内容并被重建索引。

建议后续改造：

| 优先级 | 建议 | 风险 |
|------|------|------|
| P0 | 在 dedup 结果中展示 `beforeChunkCount` / `afterChunkCount` / `freelistCount` / `pageCount` | 低 |
| P0 | UI 文案说明“SQLite 文件大小不会因 DELETE 立即变小” | 低 |
| P1 | 新增 `memory.vacuum.preview/apply`，要求停机或确认，执行前备份 | 中 |
| P1 | 在 dedup report 中标记“重复来源是否来自可索引源文件” | 低 |
| P2 | 新增源文件级清洗 preview，只生成 patch，不自动覆盖 | 高 |

### 7.5 需求 5：OpenHuman 分层记忆树与 Star Sanctuary 当前机制对比

`tmp/openhuman-main` 的核心思路不是“向量库 + 摘要”，而是一条分层、可追溯、可压缩的 memory tree 管线。

OpenHuman 参考点：

| 机制 | OpenHuman 文件 | 说明 |
|------|------|------|
| 总体管线 | `tmp/openhuman-main/gitbooks/features/obsidian-wiki/memory-tree.md` | source adapter -> canonicalize -> chunk -> content_store -> score -> source/topic/global trees -> retrieval |
| 模块说明 | `tmp/openhuman-main/src/openhuman/memory/tree/README.md` | 说明 chunker、ingest、store、score、tree_source、tree_topic、tree_global、jobs |
| 确定性 chunk id | `tmp/openhuman-main/src/openhuman/memory/tree/types.rs` | chunk id 基于 `source_kind + source_id + seq + content` 哈希，既幂等又避免同一 source 多批次内容撞号 |
| 打分与准入 | `tmp/openhuman-main/src/openhuman/memory/tree/score/mod.rs` | cheap signals 先打分，明显保留/丢弃会跳过 LLM，边界样本才调用 LLM |
| 打分信号 | `tmp/openhuman-main/src/openhuman/memory/tree/score/signals/types.rs` | token、unique words、metadata、source、interaction、entity density、LLM importance |
| 分层树 | `tmp/openhuman-main/src/openhuman/memory/tree/tree_source/types.rs` | L0 buffer 达到预算后 seal 成 L1 summary，L1 再按 fanout seal 到更高层 |
| Topic tree | `tmp/openhuman-main/src/openhuman/memory/tree/tree_topic/README.md` | 根据实体 hotness 懒加载 topic tree |
| Global tree | `tmp/openhuman-main/src/openhuman/memory/tree/tree_global/README.md` | 每日全局 digest，向周/月/年摘要折叠 |
| 后台队列 | `tmp/openhuman-main/src/openhuman/memory/tree/jobs/README.md` | SQLite job queue 处理 extract / append / seal / topic_route / digest / flush |

#### 7.5.1 本次复核后的关键校正

这次重新查代码后，原有 7.5 里有几处需要明确校正：

1. **OpenHuman 的 chunk id 不是只看 source 与 seq**  
   `types.rs` 明确把 `content` 也纳入哈希，因此它不是简单的 `(source_kind, source_id, seq)` 主键，而是“同源同序号下内容变化也会变 id”的内容参与型确定性 id。

2. **OpenHuman 的准入不是“所有 chunk 都完整跑一遍 LLM”**  
   `score/mod.rs` 明确有三段式准入：
   - cheap total 高于 definite keep：直接 admitted
   - cheap total 低于 definite drop：直接 dropped
   - 只有中间 borderline band 才调用 LLM extractor

3. **OpenHuman 的 jobs queue 是主干，不是附属异步优化**  
   `ingest.rs` 和 `jobs/README.md` 表明：persist 后只做热路径落盘与 enqueue，extract / append / seal / digest 都依赖 queue。  
   这决定了它天然更适合“旁路逐步建树”，而不是在请求线程里同步做重处理。

4. **OpenHuman 强调生命周期和 provenance 常驻，而不是删原文**  
   dropped chunk 仍保留 row；sealed summary 也是 append-only 风格；raw provenance 不因为摘要树存在而被移除。  
   这点和 Star 当前 `memory.dedup.apply` 的“直接删 chunk”是明显不同的风险取向。

#### 策划视角对比表

| 对比维度 | OpenHuman 机制 | Star Sanctuary 当前机制 | 对 Star 的建议 |
|------|------|------|------|
| 数据入口 | chat / email / document adapter 统一 canonicalize | 主要索引 `sessions/*.jsonl`、`memory/*.md`、`MEMORY.md`，另有 tasks / experience 表，conversation 侧还有 digest / session-memory / transcript / meta 等旁路状态 | 增加统一 `memory_source_envelope`，把会话、任务、日记、长期记忆、经验资产与会话派生状态都标准化 |
| 源数据形态 | canonical Markdown + provenance metadata | 文件路径、source type、memory type、metadata JSON 较轻 | 补 `source_kind`、`source_id`、`source_ref`、`time_range`、`agent_id`、`visibility`、`content_hash` |
| Chunk ID | 内容参与确定性 ID，重放幂等 | 文件索引用 `md5(filePath)_index`，同内容跨文件仍会重复 | 新记忆树层使用 content-addressed leaf id，不替换旧 chunks |
| 去重策略 | ingest 层幂等 + lifecycle 防重放 | exact dedup 只清理 DB 派生 chunk | 将去重前移到清洗/入树阶段，保留 raw source，不直接删 |
| 记忆准入 | score 后 `pending_extraction → admitted/dropped → buffered → sealed` lifecycle | 目前 chunk 默认进入检索；只有 durable extraction 有相似度跳过 | 增加 score/lifecycle：`raw`、`candidate`、`admitted`、`compressed`、`archived`、`dropped` |
| 打分解释 | 每个 signal 单独持久化 | context injection 有临时重要性评分，但没有持久 score 表 | 新增 `memory_scores`，保存各信号和总分，便于 UI 解释 |
| 压缩方式 | L0 buffer seal 到 L1/L2 summary | L0 摘要是单 chunk summary，不形成树 | 建 L0 leaf、L1 source/session/day、L2 topic/project、L3 profile/global |
| Topic 机制 | entity hotness 触发 topic tree | 有 category，但无实体索引和 hotness | 增加实体抽取和 topic hotness，优先项目、用户偏好、关键实体 |
| Global 机制 | daily global digest 折叠到周/月/年 | durable extraction 写每日 memory 文件，但没有全局树 | 增加每日/每周 agent diary 与用户/项目 digest |
| 后台任务 | SQLite job queue + worker pool | 摘要/evolution 由 gateway 空闲或 agent_end 调度 | 新增 memory clean jobs，支持 dry-run、重试、限流、可暂停 |
| 可读资产 | wiki Markdown vault | `MEMORY.md` / `memory/YYYY-MM-DD.md` 可读，但树结构不可读 | 为树节点同步可读 Markdown，形成“专属数据资产” |
| 风险控制 | append-only、summary immutable、raw provenance | dedup apply 会直接删 chunks，但有备份 | 新树先只读/旁路生成，不破坏旧 `memory.sqlite` |

| prompt snapshot / run artifact | 不作为 memory chunk | prompt inspection runtime 持久化快照 | 可用于 debug 和回归 | 高噪声、高隐私风险 | 默认不入树，只在诊断模式抽样 |
| 外部渠道消息（Feishu/email/webhook 等） | 通过 conversation/session 间接进入 | 渠道把消息写入 conversation store | 私有沟通数据资产 | 缺源级 canonicalization | 后续按 channel/source_kind 单独 canonicalize |
| resident agent 私有状态 | 是，按 agent 独立 `memory.sqlite` | `createScopedMemoryManagers()` 为 agent/stateDir 建独立 manager | 个体记忆隔离已具备基础 | 分层树还没按 agent 形成资产视图 | 新树天然按 agent_id / private stateDir 分层 |
| `dream-runtime.json` / `DREAM.md` / `dreams/**/*.md` | 不直接进入当前 `memory.sqlite` | Dream runtime 维护输入快照、运行状态、dream 文稿与 Obsidian/Commons 同步 | 属于更高层“Agent 自我整理”资产，可作为 diary/global 线索 | 这是二次整理产物，不应和 raw session 同层混放 | 作为 derived / curated 层来源，后于 raw/task/session 入树 |

当前 Star 的优势：

1. 已经有 SQLite/FTS/vector 混合检索基础。
2. 已经有任务统计、经验候选、resident agent 私有 memory manager。
3. 已经有 durable extraction，能从对话中提炼长期记忆。
4. 已经有 WebChat memory/experience UI 和 dry-run dedup 入口。

当前 Star 的主要缺口：

1. 缺统一的 canonical source envelope。
2. 缺持久化 score / rationale / lifecycle。
3. 缺 entity/topic 索引和 hotness。
4. 缺 source/topic/global 分层 summary tree。
5. 去重只在 DB chunk 层，未处理源文件重复和语义相似。
6. `sessions`、transcript、task、digest、session-memory、memory markdown、dream 资产之间还没有统一的数据资产视图。

### 7.7 Star Sanctuary 分层记忆树建议方案

目标：实现对 Agent 个体日记、对话、任务、经验、私有数据的去重、提炼、轻压缩和同步，形成 Agent 与用户的专属记忆/数据资产。

#### 7.7.0 本次复核后的方案收紧

原 7.7 方向总体成立，但本次复核后需要补一个更明确的边界：**不是所有来源都应该以“原始正文”身份直接入树。**

建议把 Star 的来源分成三类：

| 类别 | 代表来源 | 入树策略 |
|------|------|------|
| `raw` 原始源 | `sessions/*.jsonl`、`MEMORY.md`、`memory/*.md`、task/activity 结构化记录 | 作为 L0 主来源 |
| `derived` 派生源 | `.digest.json`、`.session-memory.json`、tool digest、recent tool result、dream input snapshot | 优先作为 L1/L2 候选、打分信号或补充叶子，不与 raw 同权 |
| `curated` 整理资产 | `experience_candidates`、accepted method/skill、`DREAM.md` / `dreams/*.md` | 作为高权重知识资产层，进入 topic/profile/global 更合适 |

这能避免两个常见问题：

1. 把已经压缩过的 digest / dream 再当 raw 入树，造成“摘要套摘要”的信息失真。
2. 把运行时元数据全塞进长期记忆，导致噪声、隐私和维护成本一起上升。

#### 7.7.1 本次收口新增：来源注册与存储形态决策

在 7.7 原方案基础上，再补两条正式收口边界：

1. **来源接入采用“默认来源 + 可配置外来源”双层模型**
2. **分层记忆树主实现采用数据库，Markdown 只做辅层，不反过来作为主存储**

##### A. 来源接入边界

建议把记忆树来源拆成两层：

| 层级 | 说明 |
|------|------|
| builtin 默认来源 | Star 当前内建、无需额外配置即可盘点的来源 |
| configured 外来源 | 通过单独配置脚本启用/关闭/扩展的外部来源 |

builtin 默认来源建议至少包括：

- `sessions/*.jsonl`
- `sessions/*.transcript.jsonl`
- `sessions/*.meta.json`
- `MEMORY.md`
- `memory/*.md`
- `tasks / task_activities`
- `experience_candidates / experience_usages`
- `.digest.json / .session-memory.json`
- `dream-runtime.json / DREAM.md / dreams/**/*.md`

configured 外来源建议作为后续扩展位，允许按配置增减，例如：

- email
- Obsidian vault
- 本地文档目录
- 未来的 OpenHuman 风格 adapter

注意：

- 外来源不应默认与 builtin raw 同权入树
- 外来源应先经过 `inventory -> classify -> score -> dry-run`
- 每个来源都必须明确映射到 `raw / derived / curated` 三分类之一

这样可以同时满足：

1. 先把 Star 自身的三类来源做扎实
2. 未来可像 OpenHuman 一样逐步扩展用户数据来源
3. 不把“接来源”与“直接入长期记忆”混成一步

##### B. 存储形态边界

建议明确：

- **现有 `memory.sqlite` 应作为分层记忆树优先的 canonical runtime store**
- **Markdown 只作为人类可读镜像、审阅报告、导出层或 curated 资产层**
- **`memory_tree.sqlite` 只作为高风险迁移时的临时旁路验证库，不应成为长期双主库方案**

原因：

1. 当前 `memory.sqlite` 本身已经不是单纯 chunk 索引库，而是运行时主记忆库：
   - `chunks` + `chunks_fts` + `chunks_vec`
   - `tasks` + `task_activities` + `task_memory_links`
   - `experience_candidates` + `experience_usages`
   - `summary`、`visibility`、`agent_id`、`category`、`meta` 等演进字段与索引

2. `createScopedMemoryManagers()` 已按 resident agent / shared layer 生成各自的 `memory.sqlite`。  
   如果再长期引入 `memory_tree.sqlite`，就不是“多一个库”这么简单，而是会把每个 Agent / shared scope 的数据库数量和迁移、备份、回滚、观察复杂度一起翻倍。

3. 分层记忆树不只是正文存储，还需要维护：
   - source ref
   - source class
   - score / rationale
   - lifecycle
   - entity/topic
   - leaf/node edges
   - clean jobs / reports

4. `P8-P10` 的核心能力都更适合数据库：
   - 幂等 ingest
   - exact / near dedup
   - leaf / node / edge 查询
   - 按来源 / 日期 / 主题 drill-down
   - dry-run 与 apply 报告持久化

5. Markdown 更适合做人读层，而不是主索引层：
   - inventory / dry-run / merge 建议报告导出
   - curated 资产镜像
   - Obsidian / 外部同步

因此不建议把：

- L0 leaf
- L1/L2/L3 树节点
- score / lifecycle / edge

直接设计成多个 `.md` 文件为主的实现。  
更稳的做法是：

- `memory.sqlite` 作为运行时真相源，优先通过增表 / 增索引 / 增元数据演进
- Markdown 做审阅、导出、同步与 curated 发布层

##### B.1 基于当前代码复核后的正式判断

这次复核后，关于“要不要长期保留 `memory_tree.sqlite`”可以正式收口为：

- **不建议长期维护 `memory.sqlite` + `memory_tree.sqlite` 双主库**
- **优先方案是把记忆树机制直接增强到现有 `memory.sqlite`**
- **只有在某一阶段 schema 迁移风险过高、需要隔离验证时，才允许短期旁路新库**

核心理由：

1. `chunks` 已经天然接近 L0 leaf：现有字段里已经有 `source_path`、`source_type`、`memory_type`、`visibility`、`agent_id`、`category`、`summary`、`metadata`，并接好 FTS、向量和 dedup。
2. `tasks` / `task_activities` / `experience_*` 已与 `chunks` 形成运行时联动，单库更容易保持 provenance、任务链路与经验资产的一致性。
3. 当前 store 已采用“安全增量迁移”模式，已有多轮 `ALTER TABLE ADD COLUMN` 演进，继续增表比再长期维护第二套主库更符合现有实现方式。
4. resident memory 是按 stateDir/agent scope 分库的；双库方案会把每个 scope 的维护成本成倍放大。

##### C. 对 P8-P10 的直接影响

基于上述收口，`P8-P10` 的边界进一步明确为：

- `P8`：先做 **builtin 默认来源 + configured 外来源** 的统一 source inventory
- `P9`：优先在现有 `memory.sqlite` 中扩展记忆树 schema，先把 `chunks` 视为过渡期 L0 leaf 主体，再补 source registry / score / node / edge
- `P10`：dry-run 结果优先写入同一个 `memory.sqlite` 的 report / review 表，再按需导出 Markdown 审阅报告

这三步应保持递进关系，不建议跳过 `source inventory` 直接做外来源长期入树。

#### 推荐总体架构

```text
candidate sources
  sessions/*.jsonl
  sessions/*.transcript.jsonl
  sessions/*.meta.json (selected fields)
  *.digest.json / *.session-memory.json
  MEMORY.md / memory/*.md
  tasks / task_activities / experience_candidates / experience_usages
  dream-runtime.json / DREAM.md / dreams/**/*.md
  channel-derived conversations
        ↓
memory source envelope
        ↓
source classification (raw / derived / curated)
        ↓
cleaning + exact/near dedup + scoring
        ↓
L0 leaves（可追溯原文片段）
        ↓
L1 source/session/task/day summaries
        ↓
L2 topic/project/person/agent summaries
        ↓
L3 user profile / agent diary / global timeline
        ↓
retrieval + WebChat asset view + optional Markdown sync
```

#### 分层定义建议

| 层级 | 内容 | 压缩目标 | 主要用途 |
|------|------|------|------|
| L0 raw leaves | 原始片段：消息、任务活动、memory 行、必要的 transcript 事件 | 不压缩或极轻压缩 | 可追溯、引用、审计 |
| L1 source summaries | 单会话、单任务、单日记文件、单经验资产摘要，以及 selected digest/session-memory 派生摘要 | 5-20 倍压缩 | 快速判断是否需要展开 |
| L2 topic trees | 项目、用户偏好、人物、系统模块、长期目标 | 20-80 倍压缩 | 跨来源知识组织 |
| L3 profile/global | Agent 个体日记、用户长期偏好、dream/全局时间线 | 高压缩 | 专属长期资产、启动/召回入口 |

#### 可调轻压缩策略

| 压缩档位 | 行为 | 适用场景 | 风险 |
|------|------|------|------|
| `off` | 只入库、只打分、不合并 | 调试、审计 | 数据膨胀 |
| `low` | exact dedup + L1 摘要，不做语义合并 | 默认安全档 | 压缩率有限 |
| `medium` | near dedup 聚类 + LLM 生成合并摘要，但保留原文引用 | 长期使用推荐 | 需要人工审阅可疑组 |
| `high` | 低分 leaf 默认不注入，只保留归档；topic/global 更积极 seal | 追求低 token 和高密度 | 可能漏掉冷门细节 |

#### 建议新增表（优先落在现有 `memory.sqlite`）

这次复核后，不再把“新建长期旁路 `memory_tree.sqlite`”作为默认主方案。  
优先做法是：**复用现有 `chunks` 作为 L0 leaf 主体，在同一个 `memory.sqlite` 里补齐来源注册、打分、节点、边与报告能力。**

| 表 | 用途 |
|------|------|
| `memory_sources` | 记录 source kind、source id、agent id、visibility、raw path、hash、time range |
| `memory_scores` | 保存 `chunk` 或 `node` 的 recency、source_weight、interaction、task_outcome、entity_density、llm_importance、confidence、total |
| `memory_entities` | 实体/主题索引，连接 leaf/node |
| `memory_tree_nodes` | L1-L3 summary node，保存 level、kind、scope、summary、score、time range |
| `memory_tree_edges` | node -> child leaf/node 的可追溯关系 |
| `memory_clean_jobs` | 清洗、打分、seal、digest 的后台任务队列 |
| `memory_clean_reports` | 每次 dry-run/apply 的报告、参数、风险、回滚路径 |

其中有两条边界需要明确：

1. **`chunks` 先不复制成第二份 `memory_leaves` 正文表**  
   Phase 1 优先把现有 `chunks` 当成 L0 leaf 使用，只补 registry / score / edge / node。  
   只有在后续确认 `chunks` 结构确实无法承载树化需求时，才评估是否拆出独立 leaf 表。

2. **`task_memory_links`、`experience_candidates`、`experience_usages` 保持与同库树结构共存**  
   不把任务链路、经验资产、记忆树拆到两套主存储，避免 provenance 断裂。

#### 7.7.2 最小 schema 演进方案（单库版）

这部分只定义 **P9-P10 最小可实施版**，目标不是一次做完整记忆树，而是先把：

1. 来源注册
2. L0 打分
3. L1-L3 节点
4. dry-run 报告

这四类能力补进现有 `memory.sqlite`，并且不破坏当前：

- `chunks` 检索
- FTS / vector
- `tasks` / `task_activities`
- `experience_candidates` / `experience_usages`
- resident 多 Agent scope

##### A. 设计原则

基于当前 `MemoryStore` 实现，最小 schema 演进应遵循以下原则：

| 原则 | 说明 |
|------|------|
| 不重写旧表 | 首轮不迁移 `chunks` / `tasks` / `experience_*` 主体结构，不做整表重建 |
| 追加式演进 | 优先 `CREATE TABLE IF NOT EXISTS`、`CREATE INDEX IF NOT EXISTS`、必要时少量 `ALTER TABLE ADD COLUMN` |
| `chunks` 先充当 L0 | 不先复制正文到第二份 leaf 表，先把现有 `chunks` 作为过渡期 leaf |
| provenance 优先 | 所有 node / score / report 都必须能回链到 chunk/source/task/experience |
| 幂等优先 | inventory、score、report 生成必须支持重复运行覆盖/增量更新 |
| 不入请求热路径 | inventory / score / dry-run / tree build 默认走后台任务或显式 RPC，不塞进聊天主链路同步执行 |

##### B. 首批建议新增表

首批建议只新增 5 张表，控制最小闭环：

| 表 | 是否首批必需 | 用途 |
|------|------|------|
| `memory_sources` | 是 | 建立来源注册表，把文件、会话、任务、经验、dream 等来源标准化 |
| `memory_scores` | 是 | 为 `chunk` 或 `node` 记录结构化分数与信号，不改写 `chunks` 主体 |
| `memory_tree_nodes` | 是 | 承载 L1/L2/L3 摘要节点 |
| `memory_tree_edges` | 是 | 维护 node -> chunk / node -> node 可追溯关系 |
| `memory_clean_reports` | 是 | 保存 inventory、dry-run dedup、压缩建议等审阅报告 |

以下两张表放到第二阶段再判断是否需要：

| 表 | 当前建议 | 原因 |
|------|------|------|
| `memory_entities` | 延后 | 先可用 metadata / LLM signal / simple extractor 过渡，不阻塞最小闭环 |
| `memory_clean_jobs` | 延后 | Phase 1/2 可先走显式 RPC 或 manager 方法，不急着先做 job queue |

##### C. 建议字段草案

###### `memory_sources`

用途：把“文件路径 / 会话 / task / dream / digest / session-memory / experience 资产”统一成来源注册表。

建议字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `TEXT PRIMARY KEY` | source id，例如 `file:<path>` / `task:<id>` / `session:<id>` |
| `source_kind` | `TEXT NOT NULL` | `file` / `session` / `task` / `task_activity` / `experience` / `dream` / `digest` / `session_memory` |
| `source_class` | `TEXT NOT NULL` | `raw` / `derived` / `curated` |
| `scope` | `TEXT NOT NULL` | `private` / `shared` / `team` |

| `source_path` | `TEXT DEFAULT NULL` | 文件类来源路径 |
| `source_ref` | `TEXT DEFAULT NULL` | 非文件来源的稳定引用，如 conversation/task id |

| `time_from` | `TEXT DEFAULT NULL` | 起始时间 |

| `item_count` | `INTEGER DEFAULT NULL` | 该来源下的 chunk / event 数 |

| `created_at` | `TEXT NOT NULL` | 创建时间 |
| `updated_at` | `TEXT NOT NULL` | 更新时间 |

建议索引：

用途：给 `chunk` 或 `node` 单独挂分，不把 score 先塞回 `chunks.metadata`。

建议字段：

| 字段 | 类型 | 说明 |
|------|------|------|

| `target_type` | `TEXT NOT NULL` | `chunk` / `node` |
| `target_id` | `TEXT NOT NULL` | `chunks.id` 或 `memory_tree_nodes.id` |
| `source_id` | `TEXT DEFAULT NULL` | 对应 `memory_sources.id` |

###### `memory_tree_nodes`

用途：维护 node 和 child chunk/node 的关系。

建议字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `TEXT PRIMARY KEY` | edge id |
| `parent_node_id` | `TEXT NOT NULL` | 父节点 id |

建议约束与索引：

- `UNIQUE(parent_node_id, child_type, child_id, relation)`

##### D. 对现有表的最小补充建议

首轮尽量不改旧表，但有两处值得评估的最小补充：

| 表 | 字段 | 是否首轮必做 | 理由 |
|------|------|------|------|
| `chunks` | `source_id TEXT DEFAULT NULL` | 可选，建议第二步再加 | 让 chunk 能直接指向 `memory_sources.id`，但首轮也可先通过 `source_path + metadata/source_type` 推导 |
| `chunks` | `canonical_chunk_id TEXT DEFAULT NULL` | 暂不建议首轮加 | exact dedup 首轮可先把 canonical 关系写进 report / metadata，避免过早改动热表 |

结论：

- **首轮先不强依赖 `ALTER TABLE chunks ...`**
- 优先用新增表建立树能力，减少对现有索引/检索热表的扰动

#### 7.7.3 最小迁移步骤

##### Phase 1：Schema 引入

目标：只把新表与索引引入，不做历史数据重写。

建议步骤：

1. 在 `MemoryStore` 中新增：
   - `SCHEMA_MEMORY_SOURCES`
   - `SCHEMA_MEMORY_SCORES`
   - `SCHEMA_MEMORY_TREE_NODES`
   - `SCHEMA_MEMORY_TREE_EDGES`
   - `SCHEMA_MEMORY_CLEAN_REPORTS`
2. 在 constructor 中按现有风格追加：
   - `this.db.exec(CREATE TABLE IF NOT EXISTS ...)`
   - `this.db.exec(CREATE INDEX IF NOT EXISTS ...)`
3. 在 `meta` 中写入新的 schema/version 标记，例如：
   - `memory_tree_schema_version`
   - `memory_tree_score_version`
4. 不触碰旧数据，不回填历史内容。

完成标准：

- 老库直接启动不报错
- 新库自动带上新增表
- 不影响现有 `searchKeyword` / `searchHybrid` / `tasks` / `experience` / dedup

##### Phase 2：Source Inventory 回填

目标：先把现有来源注册起来。

建议步骤：

1. 基于当前已知来源生成 `memory_sources`：
   - `chunks.source_path` 对应 file/session 来源
   - `tasks` / `task_activities`
   - `experience_candidates` / `experience_usages`
   - `digest` / `session-memory` / `dream` 文件侧来源
2. 对每个来源生成：
   - `source_kind`
   - `source_class`
   - `scope`
   - `agent_id`
   - `time_from/time_to`
   - `item_count`
3. 做成幂等 upsert，不要求一次补完所有外来源。

完成标准：

- inventory 可重复运行
- 至少 builtin 默认来源能落入 `memory_sources`
- agent scope / shared scope 不串库、不串来源

##### Phase 3：Chunk Score 回填

目标：不改 `chunks` 主体，先给现有 chunk 建立结构化分数。

建议步骤：

1. 为已有 `chunks` 扫描对应 `memory_sources`
2. 计算第一版 score：
   - `recency_score`
   - `source_weight_score`
   - `interaction_score`
   - `task_outcome_score`
   - `source_class_weight`
3. 将解释信号写入 `rationale_json`
4. `score_version` 固定为首版，如 `v1_rule_only`

完成标准：

- 同一 chunk 可查到结构化 score
- 重跑会更新同版本 score，而不是无限插入重复行
- 不影响现有 memory search 返回

##### Phase 4：Dry-run Report

目标：先把 inventory / dedup / compression 的审阅报告做出来。

建议步骤：

1. inventory 结果写入 `memory_clean_reports`
2. exact dedup preview 在保留现有返回结构的同时，新增持久化 report
3. compression preview / near dedup preview 先做 report-only，不直接写回 chunk
4. Markdown 导出只是 `memory_clean_reports.export_markdown_path` 的附加输出

完成标准：

- WebChat / RPC 可以查询最近 report
- report 能回链到来源、chunk、scope、时间范围
- 不自动 apply 任何 destructive 变更

##### Phase 5：Tree Node Build

目标：从 report / score 进一步建立 L1-L3 节点。

建议步骤：

1. L1 先做：
   - `conversation`
   - `task`
   - `day`
2. L2 再做：
   - `topic`
   - `project`
   - `agent`
3. L3 最后做：
   - `profile`
   - `global`
4. 通过 `memory_tree_edges` 回链到 chunk / node

完成标准：

- 节点可 drill-down
- provenance 可追到 chunk/source/task
- 不直接替换当前召回链路

#### 打分信号建议

| 信号 | 说明 | 来源 |
|------|------|------|
| `source_weight` | source 类型权重：用户明确输入、任务完成、经验资产高于普通闲聊 | envelope |
| `interaction` | 是否被用户确认、复用、引用、产生工具动作或产物 | task/activity/usage |
| `recency` | 最近更新时间和衰减 | source timestamp |
| `task_outcome` | 成功任务、失败复盘、被恢复任务不同权重 | tasks |
| `entity_density` | 是否包含项目名、人物、模块、文件、目标等实体 | entity extractor |
| `dedup_confidence` | exact / near / model 判断的重复置信度 | cleaning |
| `llm_importance` | 边界样本才调用模型评分 | draft/clean worker |
| `source_class_weight` | raw / derived / curated 的层级权重，避免 digest 与原文同权 | envelope |
| `privacy_scope` | private/shared/team 权限约束，不直接影响价值但影响可见范围 | resident policy |

#### 实施阶段建议

| 阶段 | 内容 | 风险 | 完成标准 |
|------|------|------|------|
| Phase 0：只读盘点 | 建 source inventory，列出 sessions/memory/tasks/experience/digest/session-memory/transcript/dream 的数量、大小、重复率 | 低 | UI 或报告能看到来源分布、重复风险、raw/derived/curated 分类 |
| Phase 1：单库 leaf/source/score 底座 | 在现有 `memory.sqlite` 中补 `memory_sources`、`memory_scores` 等 schema；先复用 `chunks` 作为 L0 leaf | 低到中 | 可查询 source registry、chunk score、source ref，重复运行幂等 |
| Phase 2：清洗与压缩 dry-run | 基于 `chunks` + source registry 做 exact/near dedup、聚类、压缩建议，只生成报告和候选 summary | 中 | 用户能审阅“保留/合并/丢弃/归档”建议 |
| Phase 3：L1/L2/L3 tree | 在同库中新增 source/task/day/topic/global summary node，derived/curated 来源作为补充层，保留 edges 回溯 | 中 | 能从主题或日期 drill down 到原始来源，并分清 raw 与 derived |
| Phase 4：接入 Agent 召回 | 新增 retrieval mode，按任务模式选择 L1/L2/L3，不直接注入低分 raw | 中 | 开启后上下文更短、更少重复、更可解释 |
| Phase 5：源文件清洗同步 | 对 `memory/*.md` 生成 patch，人工确认后写回 | 高 | 不自动破坏原始日记，所有写回可回滚 |

#### 关键产品决策

| 决策 | 建议 |
|------|------|
| 是否直接清理原始 `memory/*.md` | 不默认。先做 preview patch，用户确认后写回 |
| 是否让 LLM 直接删除记忆 | 不允许。LLM 只能给 merge/drop/archive 建议 |
| 是否长期引入 `memory_tree.sqlite` | 不建议。优先扩展现有 `memory.sqlite`；只有迁移隔离验证时才短期旁路 |
| 是否默认注入分层记忆 | 不默认。先提供检索和 UI，再按模式启用 |
| 是否保留 raw | 必须保留。树节点是资产层，raw 是审计和回滚层 |
| 是否纳入任务统计 | 必须纳入。任务是开发型 Agent 最有价值的结构化记忆 |

#### 最小 MVP 建议

最小可交付不是“一次做完整记忆树”，而是：

1. 先做只读 inventory：统计 sources、chunks、tasks、experience、session digest、daily memory 的数量和重复率。
2. 在现有 `memory.sqlite` 中新增 source registry + chunk score + clean report 能力，不新建长期第二主库。
3. exact dedup 从“删除 chunk”升级为“生成 canonical leaf 关系 / duplicate refs / review report”。
4. 生成 L1：按 conversation/task/day 三类先做摘要节点。
5. WebChat 增加“记忆资产预览”：按来源、主题、日期查看 leaf、score、summary、source refs，并明确区分 raw / derived / curated。

这样能先得到“专属数据资产”的骨架，同时避免 fuzzy dedup 和源文件改写的高风险。
