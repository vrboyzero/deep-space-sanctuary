## 一、整体安全态势评估

**总体结论：安全防护架构设计扎实，局部存在 3 处需要修复的实质漏洞，另有若干需要关注的设计决策。**

项目在以下方面表现良好：
- SSRF 防护（双层 DNS Rebinding 检测）
- 工具安全矩阵（多维度访问控制链）
- 命令执行白名单/黑名单机制
- 配对码使用加密安全随机数（`crypto.randomInt`）
- 文件写入原子性（临时文件 + rename）
- 审计日志敏感字段脱敏

需要修复的实质问题详见第二节。

## 二、安全漏洞与风险清单

### 🟡 S1 — 核心工作区关键文件保持可写时缺少自动备份与回滚保护

**文件**：`packages/belldandy-skills/src/builtin/file.ts:37`

```ts
const PROTECTED_FILES: string[] = [];  // 空数组
```

当前 `isProtectedFile()` 对 `SOUL.md` 实际不生效，但这不一定应被视为实现缺陷。若产品设计目标是让 AI 像修改 `AGENTS.md` / `CLAUDE.md` 一样，持续自我更新核心工作区文件，那么“保持可写”是一个可接受的能力选择。

真正的风险在于：`SOUL.md`、`AGENTS.md`、`IDENTITY.md`、`USER.md`、`TOOLS.md`、`MEMORY.md` 这类关键文件一旦被错误修改、过度漂移或被异常流程覆盖，当前缺少稳定的自动备份、保留和回滚机制。也就是说，问题不应定义为“禁止 AI 修改这些文件”，而应定义为“允许修改关键文件时，缺少变更防护网”。

**建议方向**：不做修改保护，改为增加核心工作区关键文件自动备份与清理机制。建议至少将 `SOUL.md`、`AGENTS.md`、`IDENTITY.md`、`USER.md`、`TOOLS.md`、`MEMORY.md` 纳入统一备份集合，保留 `1` 天、`7` 天、`30` 天三个时间层级的备份快照，并在新快照生成后自动清理同层级旧备份；必要时补一个手动恢复入口。

### 🔴 S2 — DNS Rebinding 检测在 DNS 解析失败时静默放行

**文件**：`packages/belldandy-skills/src/builtin/fetch.ts:117-125`

```ts
try {
  const { address } = await dns.lookup(hostname);
  if (isPrivateIP(address)) {
    return makeError(`SSRF 防护：DNS 解析到内网地址 ${address}`, ...);
  }
} catch (dnsErr) {
  // DNS 解析失败，允许继续（fetch 会自己处理）  ← 问题所在
}
```

DNS 解析失败时直接放行，攻击者可利用 DNS 超时窗口绕过第二层检测，在 fetch 层发起 SSRF。这是"应失败关闭（fail-closed）"场景，当前实现是"失败开放（fail-open）"。

**修复方向**：`dns.lookup` 失败时区分错误类型：ENOTFOUND（域名不存在）可放行让 fetch 自己报错；ETIMEOUT 等其他错误应拒绝请求，而非放行。

---

### 🟡 S3 — exec 工具 Safelist 只校验命令名，未过滤 shell 元字符

**文件**：`packages/belldandy-skills/src/builtin/system/exec.ts`

Safelist 检查的是命令名（如 `git`、`npm`），但如果命令参数中包含 shell 元字符（`;`、`|`、`$()`、`` ` `` 等），在 `shell: true` 模式或参数拼接场景下仍可能注入任意命令。`powershell` 在 Windows Safelist 中且参数极为强大。

**修复方向**：确保 `spawn` 始终以数组形式传递参数（不经过 shell 解析）；在文档中将 `powershell` 标注为高风险命令，建议运营层通过 `extraBlocklist` 显式禁用。

---

### 🟡 S4 — security/store.ts 的 readJson 吞掉所有非 ENOENT 错误

**文件**：`packages/belldandy-core/src/security/store.ts:184-193`

```ts
} catch (err) {
  const code = (err as { code?: string }).code;
  if (code === "ENOENT") return fallback;
  return fallback;  // ← 其他所有错误（权限、JSON 损坏）也返回空 allowlist
}
```

allowlist.json 或 pairing.json 文件损坏/权限错误时，返回空 allowlist，导致所有客户端重新进入配对流程。轻则用户体验中断，重则被利用为 DoS：写坏文件让所有已授权客户端失联。

**修复方向**：ENOENT 返回 fallback；其他错误（EACCES、JSON 解析失败）上报 warn 日志，并记录文件路径供排查。

---

### 🟡 S5 — BELLDANDY_WEB_ALLOW_PRIVILEGED_SAFE_SCOPE 风险提升未文档化

**文件**：`packages/belldandy-skills/src/security-matrix.ts:66-70`

Web 渠道默认只有 `web-safe`、`remote-safe` 两个安全域。设置 `BELLDANDY_WEB_ALLOW_PRIVILEGED_SAFE_SCOPE=true` 后，Web 渠道可访问 `privileged` 级工具（包括 `file_write`、`file_delete` 等）。这个环境变量未在 `.env.example` 中出现，存在配置失误的风险。

**修复方向**：在 `.env.example` 和安全配置文档中明确标注该变量的安全影响及适用场景（仅本地开发/受控环境）。

---

### 🟡 S6 — MCP Server 工具调用结果无验证，存在恶意 Server 注入风险

**文件**：`packages/belldandy-mcp/src/manager.ts`、`packages/belldandy-mcp/src/client.ts`

MCP 工具结果直接回传给 Agent，无内容过滤或大小硬限制。恶意或被入侵的 MCP Server 可以：
1. 在工具结果中注入 prompt injection 指令操控 Agent 行为
2. 返回超大 payload 撑爆上下文窗口

`MAX_INLINE_TEXT_CHARS = 12_000` 是内联展示阈值，不是硬性截断，超出部分会持久化到文件而非丢弃。

**修复方向**：对工具结果添加字节数硬上限；在结果注入 Agent context 前标注来源（`[MCP: server-name]`）以辅助 prompt injection 感知。

## 三、模块评价

### 3.1 belldandy-core

**总评：B+**

Gateway 装配层设计清晰，安全模型完整。

**优点**：
- 绑定安全：`0.0.0.0 + AUTH_MODE=none` 强制退出，防止误暴露
- Webhook 有独立的固定窗口速率限制器和并发飞行请求限制器
- 配对码 TTL 1h、最大 20 个 pending、超出截断——良好的资源边界
- `writeJson` 使用 `crypto.randomUUID()` 命名临时文件 + rename 原子写入，Windows 兼容降级逻辑完整

**待改进**：
- `readJson` 错误处理（见 S4）
- `system.doctor`、`system.restart` 通过 WebSocket RPC 暴露，需确认是否受 pairing 保护（`DEFAULT_METHODS` 列表中这两个方法需逐一确认 auth 守卫）
- `system.restart` 缺少防滥用限速：多次快速调用可能造成服务振荡

**功能补全建议**：
- 考虑给 WebSocket 连接添加 per-client 请求速率限制，防止单连接泛洪
- doctor 响应中若包含敏感路径信息（stateDir、日志路径），需评估是否需要脱敏

---

### 3.2 belldandy-agent

**总评：B+**

Agent runtime 设计成熟，有多层保护机制。

**优点**：
- `maxToolCalls` + `toolLoopIterationBudget` 双重限制防止无限工具调用循环
- compaction 系统完整（增量压缩 + 微压缩 + session transcript 持久化 + session restore）
- `FailoverClient` 实现多模型故障转移，`failureKind` 分类路由恢复策略
- `HookRunner` 钩子系统解耦，扩展性好

**待改进**：
- **Prompt Injection 风险**：`web_fetch` 结果、`file_read` 内容、MCP 工具结果直接流入模型上下文，无内容安全标记层。建议在高权限场景（goal 执行、子 Agent 编排）中标记外部内容来源。
- `STOP_REQUESTED_ERROR = "__BELLDANDY_STOP_REQUESTED__"` 用字符串常量作为 sentinel，若工具结果中恰好包含该字符串会误触停止（概率低但存在）。建议改为专用 Error 子类（`class StopRequestedError extends Error`）。
- `toolDefinitionTokenEstimateCache` 使用 `WeakMap` 缓存 token 估算——key 是工具定义对象引用，动态注册工具时若传入新对象会导致缓存失效重算，注意一致性。

**功能优化建议**：
- 对话压缩后的 session 恢复依赖 transcript 文件，若文件损坏则会话丢失。建议加入 SQLite 持久化作为备份层。
- `agent-registry.ts` 的多 Agent profile 注册表目前是启动时静态注册，考虑支持运行时热更新（添加/删除 profile 无需重启 Gateway）。

---

### 3.3 belldandy-skills

**总评：A-**

工具安全矩阵和执行器是项目中最成熟的模块之一，防御设计相当完善。

**优点**：
- `ToolExecutor.execute()` 包含 7 层串联安全检查：contract → toolSet → role policy → permission mode → disabled → agent whitelist → conversation restriction
- `preflightToolArguments()` 对参数做类型强制、enum 验证、必填检查，并返回修复建议
- `sanitizeArgs()` 审计日志时自动脱敏 password/token/key/secret 字段
- `fetch.ts` SSRF 防护设计完善（协议过滤 + 私有 IP 检测 + DNS rebinding 检测 + 重定向禁用 + 响应体截断）
- `file.ts` 路径验证使用 `path.resolve` + 边界检查（`isUnderRoot`），多工作区根支持，防路径遍历

**待修复**：
- `PROTECTED_FILES = []` 导致 SOUL.md 实际未受保护（S1，高优先级）
- DNS rebinding 检测 fail-open（S2）
- exec.ts safelist 未覆盖参数层 shell 注入（S3）

**代码补全建议**：
- `SENSITIVE_PATTERNS` 中有 `"token"` 宽泛匹配，`token-counter.ts`、`tokenizer.ts` 等合法文件路径会被误拒（`isSensitivePath("tokenizer.ts")` 返回 `false`，但 `isSensitivePath("token-counter.ts")` 返回 `true`）。建议对 `"token"` 和 `"password"` 改为仅匹配文件名而非路径片段，或调整为精确扩展名/文件名模式。
- `file_write` 的 `regex` 替换模式接受 Agent 输入的正则表达式，无 ReDoS 防护。建议对 regex 编译加 try-catch 超时检测，或限制最大 flags 组合。

### 3.4 belldandy-memory

**总评：B**

功能覆盖广泛（FTS5 + 向量检索 + dream + experience + memory-tree 治理），但同步 SQLite 阻塞是主要性能风险。

**优点**：
- FTS5 全文检索 + sqlite-vec 向量检索混合架构合理，adaptive-retrieval 层可动态调整策略
- memory-tree 治理系统（lifecycle、job ledger、dedup、source inventory）较完整
- dream 系统有独立的状态层隔离，Obsidian 同步有独立模块

**安全风险**：
- `better-sqlite3` 所有 DB 操作为**同步阻塞**，长时间查询（FTS 全文搜索、向量 k-NN）会阻塞整个 Node.js 事件循环，导致 Gateway WebSocket 请求积压。
- `external-memory-ingest.ts` 负责 Obsidian Markdown 目录导入，外部文件内容被直接存入记忆数据库再注入 Agent prompt，存在**不可信内容注入信任边界**风险（external content → memory → model context）。
- 记忆内容无 prompt injection pattern 过滤层（与 agent prompt injection 风险叠加）。

**功能优化建议**：
- 将高频/高延迟 SQLite 查询（向量检索、全文搜索）迁移到 `worker_threads`，避免阻塞事件循环
- `MEMORY_TREE_SCHEMA_VERSION = "p9-phase1-v1"` 应有明确的 migration 路径文档；当前 schema 升级是原地升级还是 migration 脚本需梳理清楚
- `memory-vacuum.ts`、`memory-dedup.ts` 的 backup 文件需要保留期限设置，避免无限增长
- dream 系统的触发（heartbeat/cron 完成事件）需要全局并发锁，防止多个 dream run 并发写冲突

---

### 3.5 belldandy-mcp

**总评：B+**

连接管理设计扎实（per-server 串行化锁、graceful shutdown、事件驱动工具更新、工具 inventory 代次缓存），但缺少自动恢复机制。

**优点**：
- `withServerOperationLock` 用 Promise 链实现 per-server 串行化，防止并发 connect/disconnect 竞态
- 工具 inventory 缓存有代次（generation）失效机制，避免旧工具暴露
- `getDiagnostics()` 提供详细的 server 状态视图，便于 doctor 集成
- stdio stderr 有 per-server 过滤规则（`STDIO_STDERR_IGNORE_PATTERNS`）

**风险与缺陷**：
- **无自动重连**：MCP Server 断连后（网络抖动、进程崩溃）无心跳检测和自动重连循环，需要外部触发 `reconnect()`。对于长期运行的 Gateway，这意味着 MCP 工具可能在无感知的情况下长期不可用。
- **stdio 进程无沙箱**：`StdioClientTransport` 启动的 MCP Server 进程继承 Gateway 的完整权限（cwd、env、文件系统访问）。恶意或被入侵的 MCP Server 可读取 `~/.star_sanctuary/` 目录内容（含 allowlist.json、API key 等）。
- 工具调用结果无字节数硬限制（S6），`MAX_INLINE_TEXT_CHARS = 12_000` 只是内联阈值。

**功能优化建议**：
- 实现自动重连：指数退避 + 最大重试次数 + 抖动，连接状态变化时触发 `tools:updated` 事件通知 Gateway
- 为 stdio server 进程设置 `env` 白名单，不透传 `BELLDANDY_OPENAI_API_KEY` 等敏感变量
- `reconnect()` 目前是 disconnect → connect 串行，重连期间工具不可用；可考虑先建立新连接再注销旧连接（warm reconnect）

## 四、横切关注点

### 4.1 Prompt Injection 防护（全模块）

项目中多处外部内容流入模型上下文：
- `web_fetch` 返回网页 HTML/JSON → 模型 context
- `file_read` 读取工作区文件 → 模型 context
- MCP 工具结果 → 模型 context
- `external-memory-ingest` 外来 Obsidian Markdown → 记忆 → 模型 context

目前没有统一的内容安全标注层。建议在 `tool-agent.ts` 的工具结果注入阶段，对外部来源内容添加来源标签，辅助模型识别可信/不可信内容边界。

### 4.2 错误处理不一致

各模块对错误的处理策略不统一：部分 catch 块静默吞掉异常，部分抛出，部分返回 fallback。建议：
1. 建立统一的错误分类枚举（参考现有 `ToolFailureKind`）
2. 安全相关路径（auth、pairing、allowlist）的错误必须上报 warn/error 日志，不可静默降级

### 4.3 依赖版本

- `better-sqlite3`（同步阻塞）：长期可考虑 worker_threads 隔离
- `cross-spawn`（belldandy-mcp）：确认版本无已知 CVE
- `@modelcontextprotocol/sdk`：MCP 协议尚在演进，注意版本锁定

### 5.1 实施影响评估

> 复核说明：
> - `exec` 项并非“完全未过滤 shell 元字符”。当前 `packages/belldandy-skills/src/builtin/system/exec.ts` 已通过 `splitCommandSegments()` 拦截 `` ` ``、`$()`、重定向，并对 `;`、`|`、`&` 分段校验；但最终仍以 `spawn(command, { shell: true })` 执行，仍存在残余注入面与兼容性权衡。
> - `BELLDANDY_WEB_ALLOW_PRIVILEGED_SAFE_SCOPE` 并非“完全未文档化”。`.env.example` 与 distribution `runtime.env` 已有说明；当前更大的风险点是 `packages/star-sanctuary-distribution/src/templates/default-env/runtime.env.local` 默认同时开启 `BELLDANDY_PRIVILEGED_WORKSPACE_WRITE_CHANNELS="gateway,cli,web"` 与 `BELLDANDY_WEB_ALLOW_PRIVILEGED_SAFE_SCOPE="true"`。
> - 本节新增两个明确尺度：`风险性` 指该事项继续后置时对安全 / 可用性 / 稳定性的现实影响；`工作量` 指按建议方向完成一版可交付修复的大致规模，均按 `高 / 中 / 低`、`大 / 中 / 小` 表示。

#### 1. 核心工作区关键文件保持可写但缺少自动备份与清理机制

- **作用效果**：
  - 明确承认 `SOUL.md`、`AGENTS.md`、`IDENTITY.md`、`USER.md`、`TOOLS.md`、`MEMORY.md` 应继续允许 AI 修改，保持自我演化、上下文治理与运行时调优能力。
  - 通过自动备份机制，把“允许修改”的风险从“不可逆误改”降为“可追溯、可回滚”。
  - 对人格漂移、规则污染、用户档案误写、工具说明误改、记忆索引覆盖等问题提供恢复抓手。
- **不良影响**：
  - 会增加少量磁盘占用，以及一次额外的备份写入成本。
  - 如果备份触发策略过于频繁，可能产生过多近似重复快照，影响排查效率。
- **实施风险**：
  - 需要明确备份触发点：是每次写入前备份、写入后备份，还是只对内容变更生成快照。
  - 需要明确默认 Agent、多 Agent 工作区、专属 Agent 下这组关键文件的备份目录归属与命名规则。
  - 需要明确清理策略，避免备份无限增长。
- **风险性**：中
- **工作量**：中
- **建议决策**：`split_task`
  - 不建议保护这组关键文件的写权限。
  - 建议新增自动备份机制，优先考虑 `1` 天、`7` 天、`30` 天三层保留，并将 `SOUL.md`、`AGENTS.md`、`IDENTITY.md`、`USER.md`、`TOOLS.md`、`MEMORY.md` 纳入统一清理与恢复方案。

#### 2. DNS rebinding 检测 fail-open

- **作用效果**：
  - 将当前“DNS 解析异常时放行”改成更接近 fail-closed，可补上 `web_fetch` 在 DNS 超时、异常解析窗口中的 SSRF 绕过面。
  - 对内网地址探测、云元数据地址试探等攻击路径有直接抑制作用。
- **不良影响**：
  - 合法请求在弱网络、企业 DNS、代理环境下的误拒绝概率会上升。
  - 如果错误分类过粗，可能把本应由 `fetch` 自身返回的普通域名错误也提前转成安全拒绝，降低可诊断性。
- **实施风险**：
  - 关键在于区分 `ENOTFOUND` 与 `ETIMEOUT` / `EAI_AGAIN` / 传输异常，不是简单“一律拒绝”。
  - 需要同步补充测试，否则极易在未来重构中退回 fail-open。
- **风险性**：高
- **工作量**：小
- **建议决策**：`fix_now`
  - 采用“域名不存在可放行给 fetch 自报错，其余解析异常默认拒绝”的细分策略。

#### 3. exec 工具最终仍经 shell 执行

- **作用效果**：
  - 若进一步改为 argv 直传并减少 shell 参与，可以从根上压缩命令注入面。
  - 同时能降低对 PowerShell / shell 内建语法的隐式依赖。
- **不良影响**：
  - 兼容性代价很高。当前很多命令能力依赖 shell 语义，例如管道、变量展开、内建命令、PowerShell 片段、glob 等。
  - 一刀切去掉 `shell: true` 后，可能让现有可工作的开发流程突然失效。
- **实施风险**：
  - 这是“安全增强 + 运行时兼容性”冲突项，不适合用一个小补丁粗暴处理。
  - 即便保留现有分段校验，`powershell` 仍是高能力命令，需要结合 safelist / blocklist / 文档治理一起看。
- **风险性**：中
- **工作量**：大
- **建议决策**：`split_task`
  - 先梳理真实使用场景，再决定是“部分命令改 argv 直传”还是“继续保留 shell，但进一步限制高风险命令”。

#### 4. security/store.ts 吞掉所有读取错误

- **作用效果**：
  - 能把“allowlist / pairing 文件损坏后用户只看到授权失效”转成“有明确日志、有路径、有告警信号”的可排障状态。
  - 对运维和 doctor 诊断价值很高。
- **不良影响**：
  - 如果只补 warn 日志但仍返回 fallback，授权链路仍会静默退化为“空 allowlist / 空 pending”，只是从“无感知”变成“有日志的无感知”。
  - 如果改成直接抛错，CLI 配对命令、网关配对流程、启动链路都可能被单个损坏文件阻断。
- **实施风险**：
  - 这项真正的风险在“错误语义设计”，不是“要不要打日志”。
  - 需要决定读取失败时系统应处于“degraded 但可运行”还是“拒绝继续使用安全状态文件”的模式。
- **风险性**：中
- **工作量**：小
- **建议决策**：`fix_now`
  - 至少补日志与诊断信息。
  - 更推荐继续拆出第二步：给 doctor / settings 暴露 degraded 状态，而不是仅靠日志。

#### 5. MCP 工具结果无字节数硬限制

- **作用效果**：
  - 可同时降低 prompt injection 暴露面、上下文膨胀和磁盘落盘膨胀风险。
  - 对恶意或失控 MCP Server 返回超大文本、超大 base64、超长资源结果的场景有直接收益。
- **不良影响**：
  - 限制过严会伤害合法的大文档读取、批量资源检索、多媒体返回等能力。
  - 如果把限制加在过早阶段，可能连 artifact 持久化都被砍掉，影响排障和结果追溯。
- **实施风险**：
  - 需要区分“注入模型上下文的上限”和“允许落盘保存 artifact 的上限”。
  - 只做字符数限制不够稳，二进制 / base64 更适合按字节数治理。
- **风险性**：高
- **工作量**：中
- **建议决策**：`fix_now`
  - 采用双层上限：context 注入严格限额，artifact 持久化单独设置更高但有限的配额。

#### 6. BELLDANDY_WEB_ALLOW_PRIVILEGED_SAFE_SCOPE 风险提升

- **作用效果**：
  - 如果仅补文档，收益主要是减少误配置。
  - 如果进一步收紧 distribution 默认模板，可实际降低 WebChat 默认拥有特权写能力的暴露面。
- **不良影响**：
  - 若直接把分发模板默认值改严，会影响当前“开箱即用 WebChat 可改文件”的体验，可能让部分既有使用者误以为功能回退。
  - 单纯补文档而不动默认模板，实际安全收益有限。
- **实施风险**：
  - 这里更像“默认发行策略”而不是“代码 bug”。
  - 需要明确产品立场：默认偏安全，还是默认偏本地开发便利。
- **风险性**：中
- **工作量**：小
- **建议决策**：`split_task`
  - 这项更准确的落点是“distribution 默认模板权限过宽”。
  - 建议拆成“默认值策略确认”和“模板 / 提示同步调整”两个小任务，而不是只停留在记录层。

#### 7. better-sqlite3 同步阻塞事件循环

- **作用效果**：
  - 若通过 worker / 独立线程 / 队列隔离，能改善长查询、索引、vacuum、批量写入对 Gateway 主循环的拖慢。
  - 对高并发、长生命周期 Gateway 的尾延迟和交互平滑性有中长期收益。
- **不良影响**：
  - 会把当前广泛依赖同步 `MemoryStore` API 的代码链路变复杂，调用风格、事务边界、测试方式都要跟着改。
  - 小心处理不好反而会增加锁竞争、序列化开销和故障排查复杂度。
- **实施风险**：
  - 这是架构级改造，不是小修。
  - 当前需要先拿到真实慢路径证据，否则容易提前优化。
- **风险性**：中
- **工作量**：大
- **建议决策**：`split_task`
  - 先补观测和热点识别，再决定是否进入 worker 隔离方案。

#### 8. MCP Server 无自动重连机制

- **作用效果**：
  - 一旦 server 短暂断连或重启，工具可自动恢复，减少人工干预。
  - 对长期驻留的 Gateway 体验提升明显。
- **不良影响**：
  - 重连策略如果太激进，会带来日志风暴、反复注册工具、状态抖动。
  - 如果 manager 与 client 两层都各自实现自动重连，容易出现重复重连与职责冲突。
- **实施风险**：
  - 当前 `MCPClient` 已有 `reconnect()` 循环和 session recovery 逻辑，真正缺的是 manager 层对断连事件的自动接线与统一策略。
  - 因此风险不在“能不能重连”，而在“谁负责重连、何时触发重连”。
- **风险性**：中
- **工作量**：中
- **建议决策**：`fix_now`
  - 优先在 manager 层接断连事件，复用 client 现有 `reconnect()` 能力，避免双层各自造轮子。

#### 9. file_write regex 模式无 ReDoS 防护

- **作用效果**：
  - 能避免恶意或误写的高复杂度正则在 `replace` 模式卡死单进程 Gateway。
  - 对以 WebChat 或远程入口触发 `file_write` 的场景尤其有价值。
- **不良影响**：
  - 无论采用 safe-regex 检查还是 RE2 替代，都会和 JavaScript 原生 regex 兼容性存在张力。
  - 部分合法但复杂的表达式可能被误拒。
- **实施风险**：
  - 需要在“完全兼容 JS regex”与“稳定性兜底”之间做取舍。
  - 相比大改 API，更适合做保守型限制，例如模式长度、回溯特征筛查、超时/替代引擎策略。
- **风险性**：中
- **工作量**：中
- **建议决策**：`split_task`
  - 倾向先做保守防护，不建议立刻引入大范围 regex 语义变化。

#### 10. STOP_REQUESTED_ERROR 字符串 sentinel

- **作用效果**：
  - 改为结构化 sentinel 或专用 Error class 后，代码语义会更清晰，后续维护也更稳。
  - 可降低“魔法字符串”在重构中被误复用的概率。
- **不良影响**：
  - 实际收益主要是代码整洁度与可维护性，对当前安全面和业务风险改善有限。
  - 若修改传播过广，反而会引入不必要的重构面。
- **实施风险**：
  - 当前该字符串主要用于模型调用 abort 路径内部比较，不是通用工具结果通道，实际误触概率很低。
- **风险性**：低
- **工作量**：小
- **建议决策**：`record_only`
  - 可在后续清理性重构时顺手处理，不建议挤占前几项修复窗口。
